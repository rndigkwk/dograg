# 보고서 임베딩 소규모 비교 — 2026-10-03

사용자의 범위 정정에 따라 실제 비교는 5개 PDF 중 **30페이지**로 제한했다. 기존 방식은39청크, ko 안전 재분할은158청크다. 한국어 질문20개(답변 가능18·근거 없음2)와 정답 페이지는 최초 결과 확인 전에 고정한 그대로 유지했다. 운영 코드와 인덱스를 전환하지 않았고 건강19,206건은 재임베딩하지 않았다.

## 표본 선정과 해석

gold 근거23페이지와 같은 주제·인접 위치의 다른7페이지를 포함한다. 숫자·표·서술·연도 구분 및 서로 다른 보고서 비교 질문을 담았다. 5개 보고서가 모두 포함되며 gold의 답변 가능한 질문은 모두 표본 안에 있다. 문서 추출·청크를 전체 PDF에서 준비한 기존 결과 중 이 표본만 선택하고, 이후의 BGE·ko 임베딩은 이 표본만 실행했다.

이 표본은 정답 근거가 풍부한 진단용 소규모 코퍼스다. 무작위 표본이나 전체922페이지의 난이도·질문 분포를 대표하지 않는다. gold 정답은 어떤 모델 결과도 보기 전에 고정했다. 표본은 사용자 범위 정정 후 선정했으며 전체 OpenAI의 집계 지표는 이미 알고 있었다. 질문별 순위나 점수를 보고 페이지를 고르지는 않았다. 작은 검색 공간의 점수를 전체 코퍼스 점수와 직접 비교하거나 일반화하지 않는다.

## 실제 표본 검색 성능

BGE와 OpenAI는 같은39개 청크를 사용한다. ko만128토큰 한도(특수토큰 포함),24토큰 overlap으로 같은30페이지를158개 청크로 나눈다. 모든 임베딩을 정규화해 cosine 전수 검색을 하고, 같은 페이지의 중복 청크를 최고 점수 하나로 합친다. BGE는 query instruction을 붙이지 않는다. 표본에 모델별 다른 문서를 넣지 않았다.

로컬 모델은 순차 실행, CPU FP32, torch8스레드·interop1스레드, batch16이다. 기존 캐시를 local_files_only로 사용했다. BGE는 실제 max_seq_length8192, ko는128을 확인하고 문서와 질문의 토큰 길이를 검증했다. 두 모델 모두 암묵적 truncation0건이다.

OpenAI 표본 작업의 peak는 이미 만들어진 벡터를 읽고 검색하는 작은 프로세스 값이며 API 생성 작업의 peak와 같지 않다. 앞서 실제 SDK로 전체 문서와 동일20질문을 호출한 프로세스의 Windows peak는228.7MiB, 전체문서 생성시간28.32초, 동일20질문 생성시간0.45초였다. 전체 문서 시간은39청크 표본 생성시간으로 제시하지 않는다. 그 원격 API 작업은 중단 전 전체 BGE CPU 작업과 약34초 겹쳤다.

RSS는 Windows 작업집합이며 라이브러리·토크나이저·가중치·activation·본문/벡터를 포함한다. 다른 프로세스, 운영 Streamlit·건강 검색·BM25는 포함하지 않는다. 로컬 peak에는 문서 일괄 임베딩이 포함되어, 미리 만든 색인을 검색하는 운영 query-only peak와도 다르다. 이 값은 배포 앱 전체 메모리나 모델 가중치 바이트 자체가 아니며 서로 다른 worker peak 차이를 앱 절감량으로 바로 대입할 수 없다. encode 시간은 일괄 처리 시간이고 실제 온라인 질문의 p95 지연은 측정하지 않았다.

## Claude 메모리 제안에 대한 판단

- BGE 제거의 약1.5GB 절감 방향은 타당하다. 기존 Windows 누적 측정에서 보고서 BGE 로드가1,493MiB 늘었다. 다만 OpenAI로 전환한 전체 앱의 실제 절감량을 측정한 것은 아니다. 개별 worker peak 차이로 이를 확정할 수 없다.
- ko 통일은 건강과 보고서가 **같은 모델 객체를 공유해야** 전체 BGE 모델 비용을 줄인다. 모델 이름만 바꾸면 현재 로더 구조에서는 별도 ko 객체가 중복될 수 있다. 기존127청크 중117개가128토큰을 넘고 중앙값459였으므로 안전 재분할이 필요하다는 제안은 맞다. 이번 표본은39→158청크(4.05배), 전체 준비된 청크 기준으로는1,193→4,635(3.89배)다.
- 모든 컬렉션 BGE 통일의0.6GB절감·총2.6GB는 건강 ko 단계618MiB를 뺀 산술 투영이다(3,195−618=2,577MiB). 이는2.516GiB/2.702GB로 단위를 섞은 한도 비교는 부정확하다. 건강19,206건 재임베딩·검색 회귀·객체 공유·Linux 배포 peak 검증이 필요하며 이번에는 수행하지 않았다.
- 전체 PDF 네 개 추가는1,066청크, BGE float32벡터 추가4.164MiB이므로 약1,000청크·4MB라는 예상은 근접하다. HNSW·본문·메타데이터·allocator 메모리는 별도다.
- [Streamlit 공식 문서](https://docs.streamlit.io/deploy/streamlit-community-cloud/manage-your-app)는2024년2월 기준 약690MB최소~2.7GB최대이며 언제든 변경될 수 있다고 한다. 모든 앱이 항상2.7GB를 확정 할당받는다는 표현은 과하다.

이 작은 표본만으로 특정 방식을 전체 서비스의 최고 모델이라고 단정하지 않는다. 메모리 절감 후보로 보고서 API 전환과 공유 ko를 비교할 가치가 있으며, 실제 전환 전에 표본 밖 질문 및 숫자 근거·무답변 처리를 확인하고 격리된 앱 전체 메모리를 측정해야 한다. 운영 전환은 하지 않았다.

## 실행 범위 정정 및 검증

처음 전체 PDF 비용 계산과 비교 실험 범위를 잘못 연결해 전체 OpenAI 임베딩을 실행했다. 사용자 정정 후 전체 BGE는41/75배치(656/1,193청크)에서 종료했다. 해당 부분 벡터는 완성 파일로 저장되지 않아 재사용할 수 없었다. 전체 ko는 시작하지 않았다. 정확한 실험 PID와 감독 프로세스만 종료했으며 콘솔 break가 지원되지 않아 해당 PID를 종료했다. 전체 재실행 방지 가드를 추가했다. 이후 BGE·ko는30페이지 표본만 임베딩했다.

gold SHA256: `ea4615d4f22d5929d4750ec2bd9909157f4623e50592ddfb907c32c75f349744`. 원래 gold와 byte단위 일치, 결과 후 라벨 변경 없음. OpenAI 표본 벡터는 전체 저장 벡터의 정확한 입력 인덱스와20질문 벡터를 byte단위로 검증했다. ko원문 구간 전체 보존·벡터 차원/정규화·입력해시·독립적인 점수 재계산을 검증했다. 5개의 의미있는 metric 검사가 통과했다. PDF5개와 운영 코드/기존 데이터/Chroma37개 해시가 기준과 일치했다. 운영 파일 해시 기준은 중단 전 전체BGE 인코딩 중 기록했고 PDF기준은 최초 준비 단계의 인벤토리다.
