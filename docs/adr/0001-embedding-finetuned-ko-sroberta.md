# ADR-0001: 건강 상담 임베딩으로 미세조정한 ko-sroberta 사용 (질문은 ONNX int8), 보고서는 OpenAI 임베딩

- **상태:** 채택 (2026-10-09 #78 적용, 2026-10-13 소급 작성)

## 맥락
- 건강 상담 검색의 대상은 AI Hub 상담 19,206건의 질문 글이다. 보호자의 실제 질문은 짧은 구어체("오줌 색이 달라졌어요")다. 상담 글은 길다.
- **제약:**
  - Streamlit Community Cloud의 보장 메모리는 690MB다(최대 2.7GB). CPU만 있다.
  - 질문 임베딩은 앱 안에서 돌아야 한다. 문서 임베딩은 앱 밖에서 미리 계산해 DB에 넣는다.
- 문서와 질문은 같은 모델이어야 한다. 모델이 다르면 벡터 공간이 달라 유사도가 의미를 잃는다.

## 결정
- **건강 상담:** `jhgan/ko-sroberta-multitask`(768차원)를 보호자 말투 합성 질의로 미세조정한 `ko-sroberta-dograg-b`를 쓴다.
  - 문서 벡터: PyTorch float로 미리 계산, 정규화, 코사인
  - 질문 벡터: 같은 모델의 ONNX int8(MatMul만, 채널별 스케일), torch 없이 실행
- **보고서:** OpenAI `text-embedding-3-small`을 쓴다.

**고려한 후보와 뺀 이유:**

| 후보 | 결과 | 뺀 이유 |
| --- | --- | --- |
| 기준 ko-sroberta (미세조정 전) | 짧은 질문 useful@3 0.600 | 미세조정 모델이 0.783 (p=0.0001), 긴 질문 0.72 → 0.84 (p=0.023) |
| OpenAI `text-embedding-3-small` (건강) | hit@3 0.2674 → 0.2353 | 이 데이터에서 더 나쁘다. 질문이 외부로 나가고 호출마다 비용이 든다 |
| `bge-m3` (보고서, 로컬) | 앱 최대 메모리 3,195MB | 메모리 한도 초과. OpenAI로 바꾸자 1,765MB |
| PyTorch로 질문 임베딩 | 최대 1,587MB | ONNX int8로 985MB. 같은 질문의 float 대비 코사인 평균 0.990, 최소 0.985 |
| int8 기본 설정 (모든 연산, 텐서당 스케일) | 코사인 평균 0.960 | 원본에서 너무 멀다. 채택 설정은 0.990이고, 파일이 75MB 더 크다 |

- 정확도는 앱과 같은 경로로 쟀다(float 문서 벡터 + int8 질문 + BM25 + RRF). 양자화 손실까지 포함한 값이다.
- 미세조정 비용: 합성 질의 $3.37, Colab T4 4.6분

## 결과
- **얻는 것:** 짧은 질문 검색 품질 상승, torch 없는 앱(메모리 985MB 수준), 질문이 외부로 나가지 않음(건강)
- **감수하는 것:**
  - 라벨 기준 hit@3는 그대로였다(0.2638 → 0.2602, p=0.91).
  - 모델 파일이 186MB이고, 메모리가 70MB 늘었다.
  - 비공개 모델과 데이터 리비전(`data-v2`)을 관리해야 한다.
  - 보고서 질문은 OpenAI로 나간다.
- **다시 검토할 조건:**
  - 앱이 Cloud Run(2GiB)만 쓰게 되면 질문 쪽 메모리 제약이 풀린다. 더 큰 모델(bge-m3, KURE 등)을 같은 평가로 다시 비교한다.
    - 2026-10-13: KURE-v1(미세조정 없음)을 비교했다. 하이브리드 0.723 대 0.809(p=0.008)로 지금 모델이 낫다([wiki](../wiki/embedding-finetune.md) "큰 한국어 모델"). KURE-v1 미세조정은 정확도가 더 필요할 때의 후보로 남긴다.
  - 문서 데이터가 바뀌거나 보호자 질문 분포가 달라지면 합성 질의를 다시 만들어 미세조정한다.
  - 하드 네거티브 학습(Day 74)이 같은 holdout에서 유의하게 나으면 새 ADR로 대체한다.
  - 모델을 바꾸면 문서 19,206건 재색인이 필요하다. 그 비용(시간, DB 리비전)을 함께 적는다.

## 추가 확인: 잘림 비율 (2026-10-13)
결정 당시에는 잘림 비율을 축으로 보지 않았다. 이 모델은 128토큰에서 문서를 자르고, 상담 글의 52%가 잘린다(앞부분 약 250자만 반영). Day 58 교안 01은 잘림 1% 초과를 탈락 조건으로 둔다. 그래서 잘림을 풀었을 때 나아지는지 쟀다.
- 같은 모델로 문서를 256·512토큰으로 임베딩하거나, 128토큰 창으로 나눠 가장 맞는 조각의 점수를 썼다(220문항 useful@3).
- 앱 방식(하이브리드)에서 지금(0.823)보다 나은 설정이 없었다(0.795~0.800, 모두 p>0.2).
- **결정은 그대로다.** 이 데이터에서는 잘림이 검색 품질을 떨어뜨리지 않았다. 문장 임베딩만 써도 길게 넣어 나아지지 않았다(128·256·512토큰 Dense 0.832·0.841·0.818). 보호자 질문 글은 앞부분에 주요 증상이 오고, 모델도 128토큰으로 학습했다. 키워드 검색은 건강 검색 점수를 올리지 않아(Dense 0.827 대 하이브리드 0.809) 잘림의 보완 이유가 아니다.
- **다시 검토할 조건 추가:** 뒷부분에 핵심이 오는 문서(긴 경과 기록 등)가 늘면 잘림을 다시 잰다. 모델을 바꿀 때는 잘림 비율을 비교표에 넣는다.
- (처음에는 "키워드 검색이 글 전체를 본다"를 이유로, "키워드 검색을 빼면"을 다시 볼 조건으로 적었다. 측정으로 뒷받침되지 않아 2026-10-13에 고쳤다. Supabase 장애 때 쓰는 대체 검색은 실제로 건강 키워드 검색을 뺐다, ADR-0007.)
