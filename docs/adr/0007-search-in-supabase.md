# ADR-0007: 벡터 검색과 키워드 검색을 Supabase(pgvector + PGroonga)로 옮김

- **상태:** 채택 (2026-10-13). 두 배포 모두 `SEARCH_BACKEND=supabase`로 운영한다(아래 "배포 확인"). ADR-0003(메모리 안 전수 검색)을 대체한다.

## 맥락
- 앱 메모리의 대부분은 벡터가 아니라 키워드 검색이다. Kiwi 형태소 분석기와 BM25 색인이 약 320MB를 쓴다.
- ADR-0003으로 벡터를 메모리 안 전수 검색으로 바꿔도 앱 최고 메모리는 910MB다. Streamlit Community Cloud 보장값(690MB)을 넘는다.
- 메모리가 풀리면, 메모리 때문에 접었던 실험을 다시 할 수 있다. 예: 더 큰 질문 임베딩 모델.
- 외부 DB를 써도 된다(ADR-0004 거절). Supabase 서울에는 pgvector 0.8.2와 PGroonga 3.2.5가 있다.

## 결정 (제안)
건강·보고서 컬렉션을 Supabase 서울의 표 두 개로 옮긴다(`src/supabase_store.py`, `scripts/export_supabase_store.py`).
- 벡터: pgvector HNSW. 반복 탐색을 켜서 필터 결과가 덜 차지 않게 한다.
- 키워드: PGroonga "비슷한 문서" 검색(`&@*`). Kiwi BM25를 대신한다.
- 질문 임베딩은 지금처럼 앱 안의 ONNX 모델로 한다.

**측정 (2026-10-13, 로컬에서 서울 Supabase로):**

| | Chroma + Kiwi (지금) | 메모리 안 전수 + Kiwi (ADR-0003) | **Supabase** |
| --- | ---: | ---: | ---: |
| 앱 최고 메모리 (3회) | 990~991MB | 909~910MB | **442MB** |
| chromadb / Kiwi 로딩 | 예 / 예 | 아니요 / 예 | 아니요 / 아니요 |
| 건강 useful@3, 하이브리드 (220문항) | 0.809 | 0.809 (같은 결과) | **0.818** (p=0.85, 차이 없음) |
| 보고서 정답 페이지 (상위 6, 18문항) | 16/18 | 16/18 | 15/18 |
| 하이브리드 검색 1건 (질문 임베딩 포함) p50 | 459ms | – | **242ms** |
| dense 결과가 Chroma와 같은 비율 (상위 12) | – | 0.9975 | 0.9946 (필터 0.9933) |

- **PGroonga 키워드만 쓰면 약하다.** "비슷한 문서" 방식이 useful@3 0.418, OR 검색이 0.300으로, Kiwi BM25(0.595)보다 낮다. 형태소 사전 없이 글자 n-gram으로 찾기 때문이다. 하지만 dense와 합치면 같은 수준이다. 하이브리드에서 키워드는 보조라서다.
- **검색이 더 빠르다.** Kiwi로 긴 질문을 분석하는 시간이 빠지고, DB 왕복은 서울에서 수 ms다.
- **Supabase 사용량:** DB 전체 448MB(무료 한도 500MB), 내역은 아래 "채택 준비". 상담 본문도 DB에 들어간다(소유자의 비공개 프로젝트).

## 채택 준비 (2026-10-13)

**1. 저장 공간: 무료 한도(500MB)에 가깝다.** DB 전체가 447.9MB다(`pg_database_size`).

| 항목 | 크기 |
| --- | ---: |
| 건강 표 (본문·메타데이터·벡터, HNSW 79MB 포함) | 176.9MB |
| 보고서 표 (HNSW 10MB 포함) | 21.9MB |
| PGroonga 색인 (Groonga 객체 합, 표 크기에 잡히지 않음) | 약 189MB |
| 시스템 카탈로그 등 나머지 | 약 60MB |

- PGroonga가 벡터 표 둘을 합친 만큼 쓴다. 본문을 자기 파일에 한 벌 더 저장하고(건강 38MB, 보고서 34MB), 객체마다 고정 크기(약 12.6MB)가 있다.
- **벡터를 float16(`halfvec`)으로 저장한다.** 벡터와 HNSW가 절반이 되어 약 70MB가 준다. 정확도는 그대로다(`scripts/evaluate_halfvec.py`).
  - 건강 220문항: 상위 12건 겹침 1.0, 상위 3건 순서까지 220/220 같음, useful@3 dense 0.827·하이브리드 0.823 그대로
  - 보고서 18문항: 상위 20건 겹침 1.0, 정답 페이지 16/18 그대로
  - 벡터 1개: 건강 3,080 → 1,544바이트, 보고서 6,152 → 3,080바이트
- 기존 표는 제자리에서 바꾼다(`scripts/export_supabase_store.py --to-halfvec`). HNSW를 먼저 지우고 열 형식을 바꾼 뒤 다시 만들어, 변환 중에도 한도를 넘지 않게 했다. `PgVectorStore`는 열 형식을 읽어 맞추므로 변환 전후 모두 동작한다.

**2. 장애 때 로컬 검색으로 넘어가기 (`src/supabase_store.py`, `src/resources.py`)**
- `SEARCH_BACKEND=supabase`이고 `SUPABASE_DB_URL`이 있을 때만 Supabase를 쓴다. 기본값은 지금처럼 로컬(Chroma + Kiwi BM25)이다.
- DB 오류(연결 실패, 3초 연결·쿼리 제한 초과)가 나면 그 질문부터 로컬 저장소로 답한다. 로컬 저장소는 이때 처음 불러온다.
- 프로세스당 하나인 차단기를 네 검색(건강·보고서 × 벡터·키워드)이 함께 쓴다. 장애 한 번에 기다림도 한 번이다. 5분 뒤 Supabase를 다시 시도한다.
- 쿼리 오류(코드 버그)는 숨기지 않고 그대로 올린다.
- 측정 (`scripts/evaluate_search_fallback.py`, 프로세스를 새로 띄워 같은 질문 8개, 이 PC에서 서울로):

| 상황 | 첫 질문 | 이후 질문 | 최고 메모리 | 상위 3건 |
| --- | ---: | ---: | ---: | --- |
| 로컬 (지금 앱) | 9.0초 | 0.05초 | 1,221MB | 기준 |
| Supabase 정상 | 3.9초 | 0.04~0.09초 | **621MB** | dense는 같음, 키워드는 PGroonga라 다름(품질은 위 측정처럼 같음) |
| DB에 닿지 않음 | 11.5초 | 0.05초 | 1,226MB | 로컬과 같음 (차단 1회) |
| 비밀번호 틀림 | 12.1초 | 0.05초 | 1,230MB | 로컬과 같음 (차단 1회) |

- 장애 때 첫 질문이 로컬보다 2.5~3초 늦다(연결 제한 3초). 그 뒤로는 지금 앱과 같다.
- 한 번 넘어가면 로컬 저장소가 메모리에 남는다. DB가 돌아와도 재시작 전까지는 메모리가 지금 앱 수준이다.
- 검색 한 번이 DB 왕복 1번이 되도록 HNSW 설정을 연결마다 한 번만 보낸다. 처음에는 검색마다 5번 왕복해 질문당 약 0.9초가 걸렸다.

**3. 회귀 (2026-10-13, halfvec 변환 뒤, 같은 시각에 두 모드를 나란히)**

| | 로컬 (지금) | Supabase |
| --- | ---: | ---: |
| CRAG: 답할 수 있는 건강 질문에서 거절 (20) | 0 | 0 |
| CRAG: 답할 수 없는 건강 질문 거절 (20) | 16 | 17 |
| CRAG: 보고서 정답 페이지 (18) | 16/18 | 15/18 |
| CRAG: 오류 (60) | 0 | 0 |
| 보고서 답 정답 (18문항 × 2회) | 29/36 (틀림 3) | **30/36 (틀림 0)** |
| 건강 질문 평균 응답 시간 | 10.5초 | 10.7초 |

- 나빠진 항목이 없다. 보고서 정답 페이지 1문항 차이는 #114와 같은 결과이고, 답의 정답 수는 오히려 같거나 많다.
- 실행: `SEARCH_BACKEND=local|supabase uv run --group tools python scripts/evaluate_crag.py --output …`, `scripts/evaluate_report_pages.py compare --variants hybrid --repeats 2`

## 배포 확인 (2026-10-13)
- Streamlit Cloud: 앱 Secrets에 `SEARCH_BACKEND`, `SUPABASE_DB_URL`. Cloud Run: repository secret `SEARCH_BACKEND`와 Secret Manager `SUPABASE_DB_URL`(revision `ragdog-00028`).
- 두 배포에서 질문할 때 Supabase 벡터 색인 사용 횟수가 늘었고(`pg_stat_user_indexes`), Langfuse 기록의 `search_backend`가 `supabase`다.
- 같은 질문 4개(건강 3, 보고서 1). 메모리는 질문마다 Langfuse 기록에 남긴 값이다(`src/memory_limits.process_memory_mb`).

| | Streamlit Cloud (오리건 추정) | Cloud Run (서울) |
| --- | ---: | ---: |
| 답변 완료 (4문항) | 10.4~14.0초 | 7.3~11.7초 |
| 질문 중 메모리 (RSS) | 592~636MB | 572~614MB |
| 최고 메모리 (시작 포함, VmHWM) | **702MB** | 기록 안 됨 (샌드박스가 제공하지 않음) |

- Streamlit Cloud 최고 메모리가 로컬 측정(991MB, Chroma + Kiwi)에서 702MB로 줄었다. 보장값 690MB에 거의 닿는다.
- 답변 시간은 회귀 평가의 로컬 값(건강 평균 10.5초)과 같은 수준이다. 미국에서 서울 DB까지의 왕복은 검색당 1번이라 체감되지 않는다.

## 결과
- **얻는 것:**
  - 앱 최고 메모리가 절반 이하로 줄어 보장값 690MB 안에 들어간다.
  - 남는 약 250MB로 더 큰 질문 임베딩 모델 등을 시도할 수 있다.
  - 이미지와 비공개 데이터 다운로드가 작아진다.
  - 데이터를 갱신할 때 앱을 다시 배포할 필요가 없다.
- **감수하는 것:**
  - Supabase가 멈추면 로컬 검색으로 넘어간다(위 2). 그동안 메모리는 지금 앱 수준(약 1.2GB)이다. Streamlit Cloud에서는 보장값을 넘는 지금 상황과 같다.
  - Streamlit Cloud(오리건 추정)에서는 검색마다 서울까지 왕복이 붙는다. 질문당 0.1~0.3초 예상이고 재지 않았다.
  - 무료 플랜의 미사용 일시 정지 정책을 확인하고, 필요하면 점검 작업이 DB도 깨우게 한다.
  - 보고서 정답 페이지가 1문항 줄었다(18문항이라 판단하기엔 작다).
- **채택 전에 할 것:**
  - ~~DB 연결 실패 때의 동작을 정한다~~ → 로컬 검색으로 넘어가기 (위 2)
  - ~~앱 로더를 바꾼다~~ → `SEARCH_BACKEND` 설정으로 전환 (기본은 로컬)
  - ~~Supabase 표를 halfvec으로 바꾼다~~ → 2026-10-13 변환, DB 448 → 350MB
  - ~~Supabase 모드로 회귀를 확인한다~~ → 위 3, 나빠진 항목 없음
  - 배포 비밀값에 `SEARCH_BACKEND = "supabase"`와 `SUPABASE_DB_URL`을 넣고, Streamlit Cloud와 Cloud Run에서 실제 지연과 메모리를 잰다.
- **다시 검토할 조건:** Supabase 장애·지연이 운영에 문제가 되면 ADR-0003(메모리 안 전수)으로 돌아간다. 그 코드는 남겨 둔다.
