# ADR-0003: 건강 상담 벡터 저장소로 FAISS 전수 검색(IndexFlatIP) 사용

- **상태:** 제안 (2026-10-13). 아직 Chroma를 쓴다. 아래 "채택 전에 확인할 것"을 통과하면 채택한다.

## 맥락
- 지금 건강 상담 벡터는 Chroma(로컬 파일, HNSW)에 있다. 처음 수업 예제를 따라 정했고, 다른 저장소와 비교한 기록이 없었다.
- 규모: 문서 19,206건, 768차원, 정규화, 코사인(ADR-0001). 벡터만 약 56MB다.
- 앱이 보내는 질의:
  - 질문 하나당 상위 12건(ADR-0002)
  - 가끔 메타데이터 필터(나이 단계·진료과)
  - BM25는 저장소 밖(메모리 안 Kiwi + rank_bm25)에서 돌아 저장소 선택과 무관하다.
- 제약:
  - 앱 안에서 돈다. 외부 DB는 장애 지점이 된다(ADR-0004).
  - Streamlit Cloud의 보장 메모리는 690MB다.
  - 검색은 답변 전 단계라 짧아야 한다.

## 결정
건강 상담 벡터를 FAISS `IndexFlatIP`(전수 검색, 정규화 벡터의 내적 = 코사인)로 옮기는 것을 제안한다. 필터는 `IDSelectorBatch`로 건다.

**측정** (`scripts/compare_vector_stores.py`, 2026-10-13):
- 같은 벡터를 각 저장소에 넣고, 검증 질문 561개를 앱처럼 ONNX int8로 임베딩해 찾았다.
- 정확도는 numpy 전수 검색 대비 recall@12다. 같은 벡터라서 차이는 근사 검색이 놓친 것뿐이다.
- 지연은 이 PC(서울)에서 잰 질문 1건 시간이다.
- 메모리는 새 프로세스에서 저장소를 불러올 때 늘어난 RSS다.

| 후보 | recall@12 | recall@12 (필터) | 지연 p50 / p95 | 메모리 증가 | 저장 크기 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Chroma HNSW (지금) | 0.998 | 1.000 | 4.9 / 5.9ms | 364MB | 177MB (폴더 전체, 보고서·FTS 포함) |
| **FAISS 전수 검색** | **1.000** | **1.000** | **4.0 / 4.8ms** | **82MB** | **56MB** |
| FAISS HNSW (M=16, ef=40) | 0.986 | 0.963 | 0.3 / 0.4ms | 79MB | 59MB |
| pgvector 전수 검색 (Supabase) | 1.000 | 1.000 | 242 / 260ms | (앱 밖) | 78MB |
| pgvector HNSW (Supabase) | 0.991 | 0.938 | 139 / 158ms | (앱 밖) | 153MB |

- **Supabase 프로젝트는 뭄바이(ap-south-1)에 있다.** 서울에서 왕복 한 번(`select 1`)에 p50 165ms가 걸렸다. pgvector 지연의 대부분은 네트워크다.
- pgvector HNSW의 필터 재현율이 낮다(0.938). HNSW로 후보를 먼저 찾은 뒤 필터를 적용해서, 걸러지면 12건이 덜 찬다.

**선정 절차 (교안 Day 58):**
1. **제약:** 앱 안에서 돌 것(ADR-0004), recall@12 ≥ 0.98, 필터 recall ≥ 0.95, 지연 p95 ≤ 300ms. pgvector 두 후보가 첫 조건에서 빠진다. HNSW 쪽은 필터 재현율도 미달이다.
2. **지배:** Chroma는 FAISS 전수 검색에 모든 축(정확도, 지연, 메모리, 저장)에서 같거나 나빠 지배당한다. 파레토 후보는 FAISS 전수 검색과 FAISS HNSW다.
3. **고정 기준 점수:**
   - 기준: 지연 300ms, 메모리 690MB, 저장 500MB
   - 가중치: 정확도 0.7, 나머지 각 0.1. 정확도는 필터 유무 recall의 평균이다.
   - 결과: FAISS 전수 0.976, FAISS HNSW 0.959, Chroma 0.910
   - 검산(환율): 정확도 1%p = 지연 21ms = 메모리 48MB = 저장 35MB
4. **민감도:** 가중치를 하나씩 ±20% 바꾼 8가지 조합 모두 FAISS 전수 검색이 1위였다. 가장 작은 격차는 0.015다.

**FAISS HNSW를 고르지 않는 이유:** 이 규모에서는 전수 검색도 4ms다. HNSW로 얻는 3.7ms보다, 필터 재현율 0.963로 잃는 것이 크다.

## 결과
- **얻는 것:**
  - 정확한 검색(근사 손실 0)
  - 프로세스 메모리 감소. 측정한 증가분 차이는 282MB다.
  - 저장 크기 감소(벡터 56MB)
- **감수하는 것:**
  - 문서 본문·메타데이터를 따로 들고 있어야 한다. 지금 Chroma가 함께 갖고 있다.
  - LangChain `Chroma` 대신 직접 만든 검색 함수를 쓴다.
  - 필터는 ID 목록으로 바꿔 넘긴다.

**채택 전에 확인할 것:**
- **메모리 차이는 상한이다.** Chroma 쪽 364MB에는 `chromadb` 라이브러리 로딩이 들어 있다. 보고서 컬렉션(OpenAI 임베딩)도 Chroma에 있어서, 건강만 옮기면 라이브러리 몫은 그대로 남는다. 앱 전체 최고 메모리(`scripts/measure_memory.py`)를 두 경우로 잰다: 건강만 옮김, 둘 다 옮김.
- 검색 결과가 같다는 것을 앱 경로로 확인한다(`scripts/evaluate_app_retrieval.py`, useful@3). 전수 검색이라 Chroma보다 나쁠 수는 없다(recall 0.998 → 1.000).
- 비공개 데이터셋에 새 리비전을 올린다(FAISS 색인 + 메타데이터). 옛 코드가 새 파일을 받지 않게 리비전을 고정한다.

**다시 검토할 조건 (시나리오):**
- **문서가 10배(약 19만 건)가 되면:** 벡터만 약 560MB라 앱 안 저장소(FAISS·Chroma 모두)가 메모리 690MB 제약을 넘는다. 그때는 같은 지역의 외부 저장소(pgvector 등)를 다시 비교한다. 외부 DB를 쓰면 ADR-0004도 함께 다시 본다.
- **1024차원 모델로 바꾸면(ADR-0001 재검토):** 벡터가 약 75MB가 된다. 지금 결론은 그대로이고 숫자만 다시 잰다.
- **pgvector를 다시 볼 때:** 서울 지역(ap-northeast-2) 프로젝트로 잰다. 뭄바이 수치는 네트워크가 대부분이다. HNSW 필터는 반복 탐색(`hnsw.iterative_scan`) 설정을 함께 잰다.
