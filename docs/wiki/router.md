# 질문 라우터

질문을 `rag`(건강) / `sql`(반려동물 시설: 병원·약국·동반 시설·미용·위탁·장묘) / `analysis`(보고서) / `none`(일반 대화) 중 하나로 보낸다. 시설 종류 판별 규칙은 [places-data.md](places-data.md). 구현은 `src/tools/router.py`의 `classify_question()`.

## 구조: 키워드 우선, LLM은 마지막

판단 순서:

1. 범위 밖 키워드(날씨, 뉴스, 주식, 환율 등) → `none`
2. 보고서 키워드 + "보고서"라는 단어 → `analysis`
3. 병원 관련 + 조회 의도 키워드(주소, 근처, 몇 곳 …) → `sql`
4. 건강 키워드(구토, 설사, 기침 …) → `rag`
5. 병원 관련 → `sql` / 보고서 키워드만 → `analysis`
6. 위에서 결정되지 않으면 **LLM 구조화 출력**(`RouteDecision`)으로 분류
7. API 키가 없으면 대화 맥락을 포함한 키워드 규칙으로 대체

**왜 이렇게 했나:** 대부분의 질문이 키워드로 결정되므로 LLM 호출 없이 거의 0 ms에 분류된다. 아래 측정에서도 40개 질문 중 LLM이 호출된 건 5번뿐이다. API 키가 없어도 병원 검색이 동작해야 한다는 요구도 있었다.

**대가:** 키워드 목록이 `src/tools/router.py`(보고서 키워드는 `src/tools/report.py`)에 하드코딩돼 있고, 키워드가 겹치면 위 순서대로만 결정된다. 새 기능을 추가할 때는 키워드 충돌을 확인해야 한다.

## Jev 라우터 섀도 비교 (2026-09-28, 2026-09-29)

외부 분류 모델 Jev(`jev-1.13.0`)를 **섀도 모드**로 돌려 기존 라우터와 비교했다. Jev의 결과는 앱 동작을 바꾸지 않는다.

- 질문: 합성 질문 40개, 경로별 10개 (`tests/data/jev_router_questions.json`)
- 실행: `uv run --with typesafe-sdk==0.7.1 python scripts/jev_router_shadow.py`
- 결과: `output/jev_router_shadow_results.json`(9/28), `output/jev_router_speed_2026-09-29.json`(9/29)

### 오분류 사례

| 질문 ID | 질문 | 정답 | 기존 | Jev |
| --- | --- | --- | --- | --- |
| `none-10` | 강아지와 상관없는 파이썬 리스트 정렬 방법을 알려줘 | none | **analysis** (두 날 모두) | none |
| `analysis-09` | 반려동물 입양비와 생활비를 비교해줘 | analysis | analysis | **none** (9/28만) |

`none-10`의 원인: "상관**없는**"에 들어 있는 "상관"이 보고서 분석 키워드(`REPORT_ANALYSIS_KEYWORDS`의 `"상관"`)와 부분 문자열로 일치한다. 범위 밖 키워드에 "파이썬" 같은 단어도 없어서 1단계에서 걸러지지 않는다. 띄어쓰기를 지우고 부분 문자열로 비교하는 키워드 방식의 구조적인 약점이다.

### 해석과 결정

- 정확도는 사실상 같다. 40개 표본에서 1개 차이는 의미 있는 차이가 아니다.
- 지연 분포가 다르다. 기존 라우터는 키워드로 걸리면 즉시(0.04 ms), LLM으로 넘어가면 1.7~1.8초다. Jev는 항상 약 200 ms다.
- Jev는 같은 질문(`analysis-09`)에 대해 날짜에 따라 결과가 달랐다 → 비결정성이 있다.
- **현재 상태: 앱은 기존 라우터를 사용한다.** 명시적인 결정 기록은 없고, 아래는 수치를 바탕으로 한 해석이다. Jev를 도입하면 외부 의존성과 모든 질문에 대한 API 호출이 추가되는데, 얻는 이득은 LLM 폴백 경로의 p95 단축과 키워드 오탐 1건 해소 정도다.

### 남은 과제

- ~~`none-10` 오탐 수정~~ → 2026-10-04 키워드를 "상관관계"로 바꿨다. 같은 날 새 보고서 주제어(장묘, 동물복지, 복지실태, 반려동물 산업, 시장 규모, 실태조사, 펫보험)를 추가했다.
- 키워드에 걸리지 않는 질문 비율을 실제 사용 로그로 측정하면, LLM 폴백 지연이 실제로 얼마나 체감되는지 알 수 있다

## 신호 충돌은 LLM에 맡기기 (2026-10-04)

CRAG 평가 60문항에서 오분류 4건이 나왔다. 건강 질문이 "가까운 동물병원에 갈 수 없어서"라는 표현 때문에 병원 검색으로 갔고, 보고서 질문이 "동물병원" 단어 때문에 병원 검색으로 갔다. 원인은 키워드 규칙이 고정된 우선순위(병원 찾기 > 건강 > 병원 > 보고서)로 충돌을 처리했기 때문이다.

**바꾼 규칙**
1. 범위 밖 키워드 → `none`, "보고서" + 보고서 주제 → `analysis` (그대로)
2. **신호가 하나뿐일 때만 규칙으로 결정한다.**
   - 건강 신호만 있고 병원 찾기 표현이 없으면 `rag`
   - 병원 언급만 있으면 `sql`
   - 보고서 주제만 있으면 `analysis`
3. 신호가 충돌하거나 아무 신호도 없으면 LLM 라우터가 판단한다. 프롬프트에 판단 기준 3줄을 추가했다(건강 상황 설명은 병원 언급이 있어도 `rag`, 병원 찾기 요청만 `sql`, 연구·조사의 통계는 `analysis`).
4. 모델이 없으면 예전 우선순위를 그대로 쓴다.

건강 키워드도 평가에서 놓친 표현으로 보강했다(부풀, 삼켰, 흉터, 경련 등). "혹", "토"처럼 짧은 말은 "혹시", "토요일"에서 오탐이 나므로 넣지 않았다.

**결과:** 평가셋 60문항 중 오분류 4건(h08, h09, h13, r14)이 모두 바로잡혔고, 새로 틀린 질문은 없다. LLM 라우터까지 간 질문은 13개다. 경계 사례 9개도 모두 맞았다. 예: "토하는데 근처 동물병원 찾아줘"는 `sql`, "구토하는데 동물병원에 가야 하나요?"는 `rag`.

## 시설 검색 라우팅 평가 (2026-10-07)

시설 종류가 6가지(병원·약국·동반 시설·미용·위탁·장묘)로 늘어서 시설 검색 전용 평가 세트를 만들었다. `tests/data/place_routing_questions.json`, 36문항.

- 시설 검색 26문항: 종류별로 4~6문항, 지역·근처·개수·"N곳만" 표현을 섞었다.
- 헷갈리는 질문 10문항: 시설 단어가 들어갔지만 시설 검색이 아닌 질문이다.
  - 건강 질문: "미용 후 피부가 빨개지고 가려워해요", "펜션에 데려갔더니 계속 설사를 해요", "애견호텔에 맡긴 뒤로 기침을 해요"
  - 보고서 질문: "반려동물 장묘 서비스 이용 실태", "보고서에서 동물병원 진료비 평균"
  - 인사

재현: `uv run python scripts/evaluate_place_routing.py --llm` → `output/place_routing.json`

| 종류 판별 (시설 검색 26문항) | 26/26 | 26/26 |

- **LLM 라우터 호출:** 36문항 중 5문항만 LLM까지 갔다. 나머지는 키워드 규칙이 바로 정했다.
- **규칙만 썼을 때 틀린 2문항:**
  - "사람 약국에서 산 해열제를 강아지한테 먹여도 돼?"
  - "강아지가 카페 음료를 마시고 토했어요"
  - 둘 다 건강 키워드에 "토했"과 "먹여도"가 없어 `none`이 됐다. ("토해"는 있었다.)
- **조치:** 두 표현을 건강 키워드에 넣었다. 기존 라우터 평가 40문항(`jev_router_questions.json`)의 규칙 결과는 바뀌지 않았고, CRAG 평가 60문항에는 두 표현이 없다.
- **회귀 방지:** `tests/test_place_routing.py`가 규칙만으로 36문항이 모두 맞는지 확인한다.
