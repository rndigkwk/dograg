# 질문 라우터

질문을 `rag`(건강) / `sql`(반려동물 시설: 병원·약국·동반 시설·미용·위탁·장묘) / `analysis`(보고서) / `none`(일반 대화) 중 하나로 보낸다. 시설 종류 판별 규칙은 [places-data.md](places-data.md). 구현은 `src/tools/router.py`의 `classify_question()`.

## 구조: 키워드 우선, LLM은 마지막

판단 순서:

1. 범위 밖 키워드(날씨, 뉴스, 주식, 환율 등) → `none`
2. 보고서 키워드 + "보고서"라는 단어 → `analysis`
3. 병원 관련 + 조회 의도 키워드(주소, 근처, 몇 곳 …) → `sql`
4. 건강 키워드(구토, 설사, 기침 …) → `rag`
5. 병원 관련 → `sql` / 보고서 키워드만 → `analysis`
6. 위에서 결정되지 않으면 **LLM 구조화 출력**(`RouteDecision`)으로 분류
7. API 키가 없으면 대화 맥락을 포함한 키워드 규칙으로 대체

**왜 이렇게 했나:** 대부분의 질문이 키워드로 결정되므로 LLM 호출 없이 거의 0 ms에 분류된다. 아래 측정에서도 40개 질문 중 LLM이 호출된 건 5번뿐이다. API 키가 없어도 병원 검색이 동작해야 한다는 요구도 있었다.

**대가:** 키워드 목록이 `src/tools/router.py`(보고서 키워드는 `src/tools/report.py`)에 하드코딩돼 있고, 키워드가 겹치면 위 순서대로만 결정된다. 새 기능을 추가할 때는 키워드 충돌을 확인해야 한다.

## 라우터 속도: 추론 강도, Jev, OpenAI Decisions (2026-10-09)

**질문:** 키워드 규칙이 못 정한 질문은 LLM 폴백으로 가는데 1.5초쯤 걸린다. 교안의 Jev(day47·49)나 OpenAI Decisions API(분류 전용, 출력 토큰 무료)를 쓰거나, 폴백의 추론 강도를 낮추면 빨라지고 정확도는 그대로일까?

**방법:** `scripts/evaluate_router_speed.py`. 정답 경로가 있는 평가 질문 136개(Jev 섀도 40 + 시설 라우팅 36 + CRAG 60, CRAG는 건강 그룹 → rag, 보고서 그룹 → analysis)를 순서대로 한 번씩 돌렸다. LLM 폴백은 추론 강도마다 2회. Jev(`jev-1.13.0`)와 Decisions(`gpt-6-luna`)는 모든 질문에 돌려, "규칙 + 외부 모델 폴백"을 같은 기록으로 계산했다. 경로 설명은 앱의 `ROUTER_PROMPT`와 같은 기준으로 썼다. 시간은 로컬에서 잰 호출 한 번의 왕복이다.

- 규칙이 정한 질문: **116/136 (85%)**, 그중 115개 정답. LLM까지 간 질문: 20개.

| 방식 | 정답 (136) | 평균 | 중앙값 | p95 | 폴백 20개만: 정답 / 평균 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 규칙 + LLM, 기본 추론 (지금) | 134 | 227ms | 0ms | 1.57~1.72초 | 19 / 1.55초 |
| 규칙 + LLM, 추론 low | 134 | 200~222ms | 0ms | 1.41~1.53초 | 19 / 1.36~1.51초 |
| 규칙 + LLM, 추론 none | 134 | 217~221ms | 0ms | 1.63~1.65초 | 19 / 1.47~1.50초 |
| **규칙 + Jev 폴백** | 134 | **43ms** | 0ms | **280ms** | 19 / **0.29초** |
| **규칙 + Decisions 폴백** | 134 | **52ms** | 0ms | **374ms** | 19 / **0.35초** |
| Jev만 (모든 질문) | 128 | 305ms | 281ms | 485ms | |
| Decisions만 (모든 질문) | 131 | 347ms | 339ms | 518ms | |

- **추론 강도는 원인이 아니었다.** low·none으로 낮춰도 폴백이 1.4~1.5초로 거의 같다. 이 지연은 추론이 아니라 일반 채팅 호출(구조화 출력)의 기본 왕복이다. 근거 평가에서 추론을 끈 효과(9.1 → 6.0초)는 출력이 긴 판정이라서 났던 것이다.
- **폴백을 Jev나 Decisions로 바꾸면 폴백 질문이 1.2~1.3초 빨라지고 정확도는 같다**(19/20). 전체로는 질문당 평균 약 0.17초. 건강 답변 전체가 6~8초라 체감은 작고, LLM까지 가는 15% 질문에서만 느껴진다.
- **외부 모델만 쓰면 오히려 나쁘다.** 규칙이 0ms에 정하던 질문까지 0.3초씩 걸리고, 정답도 줄었다. Jev는 앵무새·거북이·뱀·사람 질문 6개를 `none`으로 보냈다(앱은 이런 질문을 건강 경로로 보내 근거 없음으로 보류한다). Decisions는 보고서 질문 3개를 놓쳤다.
- 모두 틀린 2문항(r19 실시간 약국 재고, r20 투약 용량)은 CRAG의 "답할 수 없는 보고서 질문"이라, 이 실험에서 정답을 analysis로 둔 것 자체가 애매하다. 실제 내용은 시설·건강 질문이다.

**고른 것:** "규칙 + Decisions 폴백". 정확도가 같고, 공급자가 OpenAI 하나로 유지되며, 키가 없을 때는 지금처럼 규칙만으로 동작한다. Jev는 다른 회사의 키와 SDK가 하나 더 필요하고, 9/28 측정처럼 같은 질문의 결과가 날짜마다 달랐던 적도 있다.

### 적용: 규칙 + Decisions 폴백, HTTP 직접 호출 (2026-10-09)

- `src/tools/router.py`의 `decide_route()`: 규칙이 못 정한 질문만 `POST /v1/decisions`로 보낸다. 입력은 대화 이력 + 현재 질문, 질문은 경로 4개 중 하나를 고르는 `choice`. Decisions는 openai SDK 3.26 이상에만 있는데 앱은 langchain-openai와 함께 2.53을 쓰므로, SDK를 올리지 않고 `httpx`로 직접 부른다.
- 오류·시간 초과(5초)·판단 거절·경로 밖 값이면 기존 채팅 모델 라우터로 넘어간다. 그래서 Decisions가 막혀도 지금보다 나빠지지 않는다. `ROUTER_FALLBACK=llm`으로 끌 수 있다.
- **같은 평가(136문항, 앱의 `classify_question` 그대로, 2회, 같은 시간대에 기존 방식도 다시 잼):**

| | 정답 | 평균 | p95 | 폴백 20개: 정답 / 평균 / 중앙값 |
| --- | ---: | ---: | ---: | ---: |
| 기존 (규칙 + 채팅 모델) | 134, 134 | 197~213ms | 1.42~1.54초 | 19 / 1.34~1.45초 / 1.34~1.36초 |
| **적용 (규칙 + Decisions HTTP)** | **134, 134** | **53~54ms** | **288~289ms** | **19 / 0.36~0.37초 / 0.27~0.28초** |

- 폴백 40번 중 38번은 Decisions가 정했다. 2번은 r20("독소루비신 투약 용량을 정확히 계산해 주세요")에서 Decisions가 판단을 거절해 채팅 모델로 넘어갔고(1.8초), 결과는 맞았다(`rag`). 거절 → 기존 라우터라는 설계대로다.
- **대화 맥락이 필요한 후속 질문 6개**("그중에 24시간 하는 곳도 있어?", "그럼 고양이는 얼마야?", "고마워요!" 등): 두 방식 모두 6/6, 평균 1.50초 → 0.49초. 프로세스의 첫 호출만 연결을 여느라 1.6초였고 나머지는 0.26~0.28초.
- 비용: 입력 100만 토큰당 $0.10, 출력 무료(교안 README, 10-08 공식 문서 기준). 라우팅 한 번의 입력은 질문과 대화 이력 정도다(비용은 따로 재지 않음).
- 남은 것: Decisions 호출은 LangChain 밖이라 Langfuse trace에 노드로 잡히지 않는다(라우터 노드 시간에는 포함됨).

## 신호 충돌은 LLM에 맡기기 (2026-10-04)

CRAG 평가 60문항에서 오분류 4건이 나왔다. 건강 질문이 "가까운 동물병원에 갈 수 없어서"라는 표현 때문에 병원 검색으로 갔고, 보고서 질문이 "동물병원" 단어 때문에 병원 검색으로 갔다. 원인은 키워드 규칙이 고정된 우선순위(병원 찾기 > 건강 > 병원 > 보고서)로 충돌을 처리했기 때문이다.

**바꾼 규칙**
1. 범위 밖 키워드 → `none`, "보고서" + 보고서 주제 → `analysis` (그대로)
2. **신호가 하나뿐일 때만 규칙으로 결정한다.**
   - 건강 신호만 있고 병원 찾기 표현이 없으면 `rag`
   - 병원 언급만 있으면 `sql`
   - 보고서 주제만 있으면 `analysis`
3. 신호가 충돌하거나 아무 신호도 없으면 LLM 라우터가 판단한다. 프롬프트에 판단 기준 3줄을 추가했다(건강 상황 설명은 병원 언급이 있어도 `rag`, 병원 찾기 요청만 `sql`, 연구·조사의 통계는 `analysis`).
4. 모델이 없으면 예전 우선순위를 그대로 쓴다.

건강 키워드도 평가에서 놓친 표현으로 보강했다(부풀, 삼켰, 흉터, 경련 등). "혹", "토"처럼 짧은 말은 "혹시", "토요일"에서 오탐이 나므로 넣지 않았다.

**결과:** 평가셋 60문항 중 오분류 4건(h08, h09, h13, r14)이 모두 바로잡혔고, 새로 틀린 질문은 없다. LLM 라우터까지 간 질문은 13개다. 경계 사례 9개도 모두 맞았다. 예: "토하는데 근처 동물병원 찾아줘"는 `sql`, "구토하는데 동물병원에 가야 하나요?"는 `rag`.

## 증상 + 병원 찾기: 두 경로를 함께 (day54 Adaptive RAG, 2026-10-09)

**문제:** "설사가 이틀째인데 마포구 동물병원 어디 있어?"는 답이 두 개 필요하다(증상 안내, 병원 목록). 라우터는 경로를 하나만 고른다. 이런 질문 8개를 실제로 돌려 보니 4개는 시설 검색으로 가서 증상 안내가 없었고, 4개는 건강 경로로 가서 **병원 목록이 없었다**.

**바꾼 것:**
- `router.is_symptom_and_place_request()`: 지금 질문에 증상 표현과 장소 요청이 함께 있으면, 라우터가 어느 경로를 골랐든(`rag`·`sql`) 시설 검색 → 건강 경로(CRAG)를 차례로 실행한다. 답은 병원 목록 위, "증상에 대해" 아래로 합친다. 근거가 없으면 건강 쪽은 평소처럼 보류 안내를 하고, 병원 목록은 그대로 남는다.
- 장소 요청은 **요청 동사**(알려, 찾아, 추천, 어디, 목록, 주소, 보여줘, 전화번호)로만 본다. "가까운", "근처"까지 넣으면 평가 질문 136개 중 긴 건강 상담 2개("가까운 동물병원에 방문할 수 없는 상황", "모습을 보여서")가 잘못 걸렸다. 지금 기준으로는 136개 중 0개, 복합 질문 8개 중 8개가 걸린다. 라우팅 키워드는 바꾸지 않았다(라우팅 평가 수치를 그대로 두려고).
- 건강 답변에는 질문의 **증상 부분만** 넘긴다(`router.symptom_part`, 지역·장소 단어 앞에서 자름). 전체 질문을 넘기면 답변 모델이 "검색된 자료에는 마포구 동물병원 정보가 없습니다"처럼 병원 요청까지 건강 자료로 답하려 했다(8개 중 8개). 자르고 나서는 8개 모두 증상만 다뤘다.

**측정 (`scripts/evaluate_compound.py`, 실제 모델, 배포와 같은 CRAG 경로):**

| 복합 질문 8개 | 병원 목록 | 증상 안내 | 시간 p50 |
| --- | ---: | ---: | ---: |
| 이전 | 4/8 | 0/8 | 3.1초 |
| **지금** | **8/8** | **8/8** | 6.8초 |

- 시간은 건강 경로(검색 → 근거 평가 → 답변)가 더해진 만큼 는다. 증상만 묻는 건강 질문과 비슷한 수준이다.
- 고양이 질문("고양이가 구토하는데 부산 동물병원 알려줘")은 병원 목록을 주고, 증상 쪽은 "강아지 자료라 고양이에게 그대로 적용할 수 없다"고 밝혔다.
