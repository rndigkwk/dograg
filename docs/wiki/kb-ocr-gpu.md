# KB 보고서 숫자 다시 읽기: Tesseract 대 EasyOCR 대 비전 모델 — **비전 모델이 가장 정확, 아직 바꾸지 않음** (2026-10-26)

KB 「2025 한국 반려동물 보고서」는 숫자를 유니코드 숫자가 없는 글꼴로 넣어서, PDF 글자로는 숫자가 빠진다. 그래서 보고서 검색은 93쪽을 Tesseract로 읽은 OCR 조각을 함께 쓴다([retrieval-experiments.md](retrieval-experiments.md) "KB 보고서의 사라진 숫자를 OCR로 되살리기").

Tesseract는 숫자를 한 자리씩 잘못 읽는다(7쪽·28쪽의 39.2%를 "59.2%", 14쪽의 585만을 "589만"). 지금까지 손으로 찾은 9곳은 정정표(`scripts/add_kb_ocr_chunks.py`의 `OCR_CORRECTIONS`)로 고쳤지만, 나머지 쪽에도 오독이 남아 있을 수 있다. 같은 쪽을 GPU OCR(EasyOCR)과 비전 언어 모델로 다시 읽어 비교했다.

- **노트북:** `notebooks/kb_ocr_gpu_colab.ipynb` (`scripts/build_kb_ocr_gpu_notebook.py`로 생성), Colab **L4**, 200 dpi
- **기록:** MLflow(DagsHub) 실험 `kb-report-ocr`, 실행 `gpu-ocr-vs-tesseract`(점수만)
- **쪽 글:** 비공개 Hugging Face 데이터셋 `blanden77/dograg-kb-ocr-gpu`의 `kb_ocr_gpu_texts.json`(엔진별 93쪽). 보고서 원문이라 공개 저장소에 두지 않는다
- **OpenAI 호출 0번**

## 비교한 것

| 엔진 | 내용 |
| --- | --- |
| `tesseract` | 지금 검색이 쓰는 OCR(kor+eng, 300 dpi, CPU, 2026-10-17), 읽은 그대로 |
| `tesseract_rules` | 위에 앱의 일반 규칙(연도의 "년", %p, 빠진 소수점)을 적용, 손 정정 9곳은 빼고. 앱이 정정표 없이 갖는 상태 |
| `easyocr` | EasyOCR 한국어+영어, GPU, 문단으로 묶음 |
| `vlm` | **Qwen3-VL-4B-Instruct**, "보이는 글자와 숫자를 빠짐없이 그대로 옮겨 적으라", 온도 0, 출력 상한 3,000토큰 |

정답이 모든 숫자에 있지는 않아서 네 가지로 쟀다.

1. **알려진 오독 9곳:** 맞는 숫자를 읽었나, 틀린 숫자를 읽었나
2. **기준 답변의 숫자:** 보고서 기준 답(`tests/data/report_reference_answers.json`)의 숫자가 KB 정답 쪽에서 나오나(38개)
3. **체계적 오독:** 연도의 "년"을 숫자로 읽음, 101~999% 같은 있을 수 없는 비율
4. **다른 엔진이 읽지 않은 숫자:** 비전 모델이면 지어냈을 가능성

## 결과 (93쪽)

| 엔진 | 오독 9곳: 맞게 / 틀리게 | 기준 답 숫자 | 연도 오독 | 있을 수 없는 비율 | 읽은 숫자 | 쪽당 시간 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Tesseract | 0 / 8 | 24/38 | 29 | 15 | 996 | (CPU, 10-17) |
| Tesseract + 규칙 | 0 / 9 | 26/38 | 0 | 0 | 992 | |
| EasyOCR | 3 / 0 | 12/38 | 0 | 3 | 503 | 2.6초 |
| **비전 모델 (4B)** | **9 / 0** | **27/38** | 0 | 0 | 1,151 | 59.5초 |

- **알려진 오독:** 비전 모델은 9곳을 모두 맞게 읽고 틀린 값은 하나도 내지 않았다. Tesseract는 규칙을 적용해도 9곳 모두 틀린 값 그대로다. 규칙으로 고칠 수 없는 오독이라 정정표가 필요했던 것과 맞는다.
- **기준 답 숫자:** 비전 모델이 찾은 27개는 Tesseract+규칙의 26개를 모두 포함하고, 하나(h08의 39.2%)가 더 있다. 어느 엔진도 찾지 못한 11개(h01·h02·h03·r04)는 정답 쪽에 그 표기로 없는 숫자로 보인다(쪽 그림과 대조하지는 않았다).
- **EasyOCR:** 숫자를 절반만 읽었다(503개). 문단으로 묶으면서 그래프 라벨이 빠진 것으로 보인다. 후보에서 뺀다.

### 엔진끼리 숫자가 갈리는 쪽

EasyOCR과 비전 모델이 같은 숫자를 읽었는데 Tesseract가 다르게 읽은 쪽이 **50쪽**이다. 비전 모델만 읽은 숫자(다른 엔진과 PDF 글자 어디에도 없는 것) 134개 중 **64개는 Tesseract가 한 자리만 다르게 읽은 숫자**였다. 갈리는 모양은 정정표의 오독과 같았다. 3을 5로 읽거나(30.2% ↔ "50.2%", 35.1% ↔ "55.1%", 37.4% ↔ "57.4%"), 3을 8로 읽었다(62.6% ↔ "82.6%").

**쪽 그림과 대조 (17쪽):** 비전 모델만 읽은 숫자 6개 중 5개가 그림과 맞았다(63.9%, 30.2%, 27.3%, 10.8%p, 51.4%. Tesseract는 65.9%, 50.2%, 27.5% 등). 1개(52.3%)는 그 쪽에 없는 숫자였다. 한 쪽만 본 것이라 비율로 일반화하지 않는다. 다만 Tesseract 조각에 정정표에 없는 오독이 더 남아 있다는 것은 분명하다.

### 비전 모델의 실패: 되풀이

5쪽(13·16·40·55·96쪽)에서 같은 문장을 되풀이하다 출력 상한에 닿았다. 쪽당 약 165초가 걸렸고, 글자는 2,700~4,100자였다. 나머지 쪽은 중앙값 1,220자로 Tesseract(1,092자)와 비슷했다. 되풀이한 쪽에서는 쪽 뒷부분의 숫자를 잃는다.

### 8B 모델을 쓰지 못한 이유

노트북은 GPU 메모리가 모델이 필요한 양의 1/0.95보다 커야 그 모델을 시도한다. L4가 보고하는 메모리(약 22.5GiB)로는 8B·7B(필요 22GB로 잡음)가 이 기준에 걸려 건너뛰었고, 4B를 썼다. 기준이 너무 보수적이었다. bf16 8B는 L4에 들어갈 수 있다.

## 결론

**비전 모델이 숫자를 가장 정확히 읽는다. 하지만 검색 조각은 아직 바꾸지 않는다.**

- 알려진 오독 9/9, 기준 답 숫자 27/38(+1), 연도·비율 오독 0. Tesseract의 체계적 오독(3 → 5)이 정정표 밖에도 수십 곳 남아 있을 가능성이 크다.
- 바꾸지 않은 이유:
  - **되풀이하는 쪽이 5쪽 있다.** 그 쪽은 뒷부분 숫자를 잃는다.
  - **비전 모델만 읽은 숫자 중 틀린 것도 있다**(17쪽 52.3%). 지금 정정표 9곳은 쪽 그림과 하나씩 대조한 값이라, 확인되지 않은 OCR로 덮으면 안 된다.
  - **검색과 답 평가를 다시 재야 한다.** 조각 글이 바뀌면 BM25와 임베딩이 바뀐다. 보고서 18문항 × 2회(답 36번 + 판정 36번, 약 72번 호출)로 정답 쪽 적중과 답 정확도가 지금(35/36)보다 나빠지지 않는지 확인해야 한다.

## 다음에 할 것

1. 되풀이 막기: `repetition_penalty`, 쪽을 위·아래로 나눠 읽기, 또는 되풀이를 감지하면 그 쪽은 Tesseract를 그대로 쓴다.
2. 메모리 기준을 고쳐 8B로 다시 읽는다(L4 또는 A100).
3. 비전 모델과 Tesseract가 갈리는 숫자는 쪽 그림과 대조해, 확인된 것만 정정표에 더한다. 지금 정정표 방식 그대로이고, 검색 조각 전체를 바꾸지 않는다.
4. OCR 조각을 비전 모델 글로 바꾸는 안은 1~3 뒤에 보고서 평가(약 72번 호출)로 정한다. 바꾸면 비공개 데이터셋에 새 리비전(`data-v12`)으로 올린다.
