# 교안 적용 정리 (Day 02~77, 2026-11-09 Day 77 추가)

엔코아 AI 캠퍼스 교안(`class_1`의 다섯 실습 폴더, `openai-decisions-examples`, `enkoa-practice-deep-learning`)을 Day 순서로 놓고, 각 Day의 내용을 이 프로젝트에 어떻게 썼는지 정리한다. 처음 판(2026-10-09, Day 46~56)과 재검토(2026-10-16), Day 65~69 추가(2026-10-28), Day 71~75 추가(2026-11-05), Day 76 추가(2026-11-06), Day 77 추가(2026-11-09)를 한 문서로 합쳤다.

- ✅ **적용**: 앱이나 평가·운영 도구에 들어가 있다. 어떻게 넣었고 무엇이 좋아졌는지.
- 🧪 **테스트 후 미적용**: 같은 평가 세트로 재 보고 넣지 않았다. 결과와 이유.
- ➖ **적용 안 함**: 재지 않았다. 맞지 않는 이유.
- 🔜 **할 일**: 해 볼 만하고 아직 하지 않았다. 문서 끝 "할 일"에 모았다.

수치는 모두 같은 평가 세트의 전후 비교다. 자세한 기록은 링크한 문서에 있다.

**교안 폴더에 없는 Day:** 01, 24~26, 43~45. 이 문서에서 다루지 않는다.

**판단의 배경이 바뀐 시점 (2026-10-16):** Day 46~56을 처음 검토한 10-09에는 메모리 약 1GB(Streamlit Cloud)와 "서버에 대화 내용을 남기지 않는다"는 두 제약이 있었다. ADR-0007·0008로 앱이 Cloud Run(2GiB)으로 옮겨 가고 Supabase 저장소와 로그인(RLS로 본인 행만)이 생겼다. 그 두 제약을 이유로 보류했던 항목은 해당 Day 표에 "재검토" 결과를 적었다. ## 지식 그래프 (enkoa-practice-knowledge-graph)

Day 27~42는 Neo4j로 지식 그래프를 만들고 검색하는 단원이다. 이 프로젝트의 자료(건강 Q&A, 보고서, 시설 목록)에는 "증상 → 질병 → 약" 같은 관계 데이터가 없다. 관계를 모델로 뽑으면 그 정확도부터 검증해야 하고, 그래프 DB 하나가 운영에 더 생긴다. 그래서 그래프 자체는 쓰지 않는다(Day 49와 같은 판단). 아래 표는 그래프가 아니어도 같은 생각을 쓴 곳만 ✅로 적었다.

## 딥러닝 (enkoa-practice-deep-learning/내작업)

이 프로젝트는 답변을 API 모델로, 임베딩을 CPU ONNX로 만든다. 그래서 신경망을 직접 짜고 학습하는 내용은 대부분 맞지 않는다. 쓸 만한 것은 **학습 데이터를 다루는 방법**(Day 69)과 **학습 기록·모델 고르기**(Day 66)다.

### Day 70 · SFT(지도 미세조정), 에폭별 체크포인트, 퇴행 점검

교안은 TRL `SFTTrainer`로 작은 답변 모델을 학습하고, 기본 모델과 학습한 모델을 같은 질문으로 비교한다. 결론은 "말투·형식·거절은 SFT로 배우고, 사실은 RAG로 넣는다"이다. 이 프로젝트는 답변을 API 모델로 만들어서 학습 자체는 맞지 않는다. 대신 **고르는 방법과 퇴행 점검**은 임베딩 학습에 그대로 쓸 수 있다.

| 교안 내용 | 상태 | 어떻게 / 결과 / 이유 |
| --- | --- | --- |
| `SFTTrainer`로 답변 모델 학습(prompt/completion 분리, 질문 부분은 손실에서 뺌, `<\|im_end\|>`까지 학습) | ➖ | 학습할 답변 모델이 없다. 사실은 RAG가 넣고, 말투·형식·보류는 시스템 프롬프트와 CRAG가 맡는다. GPU 서버를 계속 둘 수 없는 이유는 [curriculum-fit.md](../curriculum-fit.md)에 있다 |
| `max_length`가 가장 긴 예시보다 짧은지 확인 | ✅ | 임베딩에서 같은 확인을 했다. 128토큰에서 상담 글의 52%가 잘리고, 잘림을 풀어도 나아지지 않았다([embedding-finetune.md](embedding-finetune.md) "문서 길이와 청킹") |
| 학습률 비교(2e-5 vs 5e-6), 에폭마다 체크포인트, `report_to`로 MLflow 기록 | ✅ | 2026-11-02 재학습에서 했다. 시드 3개 × 3 epoch, 에폭마다 체크포인트 9개를 MLflow(DagsHub)에 시드별 하위 실행으로 남겼다. 학습률 비교는 하지 않았다(Day 74 표 참고) |
| 검증 손실은 기록이고, 고르는 기준이 아니다 | ✅ | 개발용 600 질의의 점수는 학습 질의와 같은 방식이라 낙관적이다. 바꿀지는 220문항 `useful@3`와 McNemar 검정으로 정했다 |
| 결과를 보기 전에 고르는 규칙을 적는다 | ✅ | KURE-v1과 bge-m3는 "바꿀 조건"(앱보다 유의하게 높을 것, p<0.05)을 먼저 적고 쟀다. 둘 다 못 채워 앱 모델을 유지했다 |
| 외운 문제와 응용 문제를 나눠 본다 | ✅ | 평가 질문의 복사본으로 나눴다(Day 69). 긴 상담 100문항 중 복사본이 있는 13문항은 모두 맞고, 없는 87문항은 0.678이다 |
| 거절률과 과잉 거절률 | ✅ | CRAG 60문항으로 잰다. 근거 없는 질문 보류 16/20, 답할 질문을 잘못 보류 1/38이다 |
| 일반 능력 퇴행(시스템 프롬프트 없는 질문, perplexity) | ✅ | 답변 모델은 학습하지 않는다. 임베딩은 학습 목표(짧은 질문)가 아닌 긴 상담 글로 퇴행을 봤다. 0.72 → 0.84로 나빠지지 않았다 |
| WiSE-FT: 기본과 학습 가중치를 섞기(α 0.5 / 0.75) | ➖ | 학습 없이 기본 ko-sroberta와 B를 섞을 수 있다. 하지만 섞는 목적은 잃은 일반 능력을 되찾는 것이고, B는 긴 상담 글에서도 나빠지지 않아 되찾을 것이 없다. 다음 학습에서 퇴행이 보이면 다시 본다 |
| Replay: 일반 데이터를 섞어 학습 | ➖ | 답변 모델 SFT가 없다. 임베딩 학습 데이터는 이미 상담 18,906건 전체에서 고루 만들었다 |
| 결정표와 다시 볼 조건 | ✅ | ADR과 위키의 "다시 볼 조건" 줄이 같은 일을 한다 |

### Day 71 · PEFT, LoRA, 어댑터 관리, DoRA

교안은 답변 LLM(0.8B)에 LoRA 어댑터를 붙여 노무 상담을 SFT하고, 에폭별 어댑터를 얹어 고른 뒤 병합한다. 이 프로젝트에는 학습하는 답변 모델이 없고, 학습하는 임베딩은 110M이라 풀 파인튜닝이 2~5분이다.

| 교안 내용 | 상태 | 어떻게 / 결과 / 이유 |
| --- | --- | --- |
| LoRA(`r`, `lora_alpha`, `target_modules`), `SFTTrainer`로 어댑터만 학습 | ➖ | 답변 모델을 학습하지 않는다(Day 70). 임베딩은 GPU 메모리가 모자라지 않아 전체를 학습한다. 교안의 "언제 LoRA를 쓰나"(메모리가 적거나 분야가 여럿) 어느 쪽도 아니다 |
| 에폭별 어댑터를 얹어 같은 지표로 고르기(`load_adapter`, `set_adapter`) | ✅ | 같은 일을 체크포인트 폴더로 했다. 2026-11-02 재학습의 9개 체크포인트를 모델 저장소 `ko-sroberta-dograg-b2`에 폴더별로 두고, 평가 스크립트가 이름으로 골라 받는다(`--retrain s13-e3`) |

### Day 74 · 도메인 임베딩 파인튜닝, Hard Negative 마이닝

이 프로젝트에서 실제로 하는 학습과 가장 가깝다. 교안의 순서(쌍 데이터 → MNR → 에폭 고르기 → hard negative → 일반화·퇴행 점검)를 앱 모델 B(2026-10-09), hn(10-21), 재학습 b2(11-02), GIST(11-05)에서 모두 거쳤다.

| 교안 내용 | 상태 | 어떻게 / 결과 / 이유 |
| --- | --- | --- |
| 기존 질문·정답 문서로 쌍 데이터, 평가 질의는 학습에 넣지 않음 | ✅ | 상담마다 합성 질의 2개(짧은·자세한)로 쌍을 만들었다. 손으로 쓴 220문항은 학습에 없다. 다만 AI Hub가 같은 상담을 말만 바꿔 두 번 실어서, 긴 상담 13문항의 복사본 53개를 11-02 재학습에서 뺐다 |
| 질의·문서 프리픽스 | ➖ | ko-sroberta는 프리픽스 없이 학습된 모델이다. 프리픽스를 쓰는 e5-small은 비교할 때 `query: ` / `passage: `를 붙였다 |
| MNR 손실, 배치 안 오답, `NO_DUPLICATES` | ✅ | 세 번 모두 MNR이다. 배치 64라 질의마다 오답 63개다. 같은 상담의 질의 둘이 한 배치에 들어가지 않게 `NO_DUPLICATES`를 쓴다 |
| `NO_DUPLICATES`는 같은 문자열만 막는다, 같은 답인 다른 문서(거짓 오답)는 따로 검토 | 🧪 | 우리 데이터의 핵심 문제다. 같은 증상의 상담이 많아 배치 안이나 마이닝한 오답이 사실상 정답일 수 있다. hn 실험이 짧은 질문에서 B보다 낮았던 이유로 이것을 짐작했다. 11-05에 `GISTEmbedLoss`(안내 모델 B가 정답만큼 가까운 배치 안 오답을 가림)로 확인했다. 데이터·설정을 b2와 같게 두고 가림만 더하자 짧은 질문 holdout 80개가 0.850으로 B(0.762)보다 높았다. 다만 p=0.065로 기준을 넘지 못했고 긴 상담은 0.82(B 0.85)라 B를 유지했다. 시드 21·34로 다시 본다([embedding-finetune.md](embedding-finetune.md) "GISTEmbedLoss") |
| 최대 5에폭, 검증 Recall@5로 고르고, 일반 질의는 고르기에 쓰지 않음 | ✅ / 🧪 | 11-02 재학습: 3 epoch × 시드 3개, dev 300 상담의 합성 질의 `mrr@10`으로 `s13-e3`을 골랐고 220문항은 고른 하나만 쟀다. 결과는 긴 상담 0.85로 B와 같고 짧은 질문 0.742로 B(0.800)보다 낮아 B를 유지했다. dev가 학습 질의와 같은 생성기의 합성 질의라 에폭을 늘릴수록 dev만 오른 것으로 본다([embedding-finetune.md](embedding-finetune.md) "복사본을 빼고 다시 학습"). 그래서 11-05 GIST부터는 사람이 쓴 짧은 질문 dev 40개로 에폭을 고르고 holdout 80개로만 보고한다(`evaluate_finetuned_embedding.py --short-split`) |
| `mine_hard_negatives`, `relative_margin=0.05`, 정답은 후보에서 제외 | 🧪 | 10-21 hn 실험에서 같은 설정을 썼다(10~50위, 5% 상대 마진, 캐는 모델은 B). 긴 상담 0.87(B 0.85)이지만 짧은 질문 0.742로 B보다 낮아 채택하지 않았다 |
| Triplet 데이터에 **손실은 MNR 그대로**(TripletLoss로 바꾸지 않음) | ✅ | hn 실험이 정확히 이 형태다. (질의, 정답, 오답) 세 칸을 MNR에 넣어, 캐낸 오답이 배치의 다른 질의에게도 후보가 된다. TripletLoss는 질의마다 오답 하나와의 margin만 보므로, 거짓 오답이 섞인 우리 데이터에서는 그 하나에 학습이 더 쏠린다. 따로 실험하지 않는다 |
| 평가 질의를 "학습에 나온 정답"과 "처음 보는 정답"으로 나눠 보기 | ✅ | 과적합 점검에서 긴 상담 100문항을 복사본이 있는 13과 없는 87로 나눴다. 오른 점수는 전부 없는 87에서 나왔다. 학습한 상담을 위로 올리는지도 dev 상담 비율로 봤다([embedding-finetune.md](embedding-finetune.md) "과적합 점검") |
| 다른 분야 검색의 퇴행 점검(일반 83질의) | ✅ | 다른 분야 검색이 없어, 학습 목표(짧은 질문)가 아닌 긴 상담 글 561·100문항을 퇴행 점검으로 쓴다. B와 재학습 모두 나빠지지 않았다 |
| 부록 · 공개 임베딩 모델과 비교 | ✅ | multilingual-e5-small, KURE-v1, bge-m3를 같은 220문항으로 쟀다. 앱 모델보다 유의하게 나은 것이 없었다 |
| 부록 · 허브에 임베딩 모델과 데이터셋 올리기 | ✅ / 🔜 | Day 71 부록과 같다 |

### Day 76 · 서빙 성능 지표와 벤치마킹, 추론 가속(접두어 캐싱·동시 실행 상한·투기적 디코딩)

교안은 RunPod에서 vLLM 상담 서버를 띄워 `vllm bench serve`로 동시 요청 1·16·64를 재고, `vllm bench sweep serve`로 서버 설정(기준, MTP)을 비교한다. 이 프로젝트는 답변 모델을 직접 서빙하지 않으므로(Day 75), 서버 옵션은 해당이 없다. 지표와 고르는 방법은 배포 API에 그대로 쓸 수 있다.

| 교안 내용 | 상태 | 어떻게 / 결과 / 이유 |
| --- | --- | --- |
| TTFT·TPOT·ITL·요청 지연을 스트리밍 응답의 도착 시각으로 계산 | ✅ | `scripts/measure_latency_by_feature.py`가 배포 API(`/chat` SSE)에서 첫 단계·근거·첫 글자·끝 시각을 잰다. 첫 글자가 TTFT, 끝이 요청 지연에 해당한다. 건강 상담은 첫 글자 6.1초, 끝 7.1초였다(10-25, [deployment-resources.md](deployment-resources.md) "기능별 응답 시간"). TPOT·ITL은 재지 않는다. 본문 출력은 약 0.5초뿐이고, 기다리는 시간 대부분은 첫 글자 전(검색, 근거 평가, 답변 모델의 추론)이다 |
| 평균 대신 백분위(p95·p99)로 지연 목표 정하기 | ✅ | [SLO](../slo.md)가 p95로 정한다(건강 상담 ≤ 25초, 보고서 ≤ 45초). 매주 최근 7일 기록으로 확인한다. 교안의 "표본이 작으면 한 요청이 백분위를 정한다"와 같은 이유로, 7일에 20문항이 안 되면 판정하지 않는다 |
| goodput과 목표 달성률(지연 목표를 모두 지킨 요청의 비율) | ✅ | 2026-11-06(#404)부터 주간 SLO 보고(`scripts/slo_report.py`)가 보인다. 건강 상담 답 중 25초 안 비율, 보고서 답 중 45초 안 비율이다. 목표가 하나라서 "95% 이상"은 p95 판정과 같으므로 판정 없이 지켜본다. 최근 28일은 건강 67개, 보고서 35개 모두 100%였다 |
| 동시 요청 수 고르기: 목표 달성률 0.95 이상 가운데 출력 처리량이 가장 큰 값 | ✅ | 2026-11-06에 쟀다([deployment-resources.md](deployment-resources.md) "동시 요청과 프롬프트 캐시"). 재기 전에 기준을 "검색 단계 p95 ≤ 2초 중 가장 큰 동시 수"로 정했다. CPU 1개에서 동시 검색 4는 p95 0.23~0.41초였고, 16은 4번 중 3번이 2초를 넘었다(초당 검색도 줄었다). 채팅 하나는 약 7초 가운데 검색에 0.1~0.2초만 쓴다. 그래서 같은 순간 검색 4개를 넘기려면 채팅 수십 개가 겹쳐야 하고, 넘어도 +2.5초로 SLO 안이다. `--concurrency`는 기본값(80)으로 둔다. 낮추면 새 인스턴스의 시작(약 23초)을 기다리게 된다. 모델을 쓰지 않는 조회 API는 동시 16에서도 p95 0.2초 안이었다 |
| 100만 토큰당 비용 = 시간당 요금 ÷ (출력 처리량 × 3600) × 10⁶, API와 비교할 때는 입력 토큰 금액까지 출력 토큰 수로 나누기 | ➖ | GPU를 빌려 서빙하지 않는다. 비용은 SLO의 질문당 모델 비용으로 본다(≤ $0.01, 10-19 측정 $0.0005). 교안의 식은 GPU가 한 시간 내내 일한다고 가정한다. 이 앱은 질문이 드물어 GPU가 대부분 쉬므로, 서버를 켜 둔 시간만큼 요금이 고정으로 든다(교안 "GPU가 쉬는 시간"). Day 75의 ➖와 같은 결론이다 |
| 접두어 캐싱: 공통 부분을 앞에, 다른 부분을 뒤에(블록 단위로 다시 씀) | ✅ | #276에서 OpenAI 프롬프트 캐시로 같은 방법을 시험했다. 고정 규칙을 시스템 메시지 앞에 두고 `prompt_cache_key`도 붙였는데, 근거와 질문이 다르면 캐시에서 읽은 토큰이 0이었다. 2026-11-06에 지금 프롬프트로 다시 쟀다(모델 호출 14번). 첫 변수 앞의 고정 부분이 1,674토큰으로 OpenAI 최소 길이 1,024토큰보다 긴데도, 질문이 다른 12번은 키가 있든 없든 모두 0이었다. 같은 프롬프트를 다시 보내면 2,466/2,469토큰을 읽었다. 이 모델은 프롬프트 전체가 같을 때만 캐시를 쓰므로 바꾸지 않는다([deployment-resources.md](deployment-resources.md) "동시 요청과 프롬프트 캐시") |

### Day 77 · FastAPI 모델 서빙 API: 라우팅·스키마·스트리밍 중계, 서비스 키·요청 한도·오류 양식, 키 관리와 사용량 기록

교안은 RunPod의 vLLM 앞에 FastAPI 상담 API(`serving_app`)를 세운다. 라우터·스키마·백엔드 계층으로 나누고, SSE를 중계하며, `X-API-Key` 서비스 키와 60초 요청 한도, 한 양식의 오류 응답(401·422·429·502·504)을 붙인다. 이어 SQLite에 키 해시와 토큰 사용량을 저장한다. 이 프로젝트의 API(`api/`, Cloud Run)도 FastAPI이고 대부분 이미 같은 방식이다. 다른 점은 둘이다. 부르는 쪽이 공개 웹 화면 하나뿐이라 서비스 키를 나눠 줄 상대가 없고, 답변 모델이 vLLM이 아니라 OpenAI·Claude API다.

| 교안 내용 | 상태 | 어떻게 / 결과 / 이유 |
| --- | --- | --- |
| 앱을 기능별 `APIRouter`로 나누고 `include_router`로 붙이기, 상태 확인 주소(`/healthz`) | ✅ | `api/main.py`가 chat·feedback·fees·memory·places·stats·visit_prep 라우터 7개를 붙인다. `/health`는 키 없이 열려 있고 배포 커밋을 돌려준다. 배포 카나리(`scripts/canary_check.py`)가 이 값으로 새 리비전을 확인한다([cloud-run.md](cloud-run.md)) |
| pydantic 요청 양식과 입력 제약(길이·범위·패턴), 틀리면 422 | ✅ | `api/chat.py`의 `ChatRequest`가 질문 길이(`MAX_QUESTION_CHARS`), 이전 대화 길이, 날짜 패턴(`^\d{4}-\d{2}-\d{2}$`)을 검사한다. 질문 하나가 모델 비용이 되므로 길이 상한이 곧 비용 상한이다 |
| `response_model`로 응답에서 내부 항목 빼기 | ➖ | 같은 목적을 손으로 한다. `/chat`은 SSE라 교안 말대로 `response_model`을 쓸 수 없다. 그래서 이벤트마다 보낼 항목을 직접 고른다. 예: 그래프의 `trace`(평가용 단계 기록)는 실행 결과에는 있지만 보내지 않는다(#414). JSON 주소(fees·places·stats)는 작은 사전이라 바꿀 이득이 없다 |
| CORS: 웹 화면의 출처만 허용 | ✅ | `RAGDOG_WEB_ORIGINS`에 적은 출처만 허용한다. 없으면 로컬 웹 하나다. 허용 헤더는 `Authorization`·`Content-Type`·`X-RagDog-Client`다. 로그인 토큰은 쿠키가 아니라 헤더로 보내므로 `allow_credentials=False`다 |
| 자동 문서(`/docs`) | ✅ | 로컬에서는 켜고, 배포에서는 끈다(`RAGDOG_API_DOCS=1`일 때만 켬). 모든 주소와 양식을 공개 인터넷에 보일 이유가 없다([security/threat-model.md](../security/threat-model.md)) |
| `def`와 `async def`: 동기 코드는 `def`(스레드 풀)로, `async def` 안에서는 막는 호출 금지 | ✅ | 엔드포인트는 모두 `def`다. 검색(FAISS·Supabase)·LangChain·httpx 호출이 동기라서다. `async def`는 `lifespan` 하나뿐이고, 그 안에서는 막는 일이 없다. `/chat`은 동기 제너레이터를 `StreamingResponse`에 넘기고, Starlette가 이를 스레드 풀에서 읽는다. 교안의 "async 안의 `time.sleep`이 이벤트 루프를 멈춤" 같은 실수는 없다 |
| `lifespan`: 시작 때 준비, 종료 때 정리 | ✅ | 배포에서는 시작 때 `warm_up()`이 임베딩 모델과 검색 자료를 미리 올린다. 그래서 첫 질문이 모델 적재를 기다리지 않는다. 다만 첫 `/places/kinds`가 두 번째 인스턴스를 기다리는 일은 남아 있다(#384, 카나리에서 해결, [cloud-run.md](cloud-run.md)) |
| 모델 응답을 SSE로 중계, 조각 도착 시각과 TTFT | ✅ | `/chat`·`/visit-prep`이 `text/event-stream`으로 step·evidence·token·result 이벤트를 보낸다. 작업 스레드가 큐에 넣고 제너레이터가 꺼내 보낸다. TTFT는 Day 76의 `scripts/measure_latency_by_feature.py`로 잰다. 요청이 끝나면 `request_log.summarized`가 경로·지연·오류를 JSON 로그 한 줄로 남긴다 |
| 클라이언트를 하나 만들어 연결풀 재사용(요청마다 만들지 않기) | 🧪 | 답변 모델(LangChain `ChatOpenAI`, `src/resources.py`)은 캐시한 하나를 같이 쓴다. Decisions 호출(경로 분류 `src/tools/router.py`, 응급 판정 `src/tools/urgency.py`)은 부를 때마다 `httpx.post`로 새 연결을 연다. 2026-11-09에 공유 `httpx.Client` 하나로 바꿔 쟀다(로컬, 경로 분류 20번씩, 브랜치 `perf/decisions-shared-client`). 재기 전 기준은 p50 0.1초 이상 감소였다. 결과는 p50 0.318 → 0.325초, 첫 호출을 뺀 p50 0.318 → 0.311초로 차이가 없었다. 달라 보인 것은 프로세스의 첫 호출 하나뿐이다(1.48 → 0.55초). 한 번씩 잰 값이라 주소 조회와 첫 TLS 준비 같은 잡음과 구별되지 않는다. 바꿔도 인스턴스마다 첫 질문 하나에만 해당한다. Decisions 호출 시간의 대부분은 연결이 아니라 모델의 판단이다. 넣지 않았다 |
| 백엔드 클라이언트 `max_retries=0`, 다시 시도는 서빙 API가 정함 | ✅ | 모델 호출마다 시간 제한이 있다(`CHAT_TIMEOUT_SECONDS` 등, 10-23). OpenAI가 실패하면 Claude로 넘기고(ADR-0012), 한동안 OpenAI를 건너뛴다(차단기). Decisions 호출은 실패하면 다시 시도하지 않고 규칙의 답을 쓴다. 다시 시도할지를 API 쪽이 정한다는 교안 원칙과 같다 |
| 서비스 키(`X-API-Key`)와 `Depends` 의존성으로 주소 보호 | ➖ | 부르는 쪽이 공개 웹 화면뿐이다. 브라우저에 넣은 키는 누구나 볼 수 있으니 서비스 키는 막는 효과가 없다. 대신 둘을 쓴다. ① 사람(브라우저 id)·네트워크별 요청 한도. ② 평가용 비밀 헤더 `X-RagDog-Check`(`RAGDOG_CHECK_TOKEN`, `hmac.compare_digest`로 비교). 이 헤더는 한도를 건너뛰는 용도로만 쓴다. 저장(기억·방문 보고서)은 Supabase 로그인 토큰과 RLS로 본인 행만 다룬다([security/least-privilege.md](../security/least-privilege.md)) |
| 요청 한도: 시간 창, 429와 `Retry-After` | ✅ | `src/rate_limit.py`. 사람당 1시간 10개·하루 30개, 네트워크당 60개·200개다. 교안은 서버 메모리에 두는데, 여기서는 Supabase 표에 소금 친 해시와 시각만 둔다. 그래서 인스턴스와 재시작이 같은 수를 센다. DB가 실패하면 메모리로 센다. `/chat`은 429 대신 SSE `limited` 이벤트로 "약 N분 뒤"(`wait_minutes`)를 보낸다. 화면이 스트림 하나만 읽게 하려는 것이다. JSON 주소(feedback·memory)는 `HTTPException(429)`이다. `Retry-After` 헤더는 읽을 프로그램 클라이언트가 없어 넣지 않았다 |
| 오류 응답을 한 양식으로(`exception_handler`), 상태 코드별 오류 이름 | ➖ | JSON 주소는 FastAPI 기본 `{"detail": ...}`에 한국어 문장을 담는다. SSE는 `error`·`limited` 이벤트로 알린다. 읽는 쪽이 이 웹 화면 하나이고 두 형식을 이미 다룬다(`web/src/lib/chat.ts`). 외부 클라이언트가 생기면 그때 맞춘다 |
| 모델 서버가 응답하지 않을 때 502·504로 구분 | ✅ | `src/model_outage.py`. 한도 소진(quota)과 응답 없음·연결 불가(unavailable)를 나누어 다른 안내를 보낸다. 상태 코드 대신 이렇게 한 이유: 모델 없이도 검색은 되므로 가까운 상담·가이드를 그대로 보여 주는 편이 사용자에게 낫다. 응급 판정은 이때도 규칙으로 한다 |
| 키 원문 대신 해시 저장 | ✅ | 같은 생각을 요청 한도에 쓴다. 브라우저 id와 IP를 그대로 두지 않고, 소금 친 SHA-256 앞 32자로 둔다(`rate_limit._hash`). 소금은 DB 주소에서 만들거나 프로세스마다 새로 만든다. 오래된 행은 지운다(`KEEP_HOURS`) |
| 관리자 키로 키 발급(201)·폐기(행을 지우지 않음) | ➖ | 나눠 줄 서비스 키가 없다. 비밀 값(체크 토큰, 모델 키)은 Secret Manager에 두고, 바꿀 때는 새 버전을 넣는다([cloud-run.md](cloud-run.md)) |
| 요청마다 토큰 사용량 기록과 사용량 조회 | ✅ | 키별이 아니라 질문별이다. 모델 호출은 Langfuse에 비용과 함께 남는다. `scripts/slo_report.py`가 매주 질문당 비용을 계산한다(목표 ≤ $0.01, [SLO](../slo.md)). 31일 291개에 $0.062였다(11-07, #385). 로컬 실행은 `src/run_log.py`가 입력·출력 토큰을 적는다 |
