# 건강 검색 임베딩 미세조정 (2026-10-09)

`jhgan/ko-sroberta-multitask`를 "보호자가 채팅창에 치는 짧은 질문 → 긴 상담 글"에 맞게 미세조정했다. 짧은 질문에서 쓸모 있는 근거가 상위 3건에 드는 비율이 0.625 → 0.800(p=0.0002)이 됐고, 긴 상담 글에서도 나빠지지 않았다(0.74 → 0.85, p=0.027). 학습은 Colab 무료 T4에서 4.6분, 데이터 비용은 $3.37이었다.

> 2026-10-10 앱에 적용했다(아래 6). 앱 경로에서도 짧은 질문 0.600 → 0.783(p=0.0001), 긴 상담 글 0.72 → 0.84(p=0.023).

## 1. 왜 했나

- **문제:** 건강 검색은 Dense(ko-sroberta) + BM25 하이브리드다. 검색 대상은 AI Hub 보호자 상담 19,206개(중앙값 257자)인데, 앱 사용자는 "강아지가 이틀째 설사해요"처럼 **짧게** 묻는다. 기준 모델은 이런 "짧은 구어체 → 긴 상담 글" 짝을 학습한 적이 없다.
- **확인한 근거:** 상담 100개로 보호자 말투 질의를 만들어, 지금 검색이 원래 상담을 몇 위에 찾는지 쟀다(시범, 아래 2-1).

  | 원래 상담을 상위 10위 안에 찾음 | 짧은 질의(중앙값 23자) | 긴 질의(58자) |
  | --- | ---: | ---: |
  | Dense만 | 15% | 34% |
  | 앱 하이브리드 | 22% | 47% |

- **포트폴리오 이유:** 지금까지는 기존 모델·API를 조합만 했다. 데이터를 만들고, 학습하고, 오프라인 지표로 검증하는 ML 엔지니어 기본 과정을 이 프로젝트 안에서 한 번 해 보기로 했다.

## 2. 어떻게 했나

### 2-1. 학습 데이터: 합성 질의 (`scripts/finetune_queries.py`)

- 상담 글마다 채팅 모델(`gpt-6-luna`, 추론 low)이 보호자가 칠 법한 질문 2개를 쓴다.
  - `short`: 15~40자, 핵심 증상 하나
  - `detailed`: 40~100자, 증상에 나이·기간·상황 하나를 더함
  - 지시: 문장을 베끼지 말 것, 보호자가 모를 진단명 대신 보이는 증상으로 쓸 것(이미 진단받았다고 쓴 병명은 허용), 품종·이름·수치는 빼거나 바꿀 것
- **시범 100건으로 먼저 쟀다.** 비용, 베끼기 비율(질의의 Kiwi 토큰 중 원문에 있는 비율: 짧은 0.67, 긴 0.56), 난이도(위 표). 대부분 원래 상담을 1위로 찾을 만큼 쉬우면 배울 게 없고, 거의 못 찾으면 질의가 엉터리다. 그 사이였다.
- **전체 생성:** 19,206건, 오류 0, 중복 0. 입력 932만·출력 487만 토큰(추론 345만 포함), **$3.37**(제3자 단가 기준 입력 $0.10, 출력 $0.50 / 100만 토큰), 동시 16개로 약 1시간.
- 예: "강아지 오줌 색이 갑자기 달라졌어요", "나이 든 강아지가 며칠째 설사하는데 오늘은 피와 끈적한 게 섞여 나왔어요"
- **짧은 질의의 한계:** "강아지가 초콜릿을 먹었는데 어떻게 해야 하나요?"는 맞는 상담이 원문 하나가 아니다. 학습에서 다른 맞는 상담이 오답 취급될 수 있다. 그래서 짧은 질의를 넣은 B와 뺀 A를 나눠 비교했다.

### 2-2. 학습 (`notebooks/finetune_embedding_colab.ipynb`, 생성 코드 `scripts/build_finetune_notebook.py`)

| 항목 | 값 |
| --- | --- |
| 환경 | Colab 무료 Tesla T4(15GB), Python 3.12.13, torch 2.11 + CUDA 12.8, VS Code Colab 확장 |
| 손실 | MultipleNegativesRankingLoss(배치 안의 다른 상담을 오답으로) |
| 배치 / 학습률 / epoch / 길이 | 64 / 2e-5 / 1 / 128토큰(앱 ONNX 토크나이저와 같음) |
| 배치 구성 | `NO_DUPLICATES`: B는 상담 하나에 질의가 둘이라, 같은 상담이 한 배치에 두 번 들어가면 자기 자신을 오답으로 배운다 |
| A | `detailed`만, 18,906쌍, 학습 2.4분 |
| B | `short` + `detailed`, 37,812쌍, 학습 4.6분 |
| 개발용 평가 | 학습에서 뺀 상담 300개의 질의 600개로, 원래 상담을 19,206개 중 몇 위에 찾는지 |

- **로컬에서 먼저 돌렸다.** Colab에 넘기기 전에 CPU에서 작은 부분집합(SMOKE)으로 끝까지 실행했다. 이때 학습 패키지 누락(`accelerate`)과 평가 점수 키 이름 문제를 미리 고쳤다.
- **토큰 처리:** VS Code Colab 확장에서는 Colab 비밀 값(`userdata`)을 못 읽는다(day48 노트북 기록). 그래서 토큰을 직접 입력받는다.
- 결과 모델은 Hugging Face 비공개 저장소 `blanden77/ko-sroberta-dograg-a`, `-b`에 상담 19,206개의 벡터(기준 모델 것 포함)와 함께 올렸다.

**개발용 점수 (합성 질의라 실제보다 좋게 나온다):**

| | 1위 | 10위 안 | 50위 안 | MRR@10 |
| --- | ---: | ---: | ---: | ---: |
| 기준 | 0.12 | 0.29 | 0.43 | 0.17 |
| A | 0.43 | 0.65 | 0.80 | 0.50 |
| B | 0.48 | 0.75 | 0.86 | 0.57 |

### 2-3. 진짜 평가 (`scripts/evaluate_finetuned_embedding.py`)

같은 조건에서 비교하려고 세 모델 모두 **정확한 전수 검색**(19,206개 코사인)으로 Dense 12건을 뽑고, BM25 12건과 RRF로 합쳐 상위 3건을 본다. 앱과 같은 경로다. 앱의 Chroma는 근사 검색이다.

| 평가 세트 | 질문 | 지표 |
| --- | --- | --- |
| 짧은 질문 | 응급 평가셋 120문항(사람이 짧게 쓴 질문, 합성 질의 생성과 무관) | `useful@3`: 상위 3건 중 "바로 쓸모 있음(2점)"이 하나라도 있는 비율 |
| 긴 상담 글 | 검증셋 100문항(실험 9의 판정 세트) | `useful@3`, 기존 판정 재사용 + 새로 나온 후보만 같은 판정으로 추가 채점 |
| 긴 상담 글 (라벨) | 검증셋 561문항 | `hit@3`: 연령·진료과·질병 라벨 일치 |

- 판정은 실험 9와 같은 LLM 판정(`scripts/relevance_set.py`)이다. 판정할 때 어느 모델이 찾은 후보인지는 보여 주지 않았다.
- 같은 질문끼리 짝지어 McNemar 검정(기준 대비)을 했다.

## 3. 결과

| 평가 | 기준 | A | **B** | B vs 기준 |
| --- | ---: | ---: | ---: | --- |
| **짧은 질문 `useful@3`** (120) | 0.625 | 0.733 | **0.800** | 26개 얻고 5개 잃음, **p=0.0002** |
| 짧은 질문 `relevant@3` | 0.967 | 0.992 | 1.000 | |
| **긴 상담 글 `useful@3`** (100) | 0.74 | 0.80 | **0.85** | 16개 얻고 5개 잃음, **p=0.027** |
| 긴 상담 글 `hit@3` (561, 라벨) | 0.262 | 0.271 | 0.262 | 44개 얻고 44개 잃음, p=1.0 |

- **B를 고른다.** 목표였던 짧은 질문에서 가장 크게 좋아졌고, 긴 상담 글에서도 유의하게 좋아졌다. 짧은 질의가 정답이 여럿이라는 우려와 달리, 짧은 질의를 넣은 B가 A보다 모든 `useful@3`에서 나았다.
- **라벨 `hit@3`는 그대로다.** 이 지표는 라벨이 질문과 34~59%만 맞아 둔감하다(실험 8). 실험 9 이후 주 지표는 `useful@3`다.
- **계산 확인:** 기준 모델의 `hit@3` 0.262는 앱 경로로 잰 기존 값(0.2620)과 같다. 기준의 긴 상담 `useful@3` 0.74가 실험 9의 0.72와 다른 것은 정확한 전수 검색과 Chroma 근사 검색의 차이다.

## 4. 한계와 주의

- **같은 계열 모델:** 질의를 만든 모델과 채점한 모델이 같은 계열(`gpt-6-luna`)이다. 채점할 때 모델 이름은 가렸지만, 같은 계열이라 치우칠 수 있다. B가 새로 맞힌 짧은 질문 20개 정도를 사람이 직접 보면 신뢰도가 크게 오른다(아직 안 함).
- **짧은 질문 세트:** 응급 평가셋이라 응급·일상 증상에 치우쳐 있다. 사람이 쓴 짧은 질문이지만 수의사 검토는 없다.
- **개발용 점수는 낙관적이다.** 같은 방식으로 만든 합성 질의라 실제보다 높다. 모델을 고를 때만 썼고 결론에는 쓰지 않았다.
- **한 번만 학습했다.** 시드를 바꾼 반복이나 학습률·epoch 비교는 하지 않았다. 어려운 오답(검색 상위 중 원문이 아닌 것)을 넣는 실험도 계획만 했다.
- **데이터 이용 조건:** AI Hub는 학습한 모델의 공개를 허용한다(데이터셋 이름과 aihub.or.kr 출처 표기). 원본과 단순 가공본의 공유는 금지라, 합성 질의와 상담 원문은 비공개 데이터셋(`blanden77/dograg-data`)에만 둔다([데이터 명세서](../data-sources.md)).

## 5. 앱 적용 (2026-10-10)

1. **ONNX 변환** (`scripts/export_finetuned_onnx.py`): float ONNX는 PyTorch와 완전히 같았다(코사인 1.0). int8 양자화 설정에 따라 차이가 컸다.

   | 양자화 | 평균 코사인 (최소) | 파일 |
   | --- | ---: | ---: |
   | 기존 앱 모델(기준 모델 공식 int8) | 0.989 (0.977) | 111MB |
   | 기본 설정(모든 연산, 텐서당 스케일) | 0.960 (0.937) | 111MB |
   | **MatMul만, 채널별 스케일 (채택)** | **0.990 (0.985)** | 186MB |

   기본 설정은 임베딩 표까지 양자화해 원본에서 멀어졌다. 채택한 설정은 기존 앱 모델보다 원본에 가깝지만, 임베딩 표를 float로 둬서 파일이 75MB 크다.
2. **Chroma 재구축** (`scripts/rebuild_health_collection.py`): 기존 `pet_care` 컬렉션의 문서·메타데이터·ID는 그대로 두고 벡터만 B 모델 것(정규화, 코사인)으로 바꿨다. DB는 210 → 177MB.
3. **데이터 버전:** 새 DB는 비공개 데이터셋의 새 브랜치 `data-v2`에 올렸다. 코드가 `REVISION = "data-v2"`로 고정한다(`src/private_data.py`). 데이터셋의 `main`(기준 모델 벡터)은 그대로 둬서, 옛 코드가 재시작돼도 새 벡터를 받지 않는다. 서버에 옛 파일이 남아 있어도 받은 버전 표시가 다르면 다시 받는다.
4. **모델 위치:** `blanden77/ko-sroberta-dograg-b`(비공개)의 `onnx/model_qint8.onnx`. 앱은 `HF_TOKEN`으로 받는다(`src/resources.py`).

**앱 경로 평가** (`scripts/evaluate_app_retrieval.py`): 근사 검색 Chroma + int8 ONNX + BM25 + RRF, 앱이 쓰는 `retrieve_health` 그대로다.

| | 이전 (기준 모델) | **이후 (B)** | 이후 vs 이전 |
| --- | ---: | ---: | --- |
| 짧은 질문 `useful@3` (120) | 0.600 | **0.783** | 26개 얻고 4개 잃음, p=0.0001 |
| 긴 상담 글 `useful@3` (100) | 0.72 | **0.84** | 18개 얻고 6개 잃음, p=0.023 |
| 긴 상담 글 `hit@3` (라벨, 561) | 0.2638 | 0.2602 | 38개 얻고 40개 잃음, p=0.91 |

- "이전" 값(0.72, 0.2638)은 앱에서 잰 기존 기록과 같다. 정확한 전수 검색 평가(위 3)와 비교하면 앱 경로에서 이득이 조금 작지만 결론은 같다.

## 네 축 종합 정리 (2026-10-13, Day 58 교안 방식, 새 측정 없음)

ADR-0001의 결정을 교안의 선정 절차로 다시 계산했다. 수치는 이 문서와 [deployment-resources.md](deployment-resources.md)의 기존 측정에서 옮겼다.

**축과 출처:**
- 정확도: 짧은 질문 useful@3(앱 경로, 120문항). 보호자 실제 말투에 가장 가까운 지표다.
- 지연: 질문당 검색 시간. 기준 int8에서 0.44초로 쟀다. 미세조정 int8은 같은 구조라 따로 재지 않고 같은 값으로 둔다.
- 메모리: 앱 최대 메모리(`scripts/measure_memory.py`)
- 저장: 모델 파일 크기

**1. 제약으로 거르기**

| 후보 | 결과 | 빠진 이유 |
| --- | --- | --- |
| OpenAI `text-embedding-3-small` | hit@3 0.2674 → 0.2353 (라벨 지표) | 건강 질문이 외부로 나간다. 같은 지표에서도 더 나빴다 |
| ko-sroberta PyTorch | 최대 1,587MB | 메모리 목표(약 1,100MB, 메모리 경고 대응 때 정함) 초과 |
| ko-sroberta ONNX fp32 | 최대 1,294MB | 메모리 목표 초과 |
| bge-m3 (로컬) | 보고서용으로 쟀을 때 앱 최대 3,195MB | 메모리 목표 초과. 건강용으로는 재지 않았다 |

**2. 남은 두 후보와 지배 관계**

| 후보 | useful@3 (짧은) | 지연 | 최대 메모리 | 모델 파일 |
| --- | ---: | ---: | ---: | ---: |
| 기준 ko-sroberta int8 | 0.600 | 0.44초 | 943MB | 111MB |
| **미세조정 ko-sroberta int8** | **0.783** | 0.44초 (같은 구조) | 1,013MB | 186MB |

- 서로 지배하지 않는다. 미세조정 모델은 정확도가, 기준 모델은 메모리와 파일 크기가 낫다. 둘 다 파레토 후보다.

**3. 고정 기준 점수**
- 기준: 지연 3초, 메모리 1,100MB, 파일 500MB
- 가중치: 정확도 0.7, 나머지 각 0.1
- 결과: **미세조정 0.704**, 기준 0.597
- 검산(환율): 정확도 1%p = 메모리 77MB = 파일 35MB = 지연 0.21초

**4. 민감도:** 가중치를 하나씩 ±20% 바꾼 8가지 조합 모두 미세조정 모델이 1위다. 격차는 0.10~0.12다.
- 기준 모델이 이기려면 메모리 차이가 약 1,409MB가 되어야 한다. 실제 차이는 70MB다. 정확도 차이 0.183이 매우 커서 결정이 흔들리지 않는다.

**5. 이 정리로 확인한 것과 한계**
- ADR-0001의 결정은 교안 절차로 계산해도 같다.
- **메모리 제약을 Streamlit Cloud 보장값(690MB)으로 두면 후보가 하나도 남지 않는다.** 두 후보 모두 최대 900MB가 넘는다. 실제 운영은 보장값이 아니라 최대 2.7GB에 기대고 있다. 이 위험은 Cloud Run(2GiB) 이원화로 덜었다.
- 정확도 축을 하나의 지표로 맞추지 못한 후보가 있다. OpenAI는 라벨 hit@3만 있고 useful@3이 없다. 그래서 점수를 매기지 않고 제약 단계에서 뺐다.

## 기본 모델 비교: multilingual-e5-small (2026-10-13)

질문: 미세조정 전 기본 ko-sroberta보다 나은 기본 모델이 있으면, 그 모델에 미세조정하는 편이 낫지 않을까? Day 58 교안 01의 후보 중 메모리에 들어갈 만한 `intfloat/multilingual-e5-small`과 비교했다.

- 방법: `scripts/compare_base_embeddings.py`
  - 같은 19,206건, 정확한 전수 검색(numpy)
  - 문서 벡터: ko-sroberta는 로컬 CPU(71분), e5-small은 Colab T4(`notebooks/e5_small_embed_colab.ipynb`)
  - 각 모델의 규칙을 따랐다. e5는 `query: ` / `passage: ` 접두어와 512토큰, ko-sroberta는 앱 설정 그대로 128토큰.
  - 문서 검색만(Dense)과 앱 방식 하이브리드(Kiwi BM25 + RRF, 상위 3건) 두 가지로 쟀다.
  - 지표: 짧은 질문 120 + 긴 상담 글 100의 `useful@3`. 새로 나온 문서만 같은 판정으로 추가 채점했다.

| | ko-sroberta (기본) | e5-small (기본) | 차이 (McNemar p) |
| --- | ---: | ---: | --- |
| 하이브리드 짧은 질문 | 0.625 | 0.633 | p=1.0 |
| 하이브리드 긴 상담 글 | 0.74 | 0.72 | p=0.85 |
| **하이브리드 전체 (220)** | **0.677** | **0.673** | p=1.0 |
| Dense 짧은 질문 | 0.533 | 0.625 | p=0.16 |
| Dense 긴 상담 글 | 0.64 | 0.60 | p=0.61 |
| 잘린 문서 비율 | 51.7% (128토큰) | 2.4% (512토큰) | |
| 질의 임베딩 (CPU, 중앙값) | 107ms | 30ms | |
| 차원 | 768 | 384 | |

- **앱 방식(하이브리드)에서는 차이가 없다.** 0.677 대 0.673이다. 미세조정한 ko-sroberta는 같은 짧은 질문에서 0.800이다(위 3). 기본 모델끼리의 차이(±0.01)는 미세조정 효과(+0.175)에 비해 매우 작다.
- **Dense 짧은 질문에서는 e5가 9%p 높지만 유의하지 않다**(p=0.16). 문서를 거의 자르지 않는 것이 이유일 수 있다. 하지만 키워드 검색과 합치면 사라진다.
- **e5의 장점은 비용 축이다.** 질의가 3.5배 빠르고 벡터 크기가 절반이다. 지연은 이미 답변 시간(약 8초)에 비해 작아서 결정을 바꾸지 못한다.
- **결정: e5-small로 갈아타서 미세조정하지 않는다.** "기본 모델이 더 좋으면"이라는 조건을 넘지 못했다. 다시 하면 합성 질의 생성, 학습, ONNX 변환, 재색인, 회귀 확인을 모두 반복해야 한다. 그런데 같은 학습 데이터로 얻을 이득의 근거가 없다.
- **다시 볼 조건:** 짧은 질문을 Dense만으로 검색해야 하는 경우(예: 키워드 검색을 빼는 결정). 또는 질의 지연이 병목이 되는 경우. 이때는 e5-small 미세조정을 먼저 시도한다.

```bash
uv run --group tools python scripts/compare_base_embeddings.py
```

- e5 문서 벡터는 노트북이 비공개 데이터셋의 `experiments` 브랜치에 올린 `e5/base_embeddings_e5-small_rows.npy`를 `output/experiments/`에 받아 두면 다시 계산하지 않는다(`df.csv` 행 순서).
- 결과: `output/experiments/base_embeddings.json`

## 문서 길이와 청킹 (2026-10-13)

질문: 미세조정 ko-sroberta는 문서를 128토큰에서 자른다. 상담 글 19,206건 중 52%가 잘린다(중앙값 132토큰, 앞부분 약 250자만 반영). 잘림을 풀면 검색이 나아질까?
- 토크나이저 차이는 아니다. ko-sroberta와 e5-small 모두 1토큰에 약 1.95자다. 차이는 길이 제한 설정(128 대 512)뿐이다.
- PDF 보고서는 해당 없다. OpenAI 모델(8,191토큰)에 1,000자 조각(최대 1,296토큰)을 넣어 잘리지 않는다.

방법: `scripts/compare_doc_lengths.py`
- 문서 벡터는 Colab T4로 만들었다(`notebooks/doc_length_embed_colab.ipynb`). `len128`은 앱 벡터와 코사인 1.0으로 같다.
- 질문은 같은 모델(float)로 로컬에서 임베딩했다. 220문항 `useful@3`, McNemar는 `len128`과 비교했다.
- 청킹: 126토큰 창을 63토큰씩 밀었다. 글당 2.27조각, 모두 43,604조각이다. 글의 점수는 가장 맞는 조각의 점수다.

| 설정 | 문서 | 질문 | Dense 전체 | **하이브리드 전체** | 하이브리드 p |
| --- | --- | --- | ---: | ---: | --- |
| **len128 (지금)** | 128 | 128 | 0.832 | **0.823** | |
| len256 | 256 | 128 | 0.841 | 0.800 | 0.30 |
| len256q | 256 | 256 | 0.859 | 0.800 | 0.36 |
| len512 | 512 | 128 | 0.818 | 0.795 | 0.21 |
| len512q | 512 | 512 | 0.836 | 0.795 | 0.29 |
| chunk128 | 128 조각 | 128 | 0.832 | 0.800 | 0.30 |

- **잘림을 풀어도 나아지지 않았다.** 앱 방식(하이브리드)에서는 모든 설정이 지금보다 조금 낮다. 유의한 차이는 아니다.
- **Dense에서 가장 나은 것은 len256q의 긴 상담 글(0.84 → 0.90, p=0.07)이다.** 질문도 256토큰으로 길게 넣은 경우다. 하지만 키워드 검색과 합치면 0.85로 같아진다.
- **짧은 질문은 하이브리드에서 오히려 0.800 → 0.758~0.767로 내렸다**(p=0.13~0.34). 모델이 128토큰으로 학습해서 긴 입력의 벡터가 짧은 질문과 덜 맞는 것으로 보인다.
- **왜 잘림이 덜 아픈가:** 상담 글은 앞부분에 견종·나이·주요 증상이 온다. 키워드 검색(Kiwi BM25)은 글 전체를 본다.
- **결정: 128토큰 그대로 둔다.** ADR-0001에 잘림 축과 다시 볼 조건을 추가했다. 청킹을 하면 벡터가 2.27배가 되어 메모리 안 저장소는 약 134MB, Supabase는 표가 그만큼 커진다. 얻는 것은 없다.
- 지연: 220문항 질문 임베딩(float, CPU)이 128토큰 24초, 256토큰 34초, 512토큰 50초다.

## 큰 한국어 모델: KURE-v1 (2026-10-13)

질문: Supabase로 검색을 옮겨 메모리 여유가 생겼다(Streamlit Cloud 실제 약 1GB). Day 58 교안 01의 후보 중 건강 과제 점수가 가장 높은 KURE-v1이 지금 앱보다 나을까?
- KURE-v1: BGE-M3를 한국어 검색으로 추가 학습한 모델이다. 1,024차원, 파라미터 5.7억 개다. MTEB 한국어 `PublicHealthQA` 81.92(e5-small 73.70)다.
- 방법: `scripts/compare_kure.py`
  - 문서 벡터는 Colab T4로 만들었다(`notebooks/kure_v1_embed_colab.ipynb`). 1,024토큰까지 넣어 상담 글의 0.11%만 잘린다.
  - 질문은 이 PC에서 float로 임베딩했다. 앱은 배포 그대로(미세조정 ko-sroberta, 질문은 int8 ONNX)다.
  - 220문항 `useful@3`, 같은 Kiwi BM25 하이브리드, McNemar는 앱과 비교했다.

| | 앱 (미세조정 ko-sroberta) | KURE-v1 (미세조정 없음) | p |
| --- | ---: | ---: | --- |
| Dense 짧은 질문 | **0.817** | 0.708 | **0.019** |
| Dense 긴 상담 글 | 0.84 | 0.83 | 1.0 |
| Dense 전체 | **0.827** | 0.764 | 0.065 |
| 하이브리드 짧은 질문 | **0.783** | 0.683 | **0.023** |
| **하이브리드 전체** | **0.809** | 0.723 | **0.008** |
| 질문 임베딩 (CPU, 중앙값) | 26ms (int8) | 275ms (float) | |
| 모델 파일 | 186MB | 약 2.3GB (float) | |

- **KURE-v1이 유의하게 낮다.** 특히 보호자가 짧게 쓴 질문에서 약 0.10 낮다. 이 차이는 우리 질문 말투로 만든 합성 질의로 미세조정한 효과다. 리더보드 점수(공공 보건 FAQ)가 우리 질문에서 그대로 이어지지 않았다. 교안이 "리더보드는 후보를 좁히는 데만 쓴다"고 한 경우다.
- **기본 모델끼리는 KURE-v1이 낫다.** 기본 ko-sroberta는 같은 세트에서 Dense 0.582, 하이브리드 0.677이었다(위 "기본 모델 비교"). KURE-v1은 0.764·0.723이다.
- **결정: 바꾸지 않는다.** 앱 모델이 더 정확하고, 10배 빠르고, 파일이 12분의 1이다.
- **다시 볼 조건:** KURE-v1을 같은 합성 질의로 미세조정하면 지금 모델을 넘을 수 있다(기본 모델 차이 +0.18). 다만 int8로 줄여도 모델이 약 570MB라 앱 메모리가 약 1GB에 가까워진다. 짧은 질문 정확도가 더 필요해지면 그때 Colab에서 미세조정해 같은 세트로 재고, 메모리를 실측한다.

```bash
uv run --group tools --with psutil python scripts/compare_kure.py
```

- 노트북이 비공개 데이터셋 `experiments` 브랜치에 올린 `kure/kure_v1_rows.npy`를 `output/experiments/`에 받아 둔다.
- 결과: `output/experiments/kure_v1.json`

## 면접에서 설명할 것

- **왜 합성 데이터인가:** 짧은 질문과 정답 상담의 짝이 없다. 사람이 만들기에는 2만 개가 너무 많아서 LLM으로 만들었다. 대신 시범 100건으로 비용·베끼기·난이도를 먼저 확인했다.
- **왜 MNRL인가:** 짝(질의, 정답)만 있으면 배치 안의 나머지를 오답으로 쓸 수 있다. 오답 라벨이 따로 필요 없다. 대신 같은 상담이 한 배치에 두 번 들어가지 않게 했다(`NO_DUPLICATES`).
- **왜 개발용 점수로 결론 내지 않았나:** 학습 데이터와 같은 분포라 낙관적이다. 결론은 사람이 쓴 짧은 질문과 실제 검증셋으로, 앱과 같은 하이브리드 경로에서 냈다.
- **왜 McNemar인가:** 같은 질문에서 두 모델이 맞혔는지를 짝지어, 한쪽만 맞힌 질문의 비대칭만 본다.
