# Cloud Run 배포 (2026-10-11 시작)

Streamlit Community Cloud에 더해 Google Cloud Run에도 같은 저장소의 앱을 띄운다. 계획은 Cloud Run을 주 배포로, Streamlit Cloud를 예비로 두는 것이다.

## 1단계: 컨테이너 이미지 (로컬 측정)

**파일**
- `Dockerfile`: python 3.12-slim + uv로 잠금 파일 그대로 설치한다. torch는 설치하지 않는다.
- `.dockerignore`
- `scripts/prefetch_image_assets.py`

**빌드와 실행**

```bash
docker build --secret id=hf_token,env=HF_TOKEN -t ragdog .
docker run --rm -p 8080:8080 --memory=2g --env-file <키만 담은 파일> ragdog
```

**설계**
- **비공개 데이터와 모델을 이미지에 넣는다.**
  - 앱은 원래 시작할 때 비공개 HF 데이터셋(`data-v3`, 이미지 안 254MB)과 미세조정 ONNX 모델을 내려받는다.
  - Cloud Run은 실행 중에 쓴 파일이 메모리를 차지하고, 새로 켜질 때마다 다시 받아야 한다.
  - 그래서 빌드 단계에서 받아 둔다. 데이터는 `src/private_data.py`의 리비전이 바뀔 때만 다시 받는다(별도 레이어).
  - 실행 중에는 `HF_HUB_OFFLINE=1`로 허브에 접속하지 않는다.
- **HF 토큰은 BuildKit 비밀 값으로만 넘긴다.** 이미지 레이어와 기록에 남지 않는다. 이미지 안에서 `HF_TOKEN` 환경 변수, `.env`, `.streamlit/secrets.toml`이 모두 없음을 확인했다.
- **이미지는 비공개 저장소에만 올린다.** AI Hub 데이터에서 나온 파일이 들어 있으므로 Artifact Registry 같은 비공개 저장소에만 올리고, Docker Hub 같은 공개 저장소에는 올리지 않는다.
- **`RAGDOG_CONTAINER=1`로 배포 환경임을 알린다.** 그러면 `settings.deployed()`가 참이 된다. 로컬처럼 Chroma 폴더(177MB)를 `output/`에 복사하지 않고, Langfuse 환경은 `production`이 된다. 로컬 컨테이너 시험에서는 `LANGFUSE_TRACING_ENVIRONMENT=development`로 덮어썼다.

**측정 (Docker Desktop, 컨테이너 제한 2GB·CPU 1개, 2026-10-11)**

| 항목 | 결과 |
| --- | --- |
| 이미지 크기 | 2.75GB (패키지 1.3GB, 데이터 254MB, 모델 179MB) |
| 첫 빌드 | 2분 56초 (코드만 바뀌면 의존성·데이터 레이어는 다시 쓰고, 시간은 재지 않았다) |
| 헬스 체크(`/_stcore/health`) 200 | 컨테이너 시작 직후 |
| 대기 중 메모리 | 65MB |
| 첫 페이지 표시 | 4.2초 |
| 첫 질문 답변(모델·색인 로딩 포함) | 18.2초 |
| 두 번째 건강 질문 / 시설 질문 | 3.6초 / 바로 |
| 질문 3개 뒤 메모리 | 1,024MiB |
| 방문 보고서 실행 중 최고 메모리(2초 간격 표본) | 1.06GiB |
| 방문 보고서 | 90초, 검수 통과 |

- **메모리:** 2GiB면 여유가 있다. Cloud Run 인스턴스는 2GiB로 시작한다.
- **방문 보고서에서 본 것:** 진료비 조사원이 `incomplete: max_messages`로 답 없이 끝났다. 다시 물었는데도 또 답이 없어, `NoAnswer`로 기록되고 기본 안내로 대신했다. #86의 재질문이 한 번으로는 부족한 경우가 있다는 뜻이다. 컨테이너와는 관계없는 API 응답 문제였다. 원인과 수정은 [visit-prep-team.md](visit-prep-team.md) "답 없이 끝나는 조사원"에 있다.

## 2단계: GitHub Actions로 빌드와 배포

**준비 (한 번만):**
1. Cloud Shell에서 `scripts/gcp/setup_cloud_run.sh`를 실행한다. 다시 실행해도 이미 만든 것은 그대로 둔다. 만드는 것:
   - 비공개 Artifact Registry 저장소(`ragdog`, 서울). 최신 이미지 3개만 남긴다.
   - 서비스 계정 두 개
     - `ragdog-runtime`: 앱이 실행되는 계정. 비밀 값 읽기만 한다.
     - `github-deployer`: 이미지를 올리고 배포하는 계정.
   - Workload Identity 풀과 공급자. **이 저장소(`rndigkwk/dograg`)의 Actions만** 쓸 수 있다.
   - Secret Manager 비밀 값 3개: `OPENAI_API_KEY`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`. 값은 화면에 보이지 않게 입력받는다.
2. 스크립트가 마지막에 출력한 `WORKLOAD_IDENTITY_PROVIDER` 값을 GitHub 저장소 변수 `GCP_WORKLOAD_IDENTITY_PROVIDER`에 넣는다. 비밀 값이 아닌 식별자다.

**배포** (`.github/workflows/deploy-cloud-run.yml`)
- main에 병합될 때마다 다음 순서로 돈다.
  1. 이미지를 빌드한다. HF 토큰은 저장소 비밀 값을 빌드에만 쓴다.
  2. `IMAGE:<커밋>`으로 이미지를 올린다.
  3. `gcloud run deploy`로 배포한다.
  4. `/_stcore/health`가 200을 줄 때까지 확인한다.
- 저장소 변수가 없으면 이 작업은 실패하지 않고 건너뛴다.

**Cloud Run 설정과 이유**

| 설정 | 값 | 이유 |
| --- | --- | --- |
| 메모리 / CPU | 2GiB / 1 | 측정 최고 1.06GiB |
| 최소 / 최대 인스턴스 | 0 / 2 | 쓰지 않을 때 요금 없음. 최대 2개가 비용 상한 |
| session affinity | 켬 | Streamlit은 탭마다 웹소켓 세션을 서버에 둔다. 같은 브라우저는 같은 인스턴스로 보내야 한다(멈춘 방문 보고서 실행은 2026-10-16부터 Supabase) |
| 요청 시간 제한 | 3600초 | Streamlit은 탭마다 웹소켓을 열어 둔다 |
| CPU boost | 켬 | 새로 켜질 때 모델·색인 로딩을 빠르게 |
| Langfuse 환경 | `cloudrun` | Streamlit Cloud(`production`)와 트레이스를 나눠 본다 |

- 같은 점검을 두 배포에 함께 돌린다. 점검 내용: 모든 페이지 열기, 오류 상자 확인, 날짜 질문(모델 호출 없음).

- 로컬에서 Cloud Run에 돌린 첫 점검은 첫 화면까지 25초, 답변 2초, 모든 페이지 정상이었다. 마지막 방문 후 6분쯤 지난 때라 인스턴스가 꺼진 상태였는지는 확인하지 못했다.

## 비용
- 인스턴스가 최소 0개라 쓰지 않을 때는 실행 요금이 없다. 최대 2개로 묶었다.
- Artifact Registry는 최신 이미지 3개만 남긴다(이미지 하나 약 2.75GB, 레이어 대부분은 공유).
- 예산 알림은 결제 → 예산 및 알림에서 건다. 알림만 보내고 서비스를 멈추지는 않는다.
- 며칠 운영한 뒤 실제 사용량이 무료 범위 안인지 결제 화면에서 확인한다.

## 릴리스 점검과 롤백 (2026-10-19)

데이터가 바뀌는 배포는 손으로 네 단계를 거친다.
1. 비공개 데이터 리비전을 올린다(`src/private_data.py`의 `REVISION`).
2. 그 리비전을 HF에 업로드한다.
3. 병합한다. Cloud Run이 그 리비전으로 이미지를 만든다.
4. 같은 파일로 Supabase 표를 다시 채운다.

2026-10-18에는 4번을 병합 전 코드에서 실행했다. 그래서 OCR 조각이 옛 글로 남았는데, 다른 확인은 모두 통과했다.

**`scripts/release_check.py` (읽기만 함):**
- 이 작업 폴더와 운영의 각 부분을 맞춰 보고, 어긋난 곳은 고치는 명령을 출력한다. 하나라도 어긋나면 종료 코드 1이다.
- 확인하는 것:

  | 확인 | 무엇과 비교 |
  | --- | --- |
  | git | main이고 origin/main과 같은지, src·scripts·api에 커밋 안 한 변경이 없는지 |
  | revision | 코드의 `REVISION`이 HF에 있는지 |
  | local data | 받아 둔 비공개 데이터가 그 리비전인지 |
  | report table | Supabase 보고서 표와 로컬 정확 검색 저장소의 조각 id와 글(SHA-256)이 모두 같은지 |
  | health table | 건강 표의 id와 글(SHA-256, DB 안에서 계산)이 모두 같은지, 고르게 뽑은 20행의 벡터가 같은지(float16 오차 안). 2026-10-27 전에는 행 수만 봤다 |
  | api | 운영 API `/health`의 커밋이 HEAD인지 |

- 검증:
  - 10-19 운영에 돌리니 git(작업 브랜치)을 뺀 다섯 개가 통과했다.
  - 한 버전 전 저장소(data-v7)와 비교하게 하면 "different text 4"로 고칠 OCR 조각 4개를 잡았다. 10-18의 실수를 잡는다.

**API 롤백 (`.github/workflows/rollback-api.yml`):**
- Actions의 "Roll back the API"에서 실행한다.
- Cloud Run은 배포한 리비전을 모두 남긴다. 그래서 다시 빌드하지 않고 트래픽만 옮겨 몇 초 만에 되돌린다.
  - 리비전을 비워 두면 지금 리비전의 바로 앞 리비전으로 간다.
  - 이름을 넣으면 그 리비전으로 간다.
  - `to_latest`를 켜면 최신 리비전으로 돌아온다.
- 끝에서 `/health`가 그 리비전의 커밋을 보고할 때까지 기다린다.
- 롤백하면 트래픽이 옛 리비전에 고정된다. 그래서 배포 워크플로가 배포 뒤에 `--to-latest`로 트래픽을 새 리비전에 돌려준다.
- 비공개 데이터는 이미지에 들어 있다. 그래서 API를 되돌리면 그 리비전의 코드와 데이터가 함께 돌아간다. Supabase 표는 따로 되돌려야 한다(위 4번을 옛 리비전으로).

## API 카나리 배포: 트래픽 0%로 올리고 검사한 뒤 넘기기 (2026-10-20)

**왜:** 세 차례 포트폴리오 평가(GPT·Opus·10-18)가 공통으로 꼽은 빈칸이 "승격과 복구"였다. 그때까지는 배포하자마자 새 리비전이 트래픽을 받았다. 나쁜 버전이면 사용자가 먼저 겪고, 사람이 롤백 워크플로(`rollback-api.yml`)를 돌려야 했다.

**바꾼 것** (`deploy-cloud-run.yml`):
1. 새 API 리비전을 `--no-traffic --tag=candidate`로 올린다. 사용자 트래픽은 이전 리비전에 그대로 있고, 새 리비전은 `https://candidate---ragdog-api-….run.app`로만 닿는다.
2. `scripts/canary_check.py`가 그 주소에서 네 가지를 확인한다.
   - `/health`가 배포한 커밋을 말하는지
   - 시설·진료비 API가 200인지(모델 없음)
   - 날짜 질문(규칙, 모델 없음)과 건강 질문(모델 약 4번)이 답까지 오는지
   - 한도 소진 안내(`degraded`)는 답으로 치지 않는다.
3. 통과하면 `update-traffic --to-latest`로 트래픽을 모두 넘긴다(롤백으로 고정된 트래픽도 이때 풀린다).
4. 실패하면 트래픽을 넘기지 않고 작업이 실패한다. 알림 워크플로가 이슈를 연다.

- **10% 단계를 두지 않은 이유:** 시간당 질문이 몇 개뿐이라, 트래픽 일부를 몇 분 보내도 좋고 나쁨을 가를 표본이 없다. 0% 상태의 검사가 실제로 판단하는 단계다.
- **스크립트:** 표준 라이브러리만 써서 배포 작업의 `python3`로 돈다. 요청에는 배포 점검 표시(`RagDogCheck`)를 붙여 데이터 공백 표에 남지 않게 했다.
- **고장 연습:** 수동 실행(workflow_dispatch)의 `fault`를 고르면 후보 리비전만 `RAGDOG_FAULT`를 달고 올라가고, 결과와 상관없이 승격하지 않는다(승격과 배포 확인 단계에 `if: fault == none`). 다음 정상 배포는 환경 변수를 통째로 다시 정해서 이 값이 남지 않는다.
  - `fault=chat`: 모든 질문에 오류를 낸다. 검사가 **실패**해야 한다(트래픽이 넘어가지 않음).
  - `fault=supabase`: 데이터베이스 연결이 모두 실패한다(`src/supabase_store.fault_injected`). 검색은 로컬 저장소로, 질문 한도는 메모리로, 진료 준비 보관은 메모리로 넘어가 검사가 **통과**해야 하고, 건강 답변 결과에 `"search": "local"`이 붙어야 한다(`--expect-search local`).
  - `fault=openai`: 채팅 모델의 OpenAI 주소를 아무도 듣지 않는 주소로 바꾼다(`src/resources.openai_base_url`). 모든 OpenAI 호출이 연결 실패하고 Claude Haiku가 대신 답해야 한다([ADR-0012](../adr/0012-claude-fallback.md)). 낮춘 화면("degraded")이면 건강 질문 검사가 실패하므로, 검사가 **통과**해야 한다.
- **연습 기록(2026-10-20):**
  - `fault=chat` (run 39377965715): `FAIL no answer to '오늘 날짜 알려줘'`(주입한 오류) → 승격 skipped, 운영은 3326c23c 그대로 정상 응답. 경보 이슈 #254가 자동으로 열려 기록 후 닫았다.
    - 발견 1: 실패하면 앞서 통과한 검사 줄이 로그에 없었다(run()이 끝난 뒤 한꺼번에 출력). 통과할 때마다 출력하게 고쳤다.

## Streamlit 화면을 안내 페이지로 (P5, 2026-10-23)

새 웹 주소(Vercel)로 옮긴 지 일주일이 지나 프로젝트 소유자가 정했다: 옛 Streamlit 화면은 새 웹 앱으로 가는 안내만 보여 준다(선택지 B). 화면이 둘이면 화면 수정을 두 번 해야 했다(예: #273 근거 번호).

- **두 곳 모두:** Cloud Run Streamlit 서비스(`ragdog`, main의 `main.py`)와 Streamlit Community Cloud 주소(`streamlit-backup` 브랜치). 옛 페이지 주소(`/rag`, `/hospital` 등)도 같은 안내를 보여 준다.
- **안내 페이지는 데이터와 모델을 올리지 않는다.** 그래서 Cloud Run Streamlit 서비스의 메모리를 2Gi에서 512Mi로 줄였다.
- **같은 날 Cloud Run Streamlit 서비스(`ragdog`)는 지웠다.** 안내만 띄우는 서비스를 배포마다 올리고 점검할 이유가 없고, 구글 클라우드 안에 있어 구글 클라우드 장애 때 대비책도 못 된다. 배포 워크플로에서 빼고 서비스를 삭제했다. 대비 화면은 Streamlit Cloud(`streamlit-backup`)다: 평소엔 안내, 장애 때 Secrets에 `STREAMLIT_FULL_APP = "1"`을 넣어 전체 화면으로 바꾼다([수동 배포·복구](../runbook-manual-deploy.md) 5절).
- **8시간 점검(`keep-alive.yml`):** Streamlit 페이지를 브라우저로 열던 점검을 바꿨다. 지금 서비스 중인 API에 배포 카나리와 같은 네 검사(`canary_check.py`, 커밋 확인은 빼고)를 하고, 웹 앱 주요 페이지 6개가 200인지 본다. 건강 질문이 Supabase 검색을 거치므로 Supabase 휴면 방지와 검색 확인 작업은 그대로다. main에 push할 때는 돌지 않는다. 배포 워크플로가 같은 카나리를 이미 돌린다.
- **되살리기:** 코드는 `app_pages/`에 그대로 있다. `STREAMLIT_FULL_APP=1`이면 전체 화면이 뜬다. 이원화 배포를 다시 보여 줄 때 메모리를 먼저 줄인 뒤 되살린다(메모리 2Gi, 점검 대상 복원).

## API 시작 때 검색 미리 읽기 (2026-10-23)

Streamlit에는 검색 미리 읽기가 있었지만 API에는 없어서, 인스턴스가 새로 뜬 뒤 첫 건강 질문이 검색 모델·저장소·답변 표를 읽는 시간을 냈다.
이미지와 같은 의존성(`uv sync --no-dev`)으로 로컬에서 쟀다.

| 단계 | 시간 |
| --- | ---: |
| 앱 불러오기(`import api.main`, uvicorn이 포트를 열기 전) | 약 19초 |
| 질문용 임베딩 모델(ONNX) | 1.9~4.7초 |
| 검색 저장소 + 첫 Supabase 검색 | 0.45 + 1.6초 |
| 답변 표 | 0.6초 |

`api/main.py`의 `warm_up()`이 이 셋을 시작 단계(lifespan) 안에서 읽는다. 백그라운드 스레드로 하지 않은 이유는 Cloud Run이 요청 사이의 인스턴스에는 CPU를 거의 주지 않기 때문이다. 시작 단계에는 CPU를 주고 `--cpu-boost`로 더 준다.
웹 앱은 페이지가 열릴 때 `/health`를 불러 인스턴스를 깨운다. 그러니 보호자가 질문을 쓰는 동안 미리 읽기가 끝난다. 걸린 시간은 요약 줄 `kind: warmup`의 `latency_ms`에 남는다.
실패해도 앱은 뜨고, 첫 질문이 예전처럼 나머지를 읽는다.

배포 검사 첫 건강 질문의 59~69초(14회 중 3회)는 이것으로 설명되지 않는다. 시간이 일정해서 어딘가의 60초 제한 시간이 의심되고, 운영 요청 로그로 따로 본다.
