# 건강 RAG 검색 실험

## 현재 상태 (2026-09-28 기준)

건강 질문은 **Dense + BM25 하이브리드, 동일 가중치 RRF**로 검색한다(PR #1, 커밋 `ce324f6f`).

| 설정 | 값 |
| --- | --- |
| Dense | Chroma `pet_care`, `jhgan/ko-sroberta-multitask` |
| BM25 | `rank_bm25.BM25Okapi`, Chroma 전체 문서로 메모리에 색인 |
| BM25 토크나이저 | Kiwi 형태소 분석, 명사(`N*`)·외국어(`SL`)·숫자(`SN`)만 사용 |
| 각 검색기 후보 수 | 12 |
| 결합 | RRF, c=60, 가중치 0.5 / 0.5 (실험 4에서 조정 효과 없음 확인), 동점은 문서 ID 순 |
| 최종 반환 | 기본 3건 (UI에서 1~5) |
| 메타데이터 필터 | Dense는 Chroma `filter`, BM25는 같은 조건을 파이썬으로 평가 |

## 평가 기준 (꼭 읽을 것)

- **정답 규칙:** 검색 문서의 `meta.lifeCycle`, `meta.department`, `meta.disease` 세 값이 질문과 **모두 정확히 일치**하면 적중.
- **이 지표는 의료적 정확도가 아니다.** 같은 질병이라도 연령 단계가 다르면 오답으로 처리되므로 절대값이 낮게 나온다. 방법끼리 비교하는 상대 지표로만 쓴다.
- 검증 데이터에 `기타`가 없으므로 `기타` 그룹 성능은 측정되지 않는다([data.md](data.md)).
- **2026-10-08부터 주 지표는 `useful@3`(실험 9)다.** 위 라벨 일치 규칙은 라벨 자체가 질문 본문과 34%·59%만 맞아(실험 8) 품질을 크게 낮춰 잡는다. 예전 실험과 비교할 때만 함께 적는다.

## 실험 기록

### 1. 답변 의미 유사도 (2026-08-24, Dense only)

`notebooks/rag_retrieval_evaluation.ipynb`, validation 50건 샘플, top-k 3

| 지표 | 값 |
| --- | ---: |
| 생성 답변 ↔ 정답 답변 평균 cosine | 0.7448 |
| 검색 근거 중 최고 ↔ 정답 평균 cosine | 0.7721 |
| `hit@3` (메타데이터 일치) | 0.2000 |

**해석:** 생성 답변이 검색 근거보다 정답에서 더 멀다. 생성 단계에서 근거의 정보가 일부 사라진다는 뜻이고, 검색뿐 아니라 프롬프트도 개선 대상이다.

### 2. 문자 n-gram 재정렬 — **기각** (2026-09-27)

Dense 후보 12건을 질문과 문서의 2·3-gram 겹침 비율로 재정렬(`src/health_retrieval.py`). 추가 모델 없이 질병명 일치를 높이려는 시도.

validation 561건 전체, 출처 `output/health_retrieval_comparison.json` (생성: `uv run python tests/evaluate_health_retrieval.py`)

| 방법 | hit@3 | MRR@3 | 미적중 |
| --- | ---: | ---: | ---: |
| Dense (기준) | 0.2264 | 0.1503 | 434 |
| Dense + 재정렬 | 0.2228 | 0.1583 | 436 |

**결정:** 적용하지 않음. 사전에 정한 채택 조건(전체 `hit@3` 개선, 비`기타` 악화 없음)을 통과하지 못했다. MRR은 소폭 올랐지만 적중 수 자체가 줄었다. 코드는 평가용으로만 남아 있다.

### 3. Dense + BM25 RRF — **채택** (2026-09-28)

validation 561건, 생성: `uv run python scripts/evaluate_hybrid_search.py` → `output/hybrid_retrieval_benchmark.json` (재측정본 `..._day47_retest.json`, 품질 수치 동일)

| 방법 | hit@3 | MRR@3 | 미적중 |
| --- | ---: | ---: | ---: |
| Dense | 0.2264 | 0.1503 | 434 |
| BM25 | 0.2531 | 0.1800 | 419 |
| **Hybrid (RRF)** | **0.2674** | **0.1866** | **411** |

지연 시간 (로컬, 561회):

| 단계 | 평균 | 중앙값 | p95 |
| --- | ---: | ---: | ---: |
| Dense | 171 ms | 176 ms | 234 ms |
| BM25 | 532 ms | 409 ms | 1,333 ms |
| Hybrid 전체 | 704 ms | 598 ms | 1,558 ms |

**결정:** 적용. Dense 대비 hit@3가 +4.1%p(상대 +18%), 미적중이 23건 줄었다.

> **정정 (2026-10-02, 실험 4):** 위 하이브리드 수치는 벤치마크 스크립트 안의 RRF로 측정한 값이다. 이 RRF는 점수가 같으면 BM25 문서를 앞에 둔다. 운영 코드(`src/hybrid_retrieval.py`)는 동점을 문서 ID 문자열 순으로 처리한다. 같은 후보로 운영 코드를 재현하면 **hit@3 0.2620, MRR@3 0.1842, 미적중 414**다. Dense 대비 개선(+3.6%p)이라는 결론은 그대로다.

**치른 비용:**
- 검색 지연이 약 4배 증가하며, 대부분 BM25 점수 계산(전체 19,206건 매번 계산)에서 나온다.
- 앱 첫 실행 시 BM25 색인 구축에 수 분이 걸린다(`st.cache_resource`로 1회만). Streamlit Cloud 재시작 때마다 다시 발생한다.

**참고:** BM25 단독도 Dense보다 낫다. 이 데이터의 질문은 질병명·증상명 같은 명사 일치가 중요하다는 신호다. 반대로 같은 이유로 n-gram 재정렬(실험 2)은 실패했는데, 문자 단위 겹침은 조사·어미 잡음이 많아서로 추정된다(검증하지 않음).

### 4. RRF 가중치 조정과 후보 재현율 — **가중치는 유지, 리랭킹은 유망** (2026-10-02)

[lecture-review.md](lecture-review.md)의 추천 1단계. 두 가지를 물었다.
1. Dense/BM25 가중치를 0.5/0.5에서 바꾸면 나아지는가?
2. 리랭커가 볼 후보 풀 안에 정답이 얼마나 자주 있는가?

- 실행: `uv run python scripts/evaluate_fusion_weights.py` (검색 결과 캐시 `output/fusion_candidates.json`, 분석만 다시 할 때 `--reuse-candidates`)
- 결과: `output/fusion_weight_sweep.json`
- 운영 코드의 `reciprocal_rank_fusion`을 그대로 써서 앱과 같은 순위를 재현했다. 가중치 인자는 이번에 추가했고 기본값은 0.5/0.5 그대로다.
- **과적합 방지:** 검증셋 561건을 고정 시드(47)로 tune 280건과 holdout 281건으로 나눴다. tune에서 가중치를 고르고 holdout에서 확인했다.

#### 가중치 (w = BM25 가중치, Dense는 1−w)

| w | tune hit@3 | holdout hit@3 | 전체 hit@3 | 전체 MRR@3 | 전체 미적중 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.0 (Dense만) | 0.2393 | 0.2135 | 0.2264 | 0.1503 | 434 |
| 0.3 | 0.2643 | 0.2242 | 0.2442 | 0.1708 | 424 |
| **0.5 (현재)** | 0.2929 | 0.2313 | 0.2620 | 0.1842 | 414 |
| 0.7 (tune 최고) | 0.2929 | 0.2349 | 0.2638 | 0.1892 | 413 |
| 1.0 (BM25만) | 0.2464 | 0.2527 | 0.2496 | 0.1818 | 421 |

전체 w 값(0.0~1.0, 0.1 간격)은 결과 JSON에 있다.

- tune에서 고른 0.7은 holdout에서 0.5보다 **13문항 맞히고 12문항 놓쳐, 순증 1문항**이다. 잡음 수준이다.
- 0.5~0.8 구간은 사실상 평평하다. 0.5 아래로 내리면(Dense 쪽) 확실히 나빠진다.
- **결정:** 0.5/0.5를 유지한다.

#### 동점 처리

0.5/0.5에서는 561건 중 **441건**이 상위 4건 안에 RRF 점수 동점을 가진다. Dense k위 문서와 BM25 k위 문서가 각각 한쪽에만 있으면 점수가 같아지기 때문이다. 운영 코드는 이 동점을 문서 ID 문자열 순으로 정하고 있어서 사실상 임의다.

| 동점 처리 | tune hit@3 | holdout hit@3 |
| --- | ---: | ---: |
| 문서 ID 순 (현재 운영) | 0.2929 | 0.2313 |
| BM25 우선 (예전 벤치마크) | 0.2964 | 0.2384 |
| Dense 우선 | 0.2857 | 0.2100 |

BM25 우선은 holdout에서 5문항 얻고 3문항 잃었다. 방향은 일관되지만 차이가 작다. 큰 성능 개선이라기보다 **임의 순서를 의도된 순서로 바꾸는 정리 작업**으로 볼 만하다(→ [open-questions.md](open-questions.md)).

#### 후보 재현율 — 이번 실험의 핵심

정답 문서가 후보 풀 어딘가에 있는 비율:

| 후보 풀 | 재현율 | 정답 포함 문항 |
| --- | ---: | ---: |
| **Dense 12 + BM25 12 (현재 앱)** | **0.6114** | 343 / 561 |
| Dense 20 + BM25 20 | 0.7023 | 394 / 561 |
| Dense 50 + BM25 50 | 0.8021 | 450 / 561 |

- 현재 풀에서도 정답이 있는 문항은 343개인데, 상위 3건에 드는 것은 147개(0.2620)뿐이다. **196문항은 정답이 후보에 있는데 순위에서 밀린다.** 순서를 다시 매기는 리랭커가 개선할 여지가 이만큼 있다는 뜻이다.
- 풀을 50+50으로 넓히면 재현율이 80%까지 오른다. 다만 리랭커가 점수를 매길 쌍도 그만큼 늘어난다(최대 약 100쌍, CPU 지연 증가).
- 111문항은 50+50 풀에도 정답이 없다. 리랭킹으로는 해결할 수 없고, 질의 변환이나 필터, 평가 기준 쪽의 문제다.
- **주의:** 정답 규칙이 메타데이터 3개 완전 일치라서, 같은 증상을 다룬 유용한 문서도 연령 단계가 다르면 오답으로 처리된다. 재현율과 hit@3 모두 이 기준에서의 상대 비교다.

**결론:** 가중치 조정으로 얻을 것은 없다. 리랭킹(추천 2단계)을 시도할 근거는 충분하다. 다음 실험은 Cross-Encoder로 현재 풀(최대 24건)을 재정렬해 hit@3와 질문당 지연을 측정하는 것이다.

### 5. 건강 Q&A 임베딩을 OpenAI `text-embedding-3-small`로 교체 — **품질 하락** (2026-10-04)

메모리 때문에 로컬 임베딩 모델을 없애려고, GPT 세션이 만든 OpenAI 컬렉션(`pet_care_openai3small_1536_2275beb30ef5`, 질문 문장만 임베딩)으로 앱을 전환한 뒤 같은 벤치마크를 돌렸다.

- 실행: `uv run python scripts/evaluate_hybrid_search.py --output output/hybrid_retrieval_benchmark_openai.json`
- 실험 3과 같은 스크립트, 같은 동점 처리(BM25 우선)라 실험 3의 수치와 직접 비교할 수 있다.

| 방법 | ko-sroberta (실험 3) | OpenAI 3-small | 차이 |
| --- | ---: | ---: | ---: |
| Dense hit@3 | 0.2264 | **0.1818** | −4.5%p |
| BM25 hit@3 | 0.2531 | 0.2496 | (BM25는 같은 방식, 문서 텍스트의 `\r`만 다름) |
| **Hybrid hit@3** | **0.2674** | **0.2353** | **−3.2%p** |
| Hybrid 미적중 | 411 | 429 | +18 |
| Dense 평균 지연 | 171 ms | 187 ms (API 호출 포함) | |

**해석**
- 이 데이터와 이 지표(메타데이터 3개 완전 일치)에서는 OpenAI 임베딩이 ko-sroberta보다 나쁘다. 하이브리드가 BM25 단독(0.2496)보다도 낮아졌다. 지금의 Dense 쪽이 오히려 순위를 흐린다는 뜻이다.
- 이 지표는 의료적 정확도가 아니다. 그래도 같은 조건에서 일관되게 떨어졌으므로 "품질이 유지된다"고 볼 근거가 없다.
- 반면 보고서 검색은 GPT의 30페이지 표본에서 OpenAI hit@3 0.94로 충분했다(`eval/report_embedding_sample_20261003/REPORT.md`).

**권장:** 건강은 ko-sroberta(기존 `pet_care`)로 되돌리고, 보고서만 OpenAI로 쓴다. 메모리는 약 1.76GB로 추정되며 Cloud 한도 2.7GB 안에 들어간다([deployment-resources.md](deployment-resources.md)). **2026-10-04 적용함.** 앱은 건강 `pet_care`(ko-sroberta), 보고서 `pet_reports_openai3small_1536_…`(OpenAI)를 쓴다.

### 6. 보고서 검색어에서 KB 목차 항목 제거 — **채택** (2026-10-04)

배포 앱에서 보고서 질문을 시험하다가, 근거 1순위로 KB 보고서의 목차 페이지(8쪽)가 나오는 것을 발견했다.

- **원인:** 질문이 KB 목차 항목과 맞지 않으면 `get_report_analysis_topics()`가 KB 목차 항목 **전체**를 돌려준다. 앱은 이것을 검색어 앞에 붙였다. 보고서가 KB 1종일 때 만든 방식이라 보고서 5종 구조와 맞지 않았다.
- **측정:** 정답 페이지가 고정된 보고서 질문 18개(`tests/data/crag_eval_questions.json`)로 비교했다.

| 검색어 | 상위 3건 적중 | 상위 6건 적중 | 결과에 KB 목차 페이지가 섞인 질문 |
| --- | ---: | ---: | ---: |
| 목차 항목 + 질문 (이전) | 4/18 | 7/18 | 17/18 |
| **질문만 (현재)** | **10/18** | **12/18** | 0/18 |

18개 질문 중 KB 목차 항목과 맞는 질문은 하나도 없었다. 그래서 모든 질문의 검색어 앞에 목차 항목 전체가 붙었다.

**결정:** 검색은 질문(또는 분해한 하위 질문)만으로 한다. 목차 항목은 답변 프롬프트의 분석 기준으로만 남긴다. CRAG 평가에서 보고서 정답 페이지 적중이 7/18로 낮았던 것도 이 문제 때문이었으므로, CRAG를 재평가할 때는 이 수정 이후 기준으로 비교해야 한다.

### 7. CRAG 근거 평가를 리랭커로 쓰기 — **효과 없음, 적용하지 않음** (2026-10-05)

후보 안에 정답이 있는 비율(61%)과 상위 3건 적중(26%)의 차이가 크다. 로컬 리랭커는 Cloud에서 쓸 수 없으므로, 이미 호출하고 있는 CRAG 근거 평가(LLM)가 고른 순서로 다시 정렬하면 `hit@3`가 오르는지 쟀다.

- 실행: `uv run python scripts/evaluate_llm_rerank.py --sample 100` (검증 Q&A에서 무작위 100문항, seed 47, 비용 때문에 561문항 전체가 아닌 표본)
- 비교 대상
  - 하이브리드: 운영 검색 상위 3건
  - LLM@5: 후보 5건을 평가에 넘기고, 고른 문서를 앞에 둔 뒤 나머지는 원래 순서. 지금 CRAG 설정이다.
  - LLM@12: 후보 12건을 넘긴 경우
  - 상한선: 후보 5건/12건 안에 정답이 하나라도 있는 비율. 재정렬로 얻을 수 있는 최대치다.
- 적중 기준은 실험 3과 같다(메타데이터 3개 일치).

| 방법 | hit@3 | 하이브리드 대비 얻음/잃음 | McNemar p | 평가 토큰/질문 |
| --- | ---: | ---: | ---: | ---: |
| 하이브리드 (운영) | 0.30 | – | – | – |
| LLM@5 (지금 CRAG) | 0.30 | 1 / 1 | 1.00 | 2,480 |
| LLM@5, 고른 문서만 | 0.26 | | | |
| LLM@12 | 0.34 | 10 / 6 | 0.45 | 4,205 |
| LLM@12, 고른 문서만 | 0.30 | | | |
| 상한선 @5 / @12 | 0.36 / 0.52 | | | |

이 표본의 하이브리드 hit@3(0.30)은 전체 561문항 값(0.262)보다 높다. 표본 간 비교가 아니라 같은 표본 안에서 짝지어 비교했다.

**해석**
- **지금 설정(후보 5건)에서는 재정렬 효과가 없다.** 상한선이 0.36이라 올릴 여지가 6문항뿐이었고, 실제로 1문항을 얻고 1문항을 잃었다.
- **후보 12건이면 +4문항이지만 통계적으로 의미 없다**(p=0.45). 평가 토큰은 약 1.7배, 지연은 약 +0.9초다. 상한선(0.52)과의 거리도 멀다. LLM이 이 지표의 정답을 잘 고르지 못한다.
- **"고른 문서만" 보여 주면 적중이 더 낮다**(0.26, 0.30). 앱은 고른 문서만 근거로 보여 준다. 메타데이터 라벨이 같은 문서라도 LLM은 질문에 쓸모없다고 판단해 버리기 때문이다. 이 지표는 라벨 일치일 뿐 답변에 쓸모 있는지는 아니다. 그래서 이 하락이 곧 품질 하락이라고 볼 수는 없다. 반대로 LLM 판단이 맞다는 근거도 이 실험에는 없다.
- 시도하다 중단한 전체 561문항 실행은 약 380만 토큰이 들 예정이었다. 결론을 뒤집을 만한 차이(+4/100)가 아니므로 전체 실행은 하지 않았다.

**결정:** 후보 수를 늘리지 않는다. 리랭킹으로 검색 품질을 올리려면 LLM 판정이 아니라 학습된 리랭커가 필요하다. 그런데 Cloud에서는 메모리와 속도 때문에 쓸 수 없다(deployment-resources.md). 남은 방법은 외부 리랭크 API나 경량 ONNX Cross-Encoder이고, 둘 다 측정하지 않았다.

### 실험 8: 질문 줄이기와 자동 필터 (2026-10-07)

**질문:** AI Hub 질문은 길고 인사·걱정·부탁 문장이 섞여 있다. 검색 전에 LLM으로 "나이·견종 + 증상 + 묻는 것" 1~2문장으로 줄이면 `hit@3`가 오를까?

**방법:** `scripts/evaluate_query_focus.py`. 지금까지의 벤치마크(필터 없는 하이브리드)가 아니라 **앱이 실제로 쓰는 경로**를 재현했다. 질문에서 연령 단계(나이 표현)와 진료과(키워드) 필터를 추론해 하이브리드 검색에 건다. 검증 561문항, 적중 기준은 같다(메타데이터 3개 일치). 줄인 질문은 근거 평가와 같은 모델(추론 끔)로 만들고 캐시했다.

| 검색어 / 필터 | hit@3 | MRR@3 | 앱(첫 줄) 대비 얻음/잃음 | McNemar p |
| --- | ---: | ---: | ---: | ---: |
| 원래 질문 / 연령+진료과 (**앱의 기존 동작**) | 0.141 | 0.096 | – | – |
| 줄인 질문 / 줄인 질문에서 추론한 필터 | 0.169 | 0.124 | 47 / 31 | 0.089 |
| 원래 질문 / 연령만 | 0.207 | 0.147 | 42 / 5 | <0.001 |
| 줄인 질문 / 연령만 | 0.194 | 0.141 | 62 / 32 | 0.003 |
| **원래 질문 / 필터 없음 (적용)** | **0.264** | **0.177** | **80 / 11** | **<0.001** |
| 줄인 질문 / 필터 없음 | 0.259 | 0.172 | 원래 질문·필터 없음 대비 56 / 59 | 0.85 |

**왜 필터가 손해인가:** 필터가 기대는 말뭉치 라벨이 질문 본문과 맞지 않는다.
- 연령 단계: 검색 말뭉치 19,206건에서 질문에 적힌 나이로 정한 단계와 라벨이 같은 비율이 **34%**(우연 수준, 단계 3개)다. "6개월" 질문이 노령견으로 붙은 식이다. 검증 문항에서 추론한 필터도 269건 중 83건(31%)만 정답 라벨과 같았다.
- 진료과: 키워드로 정한 진료과와 라벨이 같은 비율이 말뭉치 59%, 검증 문항 51%(488건 중 251건)다.
- 그래서 필터는 말뭉치의 임의 일부만 검색하게 만들었다. 사용자에게도 같은 손해다. 비슷한 상담이 라벨 때문에 빠진다.

**결정:**
- **자동 필터를 검색에 걸지 않는다**(`src/tools/health.py`의 `SEARCH_FILTER_KEYS = ()`). 추론한 값은 답변 프롬프트의 [선택 조건]에는 그대로 넘긴다. 앱 경로의 `hit@3`가 0.141에서 0.264로, 그동안 벤치마크로만 보던 값이 실제 앱에서 나오게 됐다.
- **질문 줄이기는 넣지 않는다.** 필터를 빼고 나면 차이가 없다(0.259 vs 0.264, p=0.85). 질문당 모델 호출 1회(약 1~2초)만 늘어난다. 코드는 평가 스크립트 안에만 남겼다.
- **답변 품질 확인 (CRAG 60문항, Langfuse 실험 `no-inferred-filters`):** accuracy 0.900 → **0.917**, 과잉 보류 1/38 → 1/38, 놓친 보류 5/22 → **4/22**, p90 12.6초 → 12.3초. 나빠진 지표가 없다.
- 재검색 때 진료과 필터를 풀던 처리(#34)는 이제 할 일이 없지만, 필터를 다시 켤 때를 위해 남겨 둔다.

### 실험 9: 라벨에 기대지 않는 평가 기준 (2026-10-08)

**왜:** 실험 8에서 정답 규칙이 기대는 라벨이 질문 본문과 맞지 않는다는 것을 알았다. 그 지표로는 리랭커 같은 개선을 판단할 수 없다.

**방법:** `scripts/relevance_set.py`, 결과 `tests/data/health_relevance_100.json`.
- 검증 561문항 중 100개를 고정 시드로 뽑는다.
- 질문마다 하이브리드가 합치는 후보 전부(Dense 12 + BM25 12, 평균 23.6개)와 예전 필터 경로의 상위 3개를 모은다.
- LLM(`gpt-6-luna`, 추론 low)이 후보마다 질문에 쓸모 있는지 매긴다. 2: 같은 문제를 다루고 답변이 바로 도움, 1: 관련 있거나 일부 도움, 0: 무관. 라벨은 보지 말고 내용으로만 판단하게 했다. 2,357개 후보를 매겼다(2: 549, 1: 896, 0: 912).
- 지표: `useful@3`(상위 3개에 2점 문서가 있는 질문 비율), `relevant@3`(1점 이상), `precision@3`(상위 3개 중 1점 이상 비율).

**판정의 일관성:** 20문항 473개 후보를 다시 매겼다. 정확히 같은 점수 86.5%(Cohen κ 0.79), 0↔2로 뒤집힌 것 0.2%, 그 20문항의 `useful@3`는 두 번 모두 0.60으로 같았다. 사람 검수는 아직 하지 않았다(아래 한계).

| 검색 | useful@3 | relevant@3 | precision@3 | 라벨 일치 hit@3 |
| --- | ---: | ---: | ---: | ---: |
| 예전 앱 (추론 필터 적용) | 0.46 | 0.86 | 0.633 | 0.14 |
| **지금 앱 (필터 없음)** | **0.72** | 0.99 | 0.770 | 0.29 |
| 후보 안에서 가장 좋은 3개 (상한) | 0.99 | 1.00 | 0.997 | 0.36 |

**해석**
- **실험 8의 결정(필터 제거)을 다른 기준으로도 확인했다.** 쓸모 있는 문서가 상위 3개에 있는 질문이 46% → 72%.
- 라벨 일치 지표는 품질을 크게 낮춰 잡는다(0.29 vs 0.72). 앞으로 검색 변경은 `useful@3`로 판단한다.
- 100문항 중 99개는 후보 안에 2점 문서가 있다. **순서만 바꿔도 0.72 → 0.99까지 오를 수 있다**는 뜻이고, 리랭커가 노릴 여지다(실험 11).
- `relevant@3`는 0.99로 거의 꽉 차서 비교에 쓸모가 적다. 주 지표는 `useful@3`.
- **한계:** 판정은 LLM 한 종류다. 같은 판정기가 두 번 매긴 일관성은 높지만, 판정 기준 자체가 맞는지는 사람이 일부 확인해야 한다. 질문 원문과 문서는 저장소의 CSV에 있고, 세트 파일에는 행 번호·문서 ID·점수만 둔다.

### 실험 11: ONNX Cross-Encoder 리랭커 (2026-10-08)

**질문:** 실험 9에서 후보 안에 쓸모 있는 문서가 99%인데 상위 3개는 72%였다. 배포 앱(CPU 2코어, 메모리 한도 2.7GB, torch 없음)에서 돌릴 수 있는 리랭커가 이 차이를 줄일까?

**방법:** `scripts/evaluate_reranker.py`(+ `scripts/onnx_reranker.py`). 실험 9의 판정된 후보를 리랭커로 다시 정렬해 같은 지표로 쟀다. 모든 후보가 이미 판정돼 있어 새 판정이 필요 없다. 앱의 질문 임베딩과 같은 방식(onnxruntime + tokenizers, 스레드 2개)으로 돌렸다.

- 20문항 열은 세 모델을 같은 부분집합에서 다시 잰 것이다. 느린 모델을 100문항 끝까지 돌리지 않고 경향과 시간만 보려고 줄였다. 이 실행의 시간은 다른 작업과 겹쳐 더 길게 나왔으므로 시간은 100문항 실행 값을 본다.

- jina는 100문항에서 0.72 → 0.76(4문항)으로 유일하게 나았지만, 질문별 유의성은 확인하지 않았고 20문항에서도 차이가 1문항이다.

**교안 모델 추가 측정 (2026-10-08):** day48 교안의 기본 리랭커 `Qwen/Qwen3-Reranker-0.6B`의 ONNX 변환본(4비트)을 같은 20문항으로 쟀다. 분류기가 아니라 언어 모델이라, 질문·문서 프롬프트 끝 위치의 "yes"/"no" 확률로 점수를 낸다(`scripts/onnx_reranker.py`의 `OnnxQwenReranker`).
- **품질:** useful@3 0.70으로 지금 순서(0.70)와 같다. 상위 3개 중 쓸모 있는 비율(precision@3)은 0.767 → 0.833으로 조금 올랐다.
- **속도·메모리:** 질문당 166초(후보 12개). 이 변환본은 모든 위치의 출력(문장 길이 × 15만 단어)을 내놓아 후보마다 수백 MB를 잠깐 쓰고, 평가 프로세스가 최고 4.9GB까지 올라갔다. 8비트 변환본은 결론을 바꾸지 못해 측정을 중단했다.
- 교안처럼 GPU나 torch로 돌리는 환경이 아니면, 이 크기의 언어 모델 리랭커는 실시간 답변에 넣기 어렵다.

**결정:** 리랭커를 넣지 않는다.
- jina의 +4문항을 위해 답변마다 약 8초와 메모리 약 0.5GB를 더 써야 한다. 지금 건강 답변 첫 글자까지가 약 6초다.
- jina는 비상업 라이선스라 서비스에 넣기 어렵다.
- 쓸 수 있는 라이선스의 두 모델은 오히려 나빴다.
- 남은 방향: 한국어 검색 데이터로 학습된 리랭커를 ONNX int8로 직접 변환해 재 보기, 또는 외부 리랭크 API(지연·비용·개인정보 확인 필요). 둘 다 이번 평가 세트로 바로 비교할 수 있다.

### 실험 12: 보고서 답변 컨텍스트 압축 (day48, 2026-10-08)

**질문:** day48 교안 02처럼 검색한 조각에서 질문에 필요한 문장만 뽑아(컨텍스트 압축) 답하면 나아질까? 압축하면 같은 길이에 더 많은 후보를 넣을 수 있으니, 실험 10이 병목으로 꼽은 검색(정답 페이지가 상위 6개에 12/18)도 함께 볼 수 있다.

**방법:** 실험 10과 같은 18문항·기준 답·판정(각 2회, `scripts/evaluate_report_pages.py compare --variants chunks compressed compressed12`). 압축은 교안의 `LLMChainExtractor`처럼 원문 문장을 그대로 옮기게 하되, 문서마다 부르지 않고 조각 전체를 번호와 함께 한 번에 넣어 한 번만 부른다(추론 강도 low). 답변 프롬프트는 앱과 같다.
- chunks: 지금 앱(상위 6개 조각)
- compressed: 같은 6개 조각을 압축
- compressed12: 상위 12개 조각을 압축(정답 페이지가 후보에 들어오는 질문 12/18 → 14/18)

| | 정답 | 일부 | 오답 | 보류 | 평균 문맥 길이 | 답까지 시간 p50 | 원문 그대로 옮긴 문장 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| chunks (지금) | 23/36 | 5 | 2 | 6 | 3,875자 | 2.7초 | – |
| compressed | 24/36 | 3 | 3 | 6 | 138자 | 4.3초 (압축 1.9초) | 85% |
| compressed12 | 25/36 | 3 | 2 | 6 | 136자 | 4.2초 (압축 2.0초) | 87% |

- **같은 질문끼리 비교(McNemar):** compressed는 chunks보다 1문항 맞히고 2문항 틀려 p=1.0, compressed12는 4문항 맞히고 2문항 틀려 p=0.69. 차이가 없다. 같은 설정의 chunks가 실험 10에서는 25/36, 이번에는 23/36이었으니 2문항 정도는 실행마다 흔들린다.
- compressed12가 새로 맞힌 r10은 후보를 12개로 늘려 정답 페이지가 들어온 질문이다. 반대로 r02는 12개 중에서 다른 표를 골라 두 번 다 틀렸다.
- 답변 모델이 읽는 문맥은 96% 줄었지만, 압축 모델이 원문 전체(6개면 3,875자, 12개면 약 7,700자)를 먼저 읽으므로 **토큰 합계와 시간은 오히려 늘었다**(+1.5초). 옮긴 문장의 13~15%는 원문에서 글자 그대로(공백 제외) 찾을 수 없었다. "원문 그대로"를 지시해도 모델이 문장을 다듬으므로, 수치를 한 번 더 옮겨 적는 단계가 생기는 셈이다.

**결정:** 적용하지 않는다. 교안도 "짧은 청크 몇 개라면 압축을 생략하는 편이 나을 수 있다"고 짚는데, 우리 보고서 답변이 바로 그 경우다(조각 6개, 3,875자). 효과는 문맥이 길어 답변 모델이 헤매거나 비용이 문맥 길이에 묶일 때 기대할 수 있다. 후보 12개 + 압축은 검색 병목을 일부 푸는 방향이라, 보고서 검색을 고칠 때 같은 평가로 다시 재 본다.

### 실험 13: 보고서 검색 — 하이브리드(day47), RAG-Fusion(day54), Window(day46) — **하이브리드 채택** (2026-10-09)

**질문:** 실험 10·12가 같은 결론을 냈다. 보고서 답변의 병목은 답변 단계가 아니라 검색이다(정답 페이지가 상위 6개에 드는 질문 12/18). 교안의 세 방법 중 무엇이 검색을 고칠까?

**방법:** 실험 10·12와 같은 18문항·기준 답·판정(각 2회, `scripts/evaluate_report_pages.py compare --variants chunks hybrid fusion window hybrid_window`).
- hybrid (day47): Dense + BM25(조각 1,193개, 건강 색인과 같은 Kiwi 토크나이저 재사용) → RRF, 후보 각 20개 → 상위 6개
- fusion (day54): 질문 + 모델이 바꿔 쓴 검색어 2개(추론 low)로 각각 Dense 검색 → RRF
- window (day46 Sentence Window를 조각 단위로): Dense 상위 6개 조각마다 같은 보고서의 앞뒤 조각을 붙임(겹친 200자 제거)
- hybrid_window: hybrid + window

| | 정답 | 일부 | 오답 | 보류 | 정답 페이지 포함 | 평균 문맥 | 검색 시간 p50 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 지금 (Dense) | 23/36 | 5 | 3 | 5 | 12/18 | 3,875자 | – |
| **hybrid** | **30/36** | 2 | 2 | 2 | **16/18** | 4,375자 | 0.17초 |
| fusion | 23/36 | 4 | 2 | 7 | 12/18 | 3,946자 | 2.8초 |
| window | 25/36 | 5 | 2 | 4 | 12/18 | 11,755자 | – |
| hybrid + window | 29/36 | 3 | 2 | 2 | 16/18 | 12,098자 | 0.17초 |

- **같은 질문끼리(McNemar):** hybrid는 지금보다 7번 더 맞히고 잃은 것은 0번(p=0.016). fusion은 차이 0, window는 2번 더(p=0.5), hybrid + window는 7번 더·1번 덜(p=0.07)로 hybrid보다 낫지 않았다.
- **왜 hybrid인가(해석):** 보고서 질문은 "의료·보험서비스 연구", "델파이 조사", "장묘 서비스 불만 유형"처럼 보고서에 그대로 나오는 용어를 쓴다. BM25는 이런 용어가 글자 그대로 있는 조각을 올려 주므로 임베딩만 쓸 때 놓친 페이지를 채운 것으로 보인다. 건강 검색에서 하이브리드가 이긴 것(실험 3)과 같은 방향의 결과다.
- **fusion이 안 된 이유:** 바꿔 쓴 검색어가 같은 문서를 다시 찾았다(교안도 "같은 문서만 나오면 유지할 이유 없음"이라고 한다). 모델 호출 하나(2.8초)만 늘었다.
- **window가 작은 이유:** 정답 페이지를 새로 찾지는 못하고(12/18 그대로) 이미 찾은 표의 잘린 부분만 붙인다. 문맥이 3배가 된다.

**적용:** `src/tools/report.py`의 `search_reports_hybrid()`를 챗봇 보고서 답변(`analyze_report`), 보고서 CRAG(`search_reports`), 방문 준비 팀의 진료비 조사(`search_report_stats`)가 함께 쓴다. BM25 색인(`resources.load_report_bm25_index`)은 건강 색인의 토크나이저를 재사용해 Kiwi(약 290MB)를 하나 더 올리지 않고, 앱 워밍업과 방문 보고서 페이지 준비 단계에서 미리 만든다(조각 1,193개, 몇 초). fusion과 window 코드는 평가 스크립트에만 남겼다.

### 실험: 기본 관리 질문 30개 (2026-10-10)

**왜:** 배포 앱에서 "심장사상충 약 얼마나 자주 먹여야 돼요?"에 "검색된 자료에 그 내용이 없다"는 답이 나왔다. 복용 주기, 접종 간격, 목욕 주기 같은 기본 관리 질문을 근거 부족으로 보류한다면 보호자에게 가장 아쉬운 부분이다. 기존 평가셋(CRAG 60)에는 이런 질문이 없다.

**방법:**
- 질문 세트: `tests/data/basic_care_questions.json`. 진찰 없이 수의사가 일반적으로 답할 수 있는 질문 30개를 측정 전에 썼다.
- 실행: `uv run python scripts/evaluate_crag.py --questions tests/data/basic_care_questions.json`. 앱과 같은 경로이고 실제 모델을 부른다.
- 채점: 앱의 판정(answer / partial / abstain)은 "자료에 구체적 주기는 없지만 …"처럼 일부만 답한 경우를 가르지 못한다. 그래서 답을 직접 읽고 **질문의 핵심 사실이나 방법을 주었는가**로 채점했다.

**결과 (검색 후보 5개, 지금 설정):**

| 채점 | 개수 | 문항 |
| --- | ---: | --- |
| 핵심을 답함 | 20 | 심장사상충 매달, 종합백신 2~4주 간격, 광견병 매년, 목욕 1~3주, 양치 매일, 구충 3~4개월, 외부기생충 매달, 중성화 시기, 먹으면 안 되는 음식, 산책, 음수량, 체온, 비만 기준(보고서), 퍼피 사료 기간, 이갈이, 눈물 자국, 항문낭, 배변 훈련, 접종 후 목욕, 스케일링 주기 |
| 일부만 | 3 | 귀 청소(주기만, 방법 없음), 급여 횟수(4개월령만), 생리 중 관리(세척만) |
| 핵심을 못 줌 | 7 | 발톱 깎는 주기, 건강검진 시작 나이, 노견 사료 전환 시기, 열사병 예방, 간식 양, 빗질 주기, 진드기 떼는 법 |

- 같은 질문을 같은 대화 안에서 물은 배포 앱과 달리, 여기서는 심장사상충 질문에 "매달 한 번"이라고 답했다. 그 질문을 검색하면 필요한 답이 1위에 나온다. 배포 앱에서 보류한 것은 앞선 대화(진료비, 일산 질문)로 검색어가 바뀐 탓으로 보이지만, 확인하지는 않았다.

**못 준 7개의 원인 (필요한 사실이 담긴 답변이 앱 검색 상위 50건 중 몇 위에 있나):**

| 원인 | 문항 | 근거 |
| --- | --- | --- |
| 후보 밖에 있음 | 진드기 떼는 법 | "핀셋으로, 머리가 남지 않게"가 6·7위. CRAG는 상위 5건만 평가한다 |
| 다른 질문의 답변 속에만 있음 | 발톱 주기, 노견 사료 시기 | "발톱 컷팅은 월 1회"는 입양 적응을 묻는 상담의 답변에 있다. 검색은 질문 글로 하므로 닿지 않는다(상위 50건 밖) |
| 자료에 거의 없음 | 열사병 예방, 간식 양, 빗질 주기 | 상위 50건에 해당 사실이 없다. 빗질은 21·22위에 언급만 있다 |
| 다른 경로로 감 | 건강검진 시작 나이 | 보고서 분석 경로로 가서 "1년에 한 번 검진이 가장 흔하다"는 설문만 인용했다 |

**검색 후보를 8개로 늘리면? (같은 날, 각 1번 실행)**

| | 후보 5 | 후보 8 |
| --- | ---: | ---: |
| 기본 관리 30: 핵심을 답함 / 일부 / 못 줌 | 20 / 3 / 7 | 20 / 3 / 7 |
| CRAG 60: 답할 질문 20개 중 보류 플래그 | 0 | 0 |
| CRAG 60: 답하면 안 되는 20개 중 보류 (보류 문구로 끝난 답) | 16 | 17 |
| 문항당 토큰 (기본 관리 / CRAG) | 3,251 / 3,823 | 4,040 / 4,547 |
| 기본 관리 응답 시간 p90 | 7.1초 | 8.3초 |

- 진드기 질문은 후보 8개에서 핀셋으로 떼는 법을 제대로 답했다. 하지만 음수량 질문이 보류로 바뀌어 합계는 같았다.
- 후보 수와 상관없는 보고서 질문(r20)도 결과가 바뀌었다. 실행마다 1~2문항씩 바뀌는 편차가 있다는 뜻이다.
- 토큰은 19~24% 늘었다. **후보는 5개로 둔다.**
- CRAG 60의 보류는 앱의 보류 문구("답변을 드리지 않았습니다")로 끝난 답만 셌다. "자료에 없다"로 시작하는 부분 답변까지 보류로 세면, 답할 질문은 4개와 3개, 답하면 안 되는 질문은 18개와 18개다. 이 정의는 기존 기록과 달라서 비교에 쓰지 않았다.

**결론:**
- 기본 관리 질문의 약 1/4은 검색 순위가 아니라 **자료 구성**이 원인이다. AI Hub 상담은 증상 상담 위주다. 일상 관리 사실은 다른 질문의 답변 속에 흩어져 있거나 아예 없다.
- 고칠 수 있는 길은 두 가지이고, 둘 다 하지 않았다.
  - 답변 글도 검색하기: 색인이 두 배가 되고 평가를 다시 해야 한다.
  - 공개된 관리 지침을 근거 자료로 추가하기: 출처와 라이선스부터 확인해야 한다.
