# 건강 RAG 검색 실험

## 현재 상태 (2026-09-28 기준)

건강 질문은 **Dense + BM25 하이브리드, 동일 가중치 RRF**로 검색한다(PR #1, 커밋 `ce324f6f`).

| 설정 | 값 |
| --- | --- |
| Dense | Chroma `pet_care`, `jhgan/ko-sroberta-multitask` |
| BM25 | `rank_bm25.BM25Okapi`, Chroma 전체 문서로 메모리에 색인 |
| BM25 토크나이저 | Kiwi 형태소 분석, 명사(`N*`)·외국어(`SL`)·숫자(`SN`)만 사용 |
| 각 검색기 후보 수 | 12 |
| 결합 | RRF, c=60, 가중치 0.5 / 0.5 (실험 4에서 조정 효과 없음 확인), 동점은 문서 ID 순 |
| 최종 반환 | 기본 3건 (UI에서 1~5) |
| 메타데이터 필터 | Dense는 Chroma `filter`, BM25는 같은 조건을 파이썬으로 평가 |

## 평가 기준 (꼭 읽을 것)

- **정답 규칙:** 검색 문서의 `meta.lifeCycle`, `meta.department`, `meta.disease` 세 값이 질문과 **모두 정확히 일치**하면 적중.
- **이 지표는 의료적 정확도가 아니다.** 같은 질병이라도 연령 단계가 다르면 오답으로 처리되므로 절대값이 낮게 나온다. 방법끼리 비교하는 상대 지표로만 쓴다.
- 검증 데이터에 `기타`가 없으므로 `기타` 그룹 성능은 측정되지 않는다([data.md](data.md)).

## 실험 기록

### 1. 답변 의미 유사도 (2026-08-24, Dense only)

`notebooks/rag_retrieval_evaluation.ipynb`, validation 50건 샘플, top-k 3

| 지표 | 값 |
| --- | ---: |
| 생성 답변 ↔ 정답 답변 평균 cosine | 0.7448 |
| 검색 근거 중 최고 ↔ 정답 평균 cosine | 0.7721 |
| `hit@3` (메타데이터 일치) | 0.2000 |

**해석:** 생성 답변이 검색 근거보다 정답에서 더 멀다. 생성 단계에서 근거의 정보가 일부 사라진다는 뜻이고, 검색뿐 아니라 프롬프트도 개선 대상이다.

### 2. 문자 n-gram 재정렬 — **기각** (2026-09-27)

Dense 후보 12건을 질문과 문서의 2·3-gram 겹침 비율로 재정렬(`src/health_retrieval.py`). 추가 모델 없이 질병명 일치를 높이려는 시도.

validation 561건 전체, 출처 `output/health_retrieval_comparison.json` (생성: `uv run python tests/evaluate_health_retrieval.py`)

| 방법 | hit@3 | MRR@3 | 미적중 |
| --- | ---: | ---: | ---: |
| Dense (기준) | 0.2264 | 0.1503 | 434 |
| Dense + 재정렬 | 0.2228 | 0.1583 | 436 |

**결정:** 적용하지 않음. 사전에 정한 채택 조건(전체 `hit@3` 개선, 비`기타` 악화 없음)을 통과하지 못했다. MRR은 소폭 올랐지만 적중 수 자체가 줄었다. 코드는 평가용으로만 남아 있다.

### 3. Dense + BM25 RRF — **채택** (2026-09-28)

validation 561건, 생성: `uv run python scripts/evaluate_hybrid_search.py` → `output/hybrid_retrieval_benchmark.json` (재측정본 `..._day47_retest.json`, 품질 수치 동일)

| 방법 | hit@3 | MRR@3 | 미적중 |
| --- | ---: | ---: | ---: |
| Dense | 0.2264 | 0.1503 | 434 |
| BM25 | 0.2531 | 0.1800 | 419 |
| **Hybrid (RRF)** | **0.2674** | **0.1866** | **411** |

지연 시간 (로컬, 561회):

| 단계 | 평균 | 중앙값 | p95 |
| --- | ---: | ---: | ---: |
| Dense | 171 ms | 176 ms | 234 ms |
| BM25 | 532 ms | 409 ms | 1,333 ms |
| Hybrid 전체 | 704 ms | 598 ms | 1,558 ms |

**결정:** 적용. Dense 대비 hit@3가 +4.1%p(상대 +18%), 미적중이 23건 줄었다.

> **정정 (2026-10-02, 실험 4):** 위 하이브리드 수치는 벤치마크 스크립트 안의 RRF로 측정한 값이다. 이 RRF는 점수가 같으면 BM25 문서를 앞에 둔다. 운영 코드(`src/hybrid_retrieval.py`)는 동점을 문서 ID 문자열 순으로 처리한다. 같은 후보로 운영 코드를 재현하면 **hit@3 0.2620, MRR@3 0.1842, 미적중 414**다. Dense 대비 개선(+3.6%p)이라는 결론은 그대로다.

**치른 비용:**
- 검색 지연이 약 4배 증가하며, 대부분 BM25 점수 계산(전체 19,206건 매번 계산)에서 나온다.
- 앱 첫 실행 시 BM25 색인 구축에 수 분이 걸린다(`st.cache_resource`로 1회만). Streamlit Cloud 재시작 때마다 다시 발생한다.

**참고:** BM25 단독도 Dense보다 낫다. 이 데이터의 질문은 질병명·증상명 같은 명사 일치가 중요하다는 신호다. 반대로 같은 이유로 n-gram 재정렬(실험 2)은 실패했는데, 문자 단위 겹침은 조사·어미 잡음이 많아서로 추정된다(검증하지 않음).

### 4. RRF 가중치 조정과 후보 재현율 — **가중치는 유지, 리랭킹은 유망** (2026-10-02)

[lecture-review.md](lecture-review.md)의 추천 1단계. 두 가지를 물었다.
1. Dense/BM25 가중치를 0.5/0.5에서 바꾸면 나아지는가?
2. 리랭커가 볼 후보 풀 안에 정답이 얼마나 자주 있는가?

- 실행: `uv run python scripts/evaluate_fusion_weights.py` (검색 결과 캐시 `output/fusion_candidates.json`, 분석만 다시 할 때 `--reuse-candidates`)
- 결과: `output/fusion_weight_sweep.json`
- 운영 코드의 `reciprocal_rank_fusion`을 그대로 써서 앱과 같은 순위를 재현했다. 가중치 인자는 이번에 추가했고 기본값은 0.5/0.5 그대로다.
- **과적합 방지:** 검증셋 561건을 고정 시드(47)로 tune 280건과 holdout 281건으로 나눴다. tune에서 가중치를 고르고 holdout에서 확인했다.

#### 가중치 (w = BM25 가중치, Dense는 1−w)

| w | tune hit@3 | holdout hit@3 | 전체 hit@3 | 전체 MRR@3 | 전체 미적중 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.0 (Dense만) | 0.2393 | 0.2135 | 0.2264 | 0.1503 | 434 |
| 0.3 | 0.2643 | 0.2242 | 0.2442 | 0.1708 | 424 |
| **0.5 (현재)** | 0.2929 | 0.2313 | 0.2620 | 0.1842 | 414 |
| 0.7 (tune 최고) | 0.2929 | 0.2349 | 0.2638 | 0.1892 | 413 |
| 1.0 (BM25만) | 0.2464 | 0.2527 | 0.2496 | 0.1818 | 421 |

전체 w 값(0.0~1.0, 0.1 간격)은 결과 JSON에 있다.

- tune에서 고른 0.7은 holdout에서 0.5보다 **13문항 맞히고 12문항 놓쳐, 순증 1문항**이다. 잡음 수준이다.
- 0.5~0.8 구간은 사실상 평평하다. 0.5 아래로 내리면(Dense 쪽) 확실히 나빠진다.
- **결정:** 0.5/0.5를 유지한다.

#### 동점 처리

0.5/0.5에서는 561건 중 **441건**이 상위 4건 안에 RRF 점수 동점을 가진다. Dense k위 문서와 BM25 k위 문서가 각각 한쪽에만 있으면 점수가 같아지기 때문이다. 운영 코드는 이 동점을 문서 ID 문자열 순으로 정하고 있어서 사실상 임의다.

| 동점 처리 | tune hit@3 | holdout hit@3 |
| --- | ---: | ---: |
| 문서 ID 순 (현재 운영) | 0.2929 | 0.2313 |
| BM25 우선 (예전 벤치마크) | 0.2964 | 0.2384 |
| Dense 우선 | 0.2857 | 0.2100 |

BM25 우선은 holdout에서 5문항 얻고 3문항 잃었다. 방향은 일관되지만 차이가 작다. 큰 성능 개선이라기보다 **임의 순서를 의도된 순서로 바꾸는 정리 작업**으로 볼 만하다(→ [open-questions.md](open-questions.md)).

#### 후보 재현율 — 이번 실험의 핵심

정답 문서가 후보 풀 어딘가에 있는 비율:

| 후보 풀 | 재현율 | 정답 포함 문항 |
| --- | ---: | ---: |
| **Dense 12 + BM25 12 (현재 앱)** | **0.6114** | 343 / 561 |
| Dense 20 + BM25 20 | 0.7023 | 394 / 561 |
| Dense 50 + BM25 50 | 0.8021 | 450 / 561 |

- 현재 풀에서도 정답이 있는 문항은 343개인데, 상위 3건에 드는 것은 147개(0.2620)뿐이다. **196문항은 정답이 후보에 있는데 순위에서 밀린다.** 순서를 다시 매기는 리랭커가 개선할 여지가 이만큼 있다는 뜻이다.
- 풀을 50+50으로 넓히면 재현율이 80%까지 오른다. 다만 리랭커가 점수를 매길 쌍도 그만큼 늘어난다(최대 약 100쌍, CPU 지연 증가).
- 111문항은 50+50 풀에도 정답이 없다. 리랭킹으로는 해결할 수 없고, 질의 변환이나 필터, 평가 기준 쪽의 문제다.
- **주의:** 정답 규칙이 메타데이터 3개 완전 일치라서, 같은 증상을 다룬 유용한 문서도 연령 단계가 다르면 오답으로 처리된다. 재현율과 hit@3 모두 이 기준에서의 상대 비교다.

**결론:** 가중치 조정으로 얻을 것은 없다. 리랭킹(추천 2단계)을 시도할 근거는 충분하다. 다음 실험은 Cross-Encoder로 현재 풀(최대 24건)을 재정렬해 hit@3와 질문당 지연을 측정하는 것이다.
