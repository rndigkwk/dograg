# 반려동물 시설 데이터 (`data/places.db`)

2026-10-07에 동물병원 하나였던 SQLite DB를 **공공데이터 6종, 38,529곳**의 시설 DB로 바꿨다. 재생성: `uv run python scripts/build_places_db.py` (원천 CSV는 저장소에 없음, 스크립트 docstring에 경로와 출처).

## 왜 하나의 테이블인가

종류마다 테이블을 나누면 챗봇이 만드는 SQL이 종류 수만큼 복잡해지고, 지도·거리 계산·지역 검색 코드도 종류마다 반복된다. 그래서 `place` 테이블 하나에 `kind` 컬럼으로 구분하고, 종류마다 다른 정보(동반 시설의 운영시간·크기 제한 등)는 `info` JSON 컬럼에 넣었다.

- LLM이 만든 SQL은 `kind = '<질문에서 찾은 종류>'` 조건이 없으면 쓰지 않고 정해진 SQL로 바꾼다. "동물약국"을 물었는데 병원이 섞여 나오는 일을 막기 위해서다.
- 좌표는 빌드할 때 WGS84 위도·경도로 한 번만 변환한다. 앱은 실행 중에 `pyproj`를 쓰지 않는다.
- 정제 단계별 건수는 `source` 테이블에 함께 저장한다. 데이터 소개 페이지의 "반려동물 시설 데이터" 탭이 이 표를 그대로 보여 준다.

정제 내용:

- **동물병원:** `영업/정상`만 썼다(폐업·휴업·말소 5,137건 제외). 좌표 EPSG:5174를 WGS84로 바꾸고 국내 범위(위도 33~39, 경도 124~132)를 벗어나면 좌표만 비웠다.
- **동물약국:** 수집 단계에서 상태코드 01(영업/정상)만 저장한 파일이다. 좌표가 `(0, 0)`이거나 없는 673곳은 좌표 없이 남겼다.
- **동반 시설:** 아래 "출처 간 중복" 참고. 여행지 871 · 카페 801 · 펜션 407 · 박물관 201 · 미술관 19 · 식당 14 · 문예회관 4 · 호텔 1. 417곳은 반려견 추가 요금이 있다.
- **미용·위탁:** 주소가 읍·면·동까지만 공개되고 좌표가 없어 지역 검색만 지원한다. 전화번호는 72%(미용)·75%(위탁)가 `***`로 가려져 있어 비웠다. 위탁업체 중 미용·판매·전시업을 함께 등록한 곳은 `info.other_licenses`에 남겼다.
- **장묘:** 좌표가 없고 주소가 시·군 단위인 경우가 많아 화면에서는 시·도로만 거른다.
- **공통:** 전화번호의 `***`, 주소·홈페이지의 `null`·`정보없음`은 빈 값으로 바꿨다. 전화번호는 숫자만 남긴 뒤 국번 규칙(02, 050X 안심번호, 1588 같은 전국 대표번호, 0XX 지역·휴대전화, 지역번호 없는 7~8자리)에 따라 하이픈을 다시 넣었다. 병원 데이터는 원본이 `025434037`처럼 숫자만 있었다. 규칙에 맞지 않는 4건(`02022088`, `001035443333` 등 원본 오류로 보이는 값)은 원본 그대로 두었다. 시·도 이름은 `경기`→`경기도`, `전라남도`·`광주광역시`→`전남광주통합특별시`처럼 현재 행정구역 이름으로 통일했다(16개 시·도로 수렴 확인).

## 출처 간 중복: 문화시설 데이터를 어디까지 쓸 것인가

문화정보원 데이터 70,650행 중 **46,105행이 동물약국**이었다. 이름+주소로 중복을 지우면 **8,443곳**이다. 같은 약국이 평균 5.5번 들어 있다. 행정안전부 공식 약국 데이터는 13,692곳이고 작성일도 더 최근이다.

- **결정:** 문화시설 데이터에서 의료(병원·약국)와 서비스(미용·용품·위탁) 분류 67,054행은 쓰지 않았다. 같은 종류는 공식 인허가 데이터를 쓴다.
- 남긴 것은 공식 데이터에 없는 **반려견과 함께 갈 수 있는 곳**(여행·식당카페·문화시설)이다.
- 그중 `반려동물 동반 가능정보 = N` 1,215곳은 뺐다. 이름에 "반려동물 동반 가능 시설"이 붙은 데이터인데도 3분의 1이 동반 불가였다.
- 이름+주소 중복 63건을 지웠다.
- 작성일이 2022년인 곳이 2,076곳(90%)이라 운영시간·요금은 바뀌었을 수 있다. 답변과 화면에 "방문 전 전화로 확인" 안내를 항상 붙인다.

## 예전 병원 데이터와 비교

- 예전 `hospital.db`(5,448곳)와 새 데이터(5,459곳)를 이름+도로명주소로 맞춰 보면 5,425곳이 같고, 예전에만 있는 곳 22곳(새 데이터의 영업/정상 목록에 없음), 새로 생긴 곳 34곳이다. 주소 표기가 바뀐 곳도 이 차이에 섞여 있을 수 있다.
- 예전 DB의 좌표는 모두 EPSG:5174로 일관됐다. 다만 같은 데이터의 CSV(팀 단계의 `hospital_completed.csv`)에는 경위도 값이 그대로 들어간 행이 208개 섞여 있었다. 새 DB는 원천에서 다시 만들어 이 CSV를 쓰지 않고, 2026-10-10 저장소에서 지웠다.
- 예전 데이터에는 영업 상태와 전화번호가 없었다. 새 데이터는 영업/정상만 담고 전화번호가 56%에 있다.

## 챗봇에서 종류를 고르는 규칙

`src/tools/places.py`의 `place_kind()`가 질문에서 종류를 찾는다.

- "동물약국", "애견미용", "펫호텔", "애견동반", "장례식장"처럼 종류가 분명한 말은 바로 그 종류로 정한다.
- "약국", "미용", "카페", "펜션"은 단독으로 쓰이면 다른 뜻일 수 있다("약국에서 산 해열제 먹여도 돼?", "미용 후 피부가 빨개요"). 그래서 "근처·어디·찾아·추천" 같은 검색 표현이 함께 있을 때만 시설 검색으로 본다.
- "장례", "장묘" 단독은 보고서 주제(장묘 서비스 실태)라서 시설 검색 키워드에 넣지 않았다.
- 지역 이름은 DB 주소에 실제로 있는 단어만 인정한다. 예전 정규식은 "대형견**도**", "애견**동**반"을 지역(도·동)으로 잘못 뽑아 검색 결과가 0곳이 됐다.

## "24시간 하는 곳" (2026-10-09)

데이터에는 영업시간이 없다. 그래서 "24시간", "야간", "밤에", "새벽", "응급" 진료를 묻는 병원 질문은 **이름에 24시·응급·야간이 들어간 병원만** 보여 주고, 그 기준을 답에 밝힌다("영업시간 정보가 없어, 이름에 24시·응급·야간이 들어간 동물병원만 골랐습니다. 실제로 지금 진료하는지는 전화로 확인하세요"). 응급 질문에서 쓰던 규칙(`EMERGENCY_NAME_WORDS`)과 같다.
- 이어지는 질문도 된다: "강남구 동물병원 알려줘" → "그중에 24시간 하는 곳도 있어?"는 앞 질문의 지역을 쓰고, 이름 조건만 더한다. 전에는 같은 10곳을 다시 보여 줬다.
- 위치를 쓰는 "가장 가까운 24시 동물병원"도 같은 조건으로 거른다. 해당 지역에 없으면 전체 목록 대신 없다고 말하고 전화 확인을 권한다.
- 측정: 질문 4개(지역 직접 2, 이어지는 질문 2) 모두 이름 기준에 맞는 병원만 나왔다(강남구 5곳, 마포구 1곳, 송파구 2곳).

## "수원", "부산", "강남": 짧은 지역 이름 (2026-10-09)

**문제:** 지역은 주소 형태("수원시", "부산광역시", "강남구")로만 알아봤다. 사람들이 흔히 쓰는 "수원 동물병원", "부산 동물병원"은 지역을 못 찾아, LLM이 SQL을 쓰고 답 문장까지 만들었다. 그래서 느렸고 가끔 틀렸다. 복합 질문의 목록 표시도 이 두 질문만 4.4~5.5초 걸렸다.

**바꾼 것 (`src/tools/places.py`):**
- `short_region_names()`: 저장된 주소의 시·군·구 이름에서 끝 글자를 뗀 짧은 이름(수원시 → 수원, 강남구 → 강남, 해운대구 → 해운대)과 시·도 줄임말(부산, 경기, 충북 …)을 주소 단어로 잇는다(274개).
- 짧은 이름 뒤가 끝, 공백·문장부호, 또는 "에서·에·의·쪽·지역·근처·인근·주변·시내"일 때만 지역으로 본다. 그래서 "고양이"는 고양시가 아니고, "남양주"는 양주시가 아니다.
- **모델에 맡기는 이름 두 개:**
  - "광주": 경기도 광주시와 옛 광주광역시(주소에서는 전남광주통합특별시의 구)가 겹친다.
  - "공주": 반려견을 "우리 공주"라고 부르는 보호자가 많다.
  - 한 글자 이름(중구 → 중)은 쓰지 않는다.
- **같이 고친 버그:** 정해진 SQL이 동반 시설 카테고리를 거르지 않았다. 그래서 "춘천 반려견 동반 카페"에 여행지가 6곳 섞였다. 이제 질문의 카페·펜션·식당·호텔·박물관·미술관·여행지·출장 미용 단어로 `category`를 거른다. 이 버그는 "강남구 …"처럼 원래 정해진 SQL로 가던 질문에도 있었다.
- 증상 + 병원 질문에서 증상 부분을 자를 때(`router.symptom_part`)도 짧은 지역 이름 앞에서 자른다.

**측정 (`scripts/evaluate_region_names.py`, `tests/data/region_names.json` 16문항: 짧은 이름 14 + 지역처럼 보이는 단어 2):**

| | 모든 결과가 그 지역 | LLM이 SQL을 씀 | 시간 p50 / 최대 |
| --- | ---: | ---: | ---: |
| 이전 | 13/16 | 14/16 | 4.4초 / 8.9초 |
| **지금** | **16/16** | **0/16** | **0.01초 / 0.28초** |

- **이전에 틀린 세 건:**
  - "성남 동물약국": 0/10. LLM이 쓴 SQL이 성남시 밖을 골랐다.
  - "강남 동물병원": 5/10. '강남대로'가 주소에 있는 다른 구가 섞였다.
  - "수원": 9/10.
- 시설 라우팅 평가 36문항은 변경 전후 모두 오류 0.
- 복합 질문 8개에서 병원 목록이 화면에 나오는 시점의 최대가 5.53초 → 0.44초. 수원·부산 질문이 0.04~0.31초가 됐다.
- **남은 것:** "서울 출장 미용"은 종류를 동물병원으로 판별한다. "미용"만으로는 미용업으로 보지 않는 기존 규칙 때문이다. 지역과는 따로 고칠 일이다.

## 하지 않은 것

- **한국관광공사 반려동물 동반여행 API**(`data/pet_travel_*`): 목록 9,674곳은 다 모았지만 동반 조건 상세는 36%만 조회됐다. 상세가 다 모이면 동반 시설에 합칠 수 있다.
- **주소 → 좌표 변환(지오코딩):** 미용·위탁·장묘업체 좌표를 만들 수 있지만 외부 API 호출과 정확도 검증이 필요해 보류했다.
- **영업 여부 실시간 확인:** 공공데이터는 인허가 기준이다. 실제 영업·영업시간·재고는 알 수 없다.
