# 웹 앱(Next.js) 첫 화면 무게

웹 앱은 Vercel에 정적 페이지로 올라가고, 답은 브라우저가 API(Cloud Run)에서 직접 받는다(ADR-0008).
화면이 늦게 뜨는 원인은 두 가지뿐이다. 페이지마다 처음 받는 JS와 홈 사진이다.

## 2026-10-23: 마크다운은 답이 올 때, 사진은 보이는 크기로

**측정 (운영 홈, 앱 안 브라우저):** HTML 5KB, TTFB 53ms, JS 청크 172KB(전송량).
홈 사진 3장이 357KB였다. Unsplash 링크가 `w=1200`만 주고 있었다. 세로 사진 원본(1200x1924)이 약 440px 너비의 4:3 틀로 그대로 왔다.

**`next build`의 First Load JS:** 마크다운(`react-markdown` + `remark-gfm`)을 쓰는 페이지만 무거웠다.

| 페이지 | 전 | 후 |
| --- | ---: | ---: |
| `/chat` | 232 kB | **188 kB** |
| `/reports` | 222 kB | **178 kB** |
| `/visit-prep` | 230 kB | **184 kB** |
| 나머지 페이지 | 104~179 kB | 같음 |

- **마크다운:** `components/Markdown.tsx`가 `MarkdownBody`를 `React.lazy`로 따로 받는다. 마크다운은 답이 온 뒤에만 그린다. 묶음이 오기 전에는 같은 글을 줄바꿈만 살려 보여 준다.
- **홈 사진:** `components/HeroImage.tsx`가 Unsplash에서 4:3으로 잘라 480·800·1200px 중 화면에 맞는 것을 받는다(`srcset`, `sizes`). 첫 사진만 `fetchPriority=high`이다. 로컬 확인(창 1024px, 배율 1.25): 사진 4번 요청 138KB(전 357KB). 미리 받기가 480px을 한 번 더 받는다(20KB).
- 바꾸지 않은 것: Supabase 로그인 라이브러리(로그인 화면들의 약 65kB)는 첫 화면에서 로그인 상태를 알아야 해서 그대로 둔다. Next 이미지 최적화는 Vercel 사용량이 들고 Unsplash가 이미 크기를 맞춰 준다.

## 2026-10-23: Lighthouse 전 페이지 점검, 대비와 채팅 흔들림

운영 9개 페이지를 Lighthouse 13.5(모바일)로 쟀다.

| 페이지 | 성능 | 접근성 | 모범 사례 | LCP | CLS |
| --- | ---: | ---: | ---: | ---: | ---: |
| 홈 | 93 | 100 | 100 | 2.7초 | 0 |
| 채팅 | 88 | **95** | 100 | 3.0초 | **0.123** |
| 시설 | 91 | 100 | 100 | 3.0초 | 0.073 |
| 진료비 | 89 | **96** | 100 | 3.1초 | 0 |
| 데이터·관리 일정·보고서·방문 준비·기억 | 90~97 | 100 | 100 | 2.0~3.4초 | 0 |

- **대비:** 보조 글자색 `#66728d`가 연한 보라·베이지 바탕에서 4.22~4.25로 기준 4.5에 못 미쳤다. `#5f6b86`(흰 바탕 5.3, 연한 바탕 4.7 이상)으로 바꿨다.
- **채팅 흔들림:** 첫 방문 저장 안내는 브라우저 기록을 읽어야 보일지 정해진다. 그래서 첫 화면이 그려진 뒤 대화 영역 위에 끼어들어 대화 전체를 밀었다. 안내를 첫 인사 문구 아래(대화 영역 안)로 옮겼다. 로컬 빌드에서 CLS 0.123 → 0, 채팅·진료비 접근성 100.
- **검색 노출(SEO 60):** Vercel이 `*.vercel.app` 주소에 `X-Robots-Tag: noindex`를 붙인다. 앱 코드 문제가 아니다. 노출할지는 소유자가 정한다(직접 도메인 연결).
- **LCP 2~3.4초:** 대부분 글자가 그려지기까지의 지연(element render delay)이다. 점수가 이미 88 이상이라 손대지 않았다.

## 2026-10-23: 대기·오류 화면

- **전:** 기다리는 동안 "⏳ 질문을 확인하고 있습니다…" 한 줄만 보였다. API가 잠에서 깨는 첫 질문(15~27초) 동안 왜 늦는지, 얼마나 기다렸는지 알 수 없었고 멈출 수도 없었다. 실패하면 인터넷이 끊겼든 서버가 실패했든 "잠시 뒤 다시 질문해 주세요" 하나였고, 같은 질문을 다시 쳐야 했다.
- **후 (`components/Waiting.tsx`, `lib/failure.ts`):**
  - 대기 줄에 경과 초를 보여 준다.
  - 8초가 지나도 API가 아무 단계도 알리지 않았으면 "처음 질문은 서버를 깨우느라 20초쯤 걸릴 수 있습니다"를 덧붙인다. 60초가 넘으면 "평소보다 오래 걸린다"고 알린다.
  - 채팅에는 3초 뒤 **멈추기** 버튼이 생긴다.
  - 실패 문구는 원인별로 나눈다: 연결 끊김(오프라인, fetch 실패) / 서버 오류(5xx) / 그 밖은 페이지의 원래 문구.
  - 채팅의 실패·멈춘 답에는 **같은 질문 다시 보내기**가 있다. 실패한 시도는 대화에 남기지 않고 바꿔 넣는다.
  - 데이터·진료비·시설 페이지는 불러오기 실패에 **다시 시도** 버튼이 있다.
- **확인:** vitest `lib/failure.test.ts`. Playwright `e2e/waiting.spec.ts`: 503 뒤 다시 보내기, 응답 없는 질문을 멈추기.

## 2026-10-27: 진료비 점 차트를 타일 지도로

- **문제:** 점 차트의 가로축이 데이터 근처(초진 5kg은 7,500원)에서 시작해서 1,000원 차이가 화면 폭의 1/3로 벌어져 보였다. 같은 값(9곳이 10,000원)은 한 줄에 몰렸다. 사용자가 "표가 이상하다"고 했다.
- **결정:** 원본 사이트(animalclinicfee.or.kr)처럼 지도 위에 지역 이름과 금액을 적는다. 다만 실제 경계 대신 같은 크기의 칸(타일 지도)이다. 실제 지도에서는 세종·대전·광주가 너무 작아 누르기 어렵다.
  - 처음에는 시·도 17칸(`lib/feeTiles.ts` `PROVINCES`, 손으로 배치)이다. 칸을 누르면 그 시·도의 시·군·구 지도로 바뀌고 "← 전국 지도"로 돌아온다.
  - 금액별 색은 넣지 않는다(사용자 결정). 칸에는 이름과 중간값만 있다. 고른 칸만 강조색이다.
  - 시·군·구 칸의 자리는 `scripts/build_fee_tiles.py`가 정해 `lib/feeTiles.json`에 넣는다. 위치는 `data/places.db`에서 그 시·군·구 주소를 가진 시설 좌표의 중앙값이다(경계 데이터 없음). 먼 곳부터 가까운 빈 칸에 넣고, 두 칸을 바꾸면 더 가까워질 때 바꾼다. 빈 행·열은 지운다. 파일에는 이름과 칸 위치만 있고 금액은 없다.
  - 조사가 바뀌어 시·군·구가 달라지면 이 스크립트를 다시 돌린다.
  - 휴대전화(375px)에서 서울은 7열, 칸 폭 42px이다. 그래서 640px 미만에서는 글자를 10px로 줄이고 금액의 "원"을 빼며, 단위는 설명에 적는다. 17개 시·도 모두 넘치는 칸이 없다.
  - 정확한 비교와 화면 낭독기를 위해 "표로 보기"(접힘)에 같은 지역을 중간값 높은 순으로 둔다. 마우스·Tab으로 평균과 범위를 읽어 주는 줄은 그대로다.
  - `dotAxis`, `gapLabel`은 지웠다.
- **확인:** vitest `feeTiles`(시·도 17곳, 칸 겹침 없음, 강남구가 강서구 동쪽), unittest `build_fee_tiles`, Playwright 진료비 테스트(전국 → 서울 → 강동구 → 표 → 전국, 데스크톱·모바일).

## 2026-10-24: 고정 자료는 서버에서 미리 (데이터·시설·진료비)

- **원인:** Lighthouse에서 이 세 페이지의 LCP(2.9~3.1초)는 브라우저가 페이지를 연 뒤 API에서 받은 자료를 그리는 시간이었다. 데이터 소개는 2.2초가 자료를 기다리는 데 들었다.
- **바꾼 것:** 이 자료(통계, 시설 종류·지역 목록, 진료비 항목과 첫 항목 수치)는 하루에 한 번 바뀔까 말까 하다. 그래서 각 페이지의 서버 컴포넌트가 받아 HTML에 넣는다.
  - Vercel은 그 페이지를 하루 보관한다(`export const revalidate = 86400`, ISR).
  - `lib/prefetch.ts` `prefetched`: 실패하거나 30초가 넘으면 null이고, 그때는 예전처럼 브라우저가 받는다. API가 잠들어 있으면 깨는 데 15~27초가 걸리므로 30초다. 이 대기는 빌드와 하루 한 번 새로 받을 때만 있고 방문자는 기다리지 않는다.
  - 다른 진료 항목을 고르거나 다시 시도하면 브라우저가 받는다.
- **확인:** 빌드된 HTML에 차트 제목·진료 항목·시설 종류가 들어 있다. 화면 테스트는 가짜 API로 빌드해 서버 받기가 실패하는 길(브라우저가 받는 길)을 그대로 지난다.
- **운영 측정(배포 뒤, Lighthouse 모바일):**

  | 페이지 | LCP | 성능 |
  | --- | ---: | ---: |
  | 데이터 소개 | 3.0 → **2.4초** | 89 → 92 |
  | 시설 찾기 | 3.1 → **2.2초** | 91 → 96 |
  | 진료비 | 2.9 → **2.0초** | 90 → 96 |

  접근성은 셋 다 100 그대로다. 데이터 소개에 남은 지연은 차트 스크립트가 늦게 실행되는 시간으로, 2.5초 기준 안이라 두었다.

## 키보드 흐름 (2026-10-24)

- **무엇:** 마우스 없이 Tab·Enter·화살표·Escape만으로 쓰는지 점검하고 빈틈 4개를 고쳤다.
  - 첫 Tab에 `본문으로 건너뛰기`(메뉴가 두 줄인 묶음 페이지에서 메뉴를 건너뛴다). 모든 컨트롤에 같은 청록 포커스 테두리(`:focus-visible`, 마우스 클릭에는 안 보임).
  - 상단 묶음 메뉴: Escape로 닫으면 포커스가 묶음 버튼으로 돌아가고, 마지막 페이지에서 Tab으로 나가면 닫힌다(전에는 포커스가 사라지거나 목록이 열린 채 남았다).
  - 채팅: 답을 받는 동안 입력창이 비활성이라 포커스가 페이지로 떨어졌다. Enter로 보낸 질문은 답이 끝나면 입력창으로 돌아온다(보내기 버튼을 누른 경우는 그대로: 휴대폰 자판이 튀어나오지 않게).
  - 데이터 소개 탭: ARIA 탭 방식(Tab 한 번, 좌우·Home·End로 이동).
- **둘째 묶음(같은 날, 방문 준비·시설 찾기):**
  - 방문 준비 보고서: 만드는 동안 칸이 비활성이라 포커스가 떨어졌다. 단계가 끝나면 다음 할 곳으로 옮긴다(되묻기 → 답변 칸, 완성 → 보고서, 실패 → `이어서 만들기`).
  - 시설 찾기: 종류 고르기 라디오는 숨겨져 있어 포커스가 안 보였다 → 알약 버튼에 테두리. `조회`·`현재 위치 사용`은 찾는 동안 `disabled` 대신 `aria-disabled`로 두어 포커스가 버튼에 남는다.
  - 지도(Leaflet)는 Tab으로 들어가 화살표로 움직이고, 같은 시설은 위 목록에 다 있어서 그대로 두었다.
- **확인:** `e2e/keyboard.spec.ts` 6개(데스크톱·휴대폰).

## 로그인 전 "우리 아이" 메뉴 표시 (2026-10-24)

- **무엇:** 로그인하지 않았을 때 메뉴(상단 묶음 목록, 묶음 탭 줄)의 `관리 일정` 옆에 "이 기기", `상담 기억` 옆에 "로그인 필요"를 작게 붙인다. 각 페이지 안 안내는 열어 봐야 보이고, 메뉴에서는 어디에 저장되는지 알 수 없었다(외부 재검토 제안). 로그인하면, 그리고 세션을 확인하기 전에는 붙이지 않는다(로그인한 사람에게 깜빡이지 않게).
- **확인:** `e2e/account.spec.ts` 1개(로그아웃 → 표시, 로그인 → 없음).

## 관리 일정: 수의사와 정한 날, 캘린더 파일 (2026-10-27)

- **수의사와 정한 다음 날:** 항목마다 입력 칸을 더했다. 그 날짜가 마지막으로 한 날보다 뒤면 지침 계산 대신 그 날짜를 쓴다(`lib/careSchedule.ts` `scheduleFor`). 그 뒤에 마지막으로 한 날을 고치면 정한 날은 끝난 것으로 보고 다시 지침으로 계산한다. 지침이 정한 날을 덮어쓰지 않는다. 화면에는 "(수의사와 정한 날)" / "(지침으로 계산한 날)"로 구분한다.
  - 저장은 따로 `ragdog:v1:care_planned`(이 브라우저). 미래 날짜도 받는다. 방문 보고서의 "할 때가 된 항목"도 같은 규칙을 따른다.
- **캘린더 파일(.ics):** 브라우저에서 만든다(`lib/careCalendar.ts`, 서버 없음). 날짜가 있는 항목마다 다음 날짜 하나를 종일 일정으로, 전날 21시 알림(`TRIGGER:-PT3H`)과 함께 넣는다.
  - 지난 날짜는 오늘로 옮기고, 지침의 늦은 날도 지났으면 제목에 "(지남)"을 붙인다.
  - UID가 항목마다 고정(`care-<id>@ragdog`)이라 다시 받으면 캘린더가 같은 일정을 바꿀 수 있다(앱에 따라 다름).
  - 반복 규칙(RRULE)은 넣지 않았다. 다음 날짜는 실제로 한 날에 따라 바뀌기 때문이다.
  - 75옥텟 줄 접기는 UTF-8 글자 중간에서 자르지 않는다.
- **확인:** vitest(정한 날 우선·해제, 보고서 항목, 저장, 일정 개수·날짜·지남·접기·이스케이프), Playwright(정한 날 입력·새로고침 유지·파일 받기 내용).

## 여정 테스트 (2026-10-27)

페이지마다 테스트가 있어도, 한 페이지에서 한 일이 다음 페이지로 넘어가는지는 따로 보지 않았다. 10-27 검토에서 상담 → 방문 보고서로 마지막 질문만 넘어가던 문제가 그 틈이었다. `web/e2e/journeys.spec.ts`가 여러 페이지를 잇는 흐름을 모델 없이(가짜 API) 검사한다.

- **관리 일정 → 홈 질문 → 상담 2턴 → 인용 → 방문 보고서:** 보고서 요청에 두 질문의 사실(어제부터 설사, 5살, 7kg, 구토 없음)과 기한이 지난 광견병 접종이 모두 들어가는지 본다. 빠진 사실 목록이 비어야 한다. 모델 답변은 들어가면 안 된다.
- **상담 장소 답변 → 장소 상세 → 카카오맵 길찾기 → 그 구의 진료비 → 진료비 지도:** 같은 구(강남구)의 같은 금액이 시설 찾기와 진료비 지도에서 같게 나오는지 본다.
- 실제 모델로 하는 여정 평가는 비용 때문에 넣지 않았다.

## 예시로 둘러보기 (/demo, 2026-10-27)

처음 온 사람(포트폴리오를 보는 사람 포함)이 질문을 직접 쓰지 않고도 2분 안에 서비스의 흐름을 보게 하는 페이지다. 홈의 질문 상자 아래 "처음이라면 예시로 2분 둘러보기"에서 연다. 비어 있는 상담 화면의 인사말("어떻게 답하는지 예시 보기")과 소개(/data) 머리글 아래에도 링크가 있다(링크마다 e2e 1개).

- **내용:** 가상의 14살 말티즈 한 마리로 세 단계를 보인다. 증상 질문과 [사례 1] 인용 답, 근거가 없어 답하지 않은 질문(우주여행), 방문 준비 보고서.
- **손으로 쓰지 않았다:** 답 두 개는 `src/chatbot.py`가 2026-10-27에 실제로 만든 것(모델 호출 약 6번, Langfuse 끔)이다. 보고서는 2026-10-19 팀이 만들고 검수자가 문장 19개를 근거와 대조해 통과시킨 것(`output/visit_prep/20261019_175325`)이다. 데이터는 `web/src/lib/demoSample.json`에 있다.
- **화면:** 채팅과 같은 `AnswerView`, 보고서와 같은 `Markdown`으로 그린다. 그래서 인용 링크와 근거 카드가 실제 화면과 똑같이 동작한다. 질문을 넘기지 않으므로 메모 저장, 방문 준비 보내기, 피드백은 나오지 않는다.
- **표시:** 페이지 머리와 본문 위 안내에 "예시 화면입니다… 아래 반려견은 가상입니다"를 둔다.
- **API를 부르지 않는다:** `e2e/demo.spec.ts`가 페이지를 다시 불러온 뒤 API로 간 요청이 0인지 확인한다.
- 답이나 보고서 형식이 바뀌면 JSON을 다시 만든다. 낡은 예시는 실제 화면과 달라 보인다.
