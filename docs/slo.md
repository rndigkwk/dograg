# 서비스 수준 목표 (SLO)

배포된 API(Cloud Run `ragdog-api`, Langfuse 환경 `cloudrun-api`)가 지킬 목표다. 매주 월요일 `Weekly service levels` 워크플로가 최근 7일 기록으로 확인한다(`scripts/slo_report.py`, 모델 호출 없음). 목표를 어기면 실패하고, `Alert on failure` 워크플로가 `alert` 이슈를 연다.

| 지표 | 목표 | 2026-10-19 측정 (최근 28일) | 왜 이 값인가 |
| --- | ---: | ---: | --- |
| 오류율 (실행 기록의 `error`) | ≤ 2% | 0% (67문항) | 모델·DB 오류는 대체 경로가 있어 드물어야 한다. 50문항 중 1번을 넘으면 원인을 본다 |
| 건강 상담 p95 지연 | ≤ 25초 | 19.1초 | 답을 스트리밍하기 전까지 기다리는 시간. 측정값에 여유를 30% 둔다 |
| 보고서 p95 지연 | ≤ 45초 | 17.1초 | 두세 보고서를 함께 찾고 긴 답을 쓴다. 여러 보고서 질문의 근거가 늘어난 것(10-18)을 감안했다 |
| 건강 상담 보류율 ("자료에 없다") | ≤ 30% | 26.3% (38문항 중 10) | 평가 세트에서는 답할 수 있는 질문의 보류가 0~2/20이다. 운영 질문에는 범위 밖 질문이 섞이므로 넓게 잡았다 |
| 질문당 모델 비용 | ≤ $0.01 | $0.0005 | 하루 한도 질문 수를 다 써도 월 비용이 작게 유지되는 선 |

- **판정 최소 표본:** 7일에 20문항이 안 되면 숫자만 보여 주고 판정하지 않는다. 표본이 작으면 한 번의 느린 답이 p95를 정한다.
- **지연:** 서버가 기록한 실행 시간(`latency_ms`)이다. 첫 방문 대기(인스턴스 0개에서 깨어나기, [cloud-run](wiki/cloud-run.md))는 들어가지 않는다.
- **비용:** Langfuse가 모델 호출마다 계산한 비용의 합이다. 임베딩과 Supabase·Cloud Run 요금은 들어가지 않는다.
- **보류율 26%는 지켜볼 값이다.** 목표 안이지만, 평가 세트보다 훨씬 높다.
  - 운영 기록은 질문 글을 가린다(`src/tracing.py`). 그래서 어떤 질문이 보류됐는지는 `ragdog_data_gaps`(자료에 없던 내용)로 본다.
  - 자료가 비는 질문을 모아 평가 세트로 옮기는 일은 [평가 범위표](wiki/eval-coverage.md)의 후속 과제다.

## 알림

`.github/workflows/alert-on-failure.yml`이 main에서 아래 워크플로가 실패하면 이슈를 연다. 같은 워크플로의 이슈가 열려 있으면 새로 열지 않고 댓글을 단다.

| 워크플로 | 무엇이 실패인가 |
| --- | --- |
| Weekly regression evaluation | 평가 점수가 기준선 밖 (`scripts/check_regression.py`) |
| Weekly service levels | 위 SLO 위반 |
| Keep deployed app awake and working | 두 배포 중 하나가 응답하지 않음 |
| Deploy to Cloud Run | 빌드·배포 실패, 새 리비전이 `/health`에 나타나지 않음 |
| Roll back the API | 롤백 대상 리비전이 응답하지 않음 |

이슈는 저장소 소유자에게 GitHub 메일로 간다. 별도의 알림 서비스나 비용은 없다.
