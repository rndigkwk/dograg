## 0. 전체 구조

```text
질문 ─▶ 분류 (규칙 → 분류 API)
          ├─ date   날짜 (코드가 답함)
          ├─ fee    진료비 (표를 그대로 옮김, 모델 없음)
          ├─ rag    건강 상담: 하이브리드 검색 → CRAG(근거 평가·재검색·보류) → 근거 기반 답변
          ├─ sql    시설 검색: SQLite 조회 (+ 증상이 같이 있으면 건강 답변도)
          ├─ analysis  보고서 분석: 하이브리드 검색 → 쪽수 인용 답변
          └─ none   일반 대화
방문 준비 보고서 (별도 페이지): 되묻기 → 계획 → 병렬 조사 → 작성 → 문장별 검수
```

- **LangGraph `StateGraph`**(`src/chat_graph.py`): 분류, 검색, 근거 평가, 재검색, 답변, 보류가 모두 노드다. 단계마다 무엇을 했는지 기록(Langfuse)과 진행 표시에 그대로 쓴다.
- **도구 주입**(`src/tools/toolset.py`): 그래프는 도구 묶음을 받아서 쓴다. 테스트에서는 가짜 도구를 넣어 모델·DB 없이 경로를 검증한다.
- **이유:** 처음에는 한 파일(`pages/rag.py`)에 화면과 로직이 섞여 있었다. 경로가 늘면서 어느 단계에서 틀렸는지 알기 어려워 노드와 도구로 나눴다([design/modular-tools-and-conversation-memory.md](design/modular-tools-and-conversation-memory.md)).

## 1. 질문 분류 (라우터)

- **하는 일:** 질문을 6개 경로 중 하나로 보낸다.
- **설계:**
  - 날짜·진료비는 다른 판단보다 먼저 규칙으로 잡는다.
  - 신호가 하나뿐인 질문(약 85%)은 키워드 규칙이 0ms에 정한다.
  - 나머지만 OpenAI Decisions(분류 전용 API)에 묻는다. 실패하거나 거절하면 채팅 모델 라우터가 정한다.
  - 증상과 시설 요청이 함께 있으면("설사하는데 마포구 병원 어디?") 두 경로를 모두 돈다.
- **이유:**
  - 규칙은 빠르고 틀리면 고치기 쉽다.
  - 애매한 질문만 모델에 맡겼다. 채팅 모델 1.4초가 분류 API로 0.36초가 됐고, 정확도는 같았다(134/136).
  - 진료비를 규칙으로 먼저 잡는 이유는 숫자를 모델이 옮기다 틀릴 일을 없애기 위해서다.
- **대안:** 모든 질문을 모델로 분류(느리고 비쌈), 규칙만 쓰기(복합·애매한 질문에 약함).
- **한계:** 규칙은 처음 보는 말투에 약하다. 그래서 규칙을 고칠 때마다 holdout 세트로 다시 잰다([router.md](wiki/router.md)).

## 2. 건강 상담 (RAG)

### 검색
- **설계:**
  - AI Hub 상담 19,206건의 질문 글을 대상으로, 질문 임베딩(Dense)과 키워드(BM25, Kiwi 명사) 두 가지로 각각 12건씩 찾는다.
  - 두 결과를 RRF로 합친다.
  - 임베딩은 ko-sroberta를 보호자 말투로 미세조정해 ONNX int8로 돌린다.
- **이유:**
  - 짧은 구어체 질문("오줌 색이 달라졌어요")과 긴 상담 글은 단어가 겹치지 않는다. 그래서 Dense만으로는 핵심 단어를, BM25만으로는 뜻을 놓친다. 하이브리드로 hit@3 0.2264 → 0.2620.
  - 미세조정으로 짧은 질문 useful@3 0.600 → 0.783.
  - ONNX int8은 torch 없이 돌아서 메모리가 1,587 → 985MB가 됐다.
- **필터를 쓰지 않는 이유:** 질문에서 연령·진료과를 추론해 거르면 정확할 것 같았다. 그런데 말뭉치 라벨이 질문 본문과 34%·59%만 맞아서, 필터를 빼자 0.141 → 0.264로 올랐다.
- **임베딩을 데이터마다 따로 고른 이유:** 건강 상담을 OpenAI 임베딩으로 바꾸면 hit@3이 0.2674 → 0.2353으로 떨어졌다. 그래서 보고서만 OpenAI를 쓴다.
- **대안(측정 후 미적용):** 리랭커 4종, CRAG 판정으로 재정렬, 후보 확대. 효과가 없거나 배포 환경에서 너무 느리고 무거웠다([improvement-log.md](improvement-log.md) 7절).

### 근거 평가와 보류 (CRAG)
- **설계:**
  - 검색 후보 5건을 모델이 "질문에 쓸 수 있는가"로 판정한다.
  - 쓸 근거가 없으면 검색어를 한 번 바꿔 다시 찾는다. 이때 진료과 필터를 푼다.
  - 그래도 없으면 **보류**한다. 보류할 때는 무엇을 찾아봤고 무엇이 없었는지 알려 준다.
  - 근거 평가는 추론을 끄고 돌린다.
- **이유:**
  - 의료 상담에서 그럴듯한 지어내기는 답하지 않는 것보다 위험하다.
  - 근거 없는 질문 보류 0 → 16/20, 답할 질문을 잘못 보류한 비율 1/38.
  - 추론을 끄자 첫 글자가 9.1 → 6.0초로 빨라졌다.
- **보고서에는 켜지 않은 이유:** 보고서 질문에서는 정답 페이지 12 → 10으로 오히려 나빠졌다.

### 답변
- **설계:** 근거에 있는 사실만 쓰게 한다(검사 이름, 빈도, 약 이름 등). 응급 신호가 보이면 답변보다 가까운 병원을 먼저 보여 준다.
- **이유:** 충실도 평가에서 나온 지어내기 유형을 프롬프트 규칙으로 막아 0.79 → 0.94가 됐다.
- **Self-RAG(답을 근거와 다시 대조)를 끈 이유:** 충실도 차이가 판정 흔들림 안(0.927 → 0.941)이었는데, 시간은 2배(8.5 → 16.1초)였다.
- **한계:** 일상 관리 질문의 약 1/4은 자료에 사실이 없거나 다른 상담의 답변 속에만 있다. 검색이 질문 글만 보기 때문이다([retrieval-experiments.md](wiki/retrieval-experiments.md) "기본 관리 질문").

## 3. 응급 신호 감지

- **설계:**
  1. 규칙(`src/health_safety.py`): 호흡곤란, 쓰러짐, 경련, 독성 물질 섭취 등을 찾고, 부정("경련은 없었고")과 가정("~하면")은 거른다.
  2. 규칙이 놓친 질문만 분류 API로 3택 판단한다(지금 응급 / 곧 진료 / 아님).
  3. 응급이면 답변 전에 경고와 가까운 병원을 표시한다.
- **이유:**
  - 응급에서는 놓치는 쪽이 더 위험하지만, 경고가 너무 많으면 아무도 믿지 않는다.
  - "응급/아님" 2택은 실제 보호자 질문의 32.5%에 경고를 띄웠다. 3택으로 바꾸자 9%가 됐다.
  - 규칙을 만들기 전에 써 둔 holdout2 기준으로 1/20 → 19/20, 오탐 0.
- **한계:** 평가셋과 경고 문구는 수의사 검토를 받지 않았다([safety-and-evidence.md](wiki/safety-and-evidence.md)).

## 4. 시설 찾기

- **설계:**
  - 공공데이터 6종 38,529곳(동물병원, 약국, 동반 시설, 미용, 위탁, 장묘)을 SQLite에 넣었다.
  - 지역·종류·개수를 규칙으로 뽑아 고정된 SQL로 조회한다. 읽기 전용이다.
  - 위치를 주면 거리순으로 보여 준다.
  - 지역은 짧은 이름("수원", "일산")도 읽는다.
- **이유:**
  - "마포구 동물병원"은 뜻 검색이 아니라 정확한 조건 검색이다. 벡터 검색은 다른 구의 병원을 섞는다.
  - 모델이 SQL을 쓰게 했을 때는 4~9초가 걸리고 14개 지역 중 3개를 놓쳤다. 짧은 지역 이름을 규칙으로 읽자 모델 호출 없이 16/16이었다.
- **증상 + 병원 질문:** 병원 목록을 먼저(0.38초) 보여 주고 증상 답변은 아래에 둔다. 아픈 아이를 둔 보호자에게 먼저 필요한 것은 갈 곳이다.
- **한계:** 인허가 데이터라 실제 영업 여부와 영업시간을 모른다. 답변마다 전화 확인을 안내한다([places-data.md](wiki/places-data.md)).

## 5. 지역별 진료비

- **설계:**
  - 농림축산식품부 2025 진료비 조사(시·군·구 201곳, 항목 19종, 6,413행)를 표로 두었다.
  - 진료비 질문이면 모델 없이 지역·전국의 중간·평균·최저·최고를 그대로 옮긴다.
  - 체중은 조사 기준(5·10·20kg) 중 가까운 값으로 맞춘다.
- **이유:** 금액은 모델이 옮기다 틀리면 안 되는 정보다. "개별 병원 가격이 아님"을 매번 밝힌다.
- **판별 규칙을 검증한 방식:**
  - 규칙을 다듬은 세트(dev)는 24/24였지만, 처음 보는 말투(holdout)에서는 23/30이었다.
  - 그 실패로 고친 뒤, 고치기 전에 써 둔 holdout2로 쟀더니 20/20, 오분류 2/15였다.
- **한계:** "입원비 대신 통원" 같은 질문은 아직 진료비로 잘못 간다([vet-fees.md](wiki/vet-fees.md)).

## 6. 보고서 분석

- **설계:** 반려동물 보고서 5종을 조각으로 나눠 OpenAI 임베딩 + BM25 하이브리드로 찾고, 보고서 이름과 쪽수를 인용해 답한다.
- **이유:**
  - 보고서 질문은 "델파이 조사", "장묘 불만 유형"처럼 문서에 그대로 나오는 용어를 쓴다. 그래서 BM25가 크게 도왔다(정답 23 → 30/36).
  - 페이지 통째로 답하기(25 → 23)와 문맥 압축(차이 없음, 1.6초 증가)은 효과가 없었다. 병목은 생성이 아니라 검색이었다.

## 7. 대화 기억과 개인정보

- **설계:**
  - **저장:** 대화와 반려견 정보는 **브라우저에만** 저장하고 서버에는 남기지 않는다. Langfuse로 보내는 기록은 마스킹한다.
  - **단기 기억:** 최근 6턴을 그대로 쓰고, 그보다 오래된 대화는 3턴씩 모아 요약한다.
  - **장기 기억:** 반려견 정보(나이, 체중, 지병)는 답변과 검색에 반영한다.
  - **검색어:**
    - 앞선 건강 질문이 있으면 저비용 모델이 혼자 읽히는 검색어를 쓴다.
    - 건강 답변을 받은 질문만 넘긴다. 앱이 답변마다 기록한 경로로 가린다. 그래서 "24시 하는 곳은?"처럼 시설 단어가 없는 시설 후속 질문도 빠진다(앞선 건강 질문 목록 0/30 → 30/30).
    - 시설 질문은 자기 지역이 있으면 그 지역만 쓰고, 없으면 지역이 나온 앞 질문을 이어받는다.
- **이유:**
  - 반려견 건강 상담은 민감한 내용이고, 로그인 없이 쓰는 서비스다.
  - 긴 대화에서 10턴 전에 말한 지병을 잊지 않도록 요약을 넣었다. 지병을 다룬 근거가 잡힌 대화가 2/6 → 5/6이 됐다.
  - 앞선 질문을 모두 붙이던 방식은 새 주제의 검색을 망쳤다(holdout 0.38 → 1.0).
- **한계:**
  - 앞 질문을 이어받는 질문의 검색은 0.72 → 0.64로 조금 나빠졌다.
  - 대화가 브라우저에 있어서 다른 기기나 다른 배포 주소에서는 보이지 않는다.

## 8. 방문 준비 보고서 (멀티에이전트 팀)

- **하는 일:** 보호자 상담으로 수의사에게 보여 줄 보고서를 만든다. 진단은 하지 않는다.
- **설계** (`team/`, core → tools → agents → graph → main):

| 단계 | 하는 일 | 제한 |
| --- | --- | --- |
| 되묻기 | 빠진 정보를 최대 3개 질문 (응급이면 묻지 않음, LangGraph `interrupt`) | 답 300자, 멈춘 실행은 30분 뒤 삭제 |
| 계획 | 증상·병원·비용 조사로 나눔 | 처음 5개, 추가 조사 2개 |
| 조사 | 작업마다 조사원이 **병렬로** 자기 도구만 사용 | 도구 3번, 모델 6번 |
| 작성 | 조사 결과의 사실만, 문장마다 근거 번호 | |
| 검수 | 문장마다 근거와 대조, 근거 없으면 반려 | 다시 쓰기 2번까지, 같은 지적 반복이면 사람 확인 |

- **이유:**
  - **역할을 나눈 이유:** 한 모델에게 다 맡기면 조사와 작성이 섞여 근거 없는 문장이 생긴다. 검수를 따로 둬서 "검수 통과"를 근거가 확인된 상태로 정의했다.
  - **상한을 둔 이유:** 처음에는 작성자가 도구로 얻을 수 없는 정보(영업 여부 등)를 계속 요청해 반복 상한에 걸렸다(통과율 0.70). 추가 조사를 한 번으로 묶고 검수 추론을 낮춰 통과율 1.00, 시간 68 → 49초가 됐다.
  - **실패 처리:**
    - 조사 하나가 실패해도 나머지는 살린다.
    - 필수 조사(증상)가 실패하면 쓰지 않고 사람 확인으로 넘긴다.
    - 진료비 조사가 실패하면 고정 안내로 채우고, 실패했다는 사실을 보고서에 적는다.
  - **답 없이 끝난 조사원:** API가 응답을 추론 조각 101개에서 자르는 경우가 있다. 이때는 도구 결과만 넣어 새로 묻는다. 이어서 묻던 방식(6/13)과 달리 15/15였다.
- **감시:** 노드 방문 횟수, 반복 의심 비율, 다시 묻기 비율을 매주 평가한다([visit-prep-team.md](wiki/visit-prep-team.md)).

## 9. 관측과 평가

- **Langfuse:** 질문·답변 원문은 길이로만 기록(마스킹)한다. 경로, 단계별 시간, 토큰, 피드백(👍/👎)을 남긴다.
- **평가 세트를 데이터셋으로 운영:** CRAG 60, 라우팅 36, 방문 보고서 상담 12개를 Langfuse 실험으로 돌려, 실행끼리 문항별로 비교한다.
- **매주 회귀 평가:**
  - 정확도, 보류율, 응답 시간, 방문 팀 통과율·반복·다시 묻기 비율이 기준을 넘으면 GitHub Actions가 실패한다.
  - 기준은 병합 시 결과보다 조금 느슨하게 잡았다. 같은 설정도 모델 호출마다 60문항 중 1~2문항이 흔들리기 때문이다.
- **배포 점검:** 8시간마다, 그리고 병합 직후에 두 배포의 모든 페이지와 챗봇 응답을 헤드리스 브라우저로 확인한다([observability.md](wiki/observability.md)).

## 10. 배포

- **두 곳에서 운영한다:** Cloud Run(주)과 Streamlit Community Cloud(예비). 같은 저장소의 같은 코드다.
- **메모리:**
  - 무료 환경(보장 690MB)에 맞추려고 BM25 토큰을 미리 계산해 두고(첫 질문 165초 → 8초), 임베딩을 ONNX int8로 돌린다(985MB).
  - Cloud Run은 2GiB(측정 최고 1.06GiB)다.
- **이미지에 데이터를 넣는다:** 시작 때 내려받지 않아 메모리를 아끼고 시작이 빠르다. 비공개 저장소에만 올린다.
- **인증:** 키 파일 없는 Workload Identity로 GitHub Actions가 배포한다.
- **공유 DB 없음:** 두 배포가 서로 의존하지 않게 했다. 대화를 서버에 두지 않는 원칙과도 맞다.
- 자세히: [docker-deployment.md](docker-deployment.md)
