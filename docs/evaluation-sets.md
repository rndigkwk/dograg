# 평가 세트와 지표

라그도그의 모든 개선은 아래 평가 세트로 전후를 재서 결정했다. 이 문서는 한 곳에서 다음을 답한다(2026-11-06 기준).

- 무엇을 재려고 어떤 세트를 어떻게 만들었는가.
- 몇 문항이고 왜 그 크기인가.
- 어떤 지표로 재고, 왜 그 지표를 골랐는가. 기준값은 어디서 나왔는가.
- 실험 결과를 믿어도 되는 이유와, 믿을 때 조심할 점.

세트는 35개, 약 1,380문항이다(`tests/data/`). 실험 결과와 과정은 [wiki](wiki/README.md)에, 세트 구성의 빈칸 점검은 [eval-coverage.md](wiki/eval-coverage.md)에 있다.

## 1. 신뢰성을 위한 규칙

모든 세트에 같은 규칙을 적용했다. 세트 파일의 `description`·`note`에 각 규칙을 지켰는지 적혀 있다.

| 규칙 | 무엇을 막나 | 어떻게 지키나 |
| --- | --- | --- |
| **측정 전에 쓴다** | 결과를 본 뒤 맞는 문항만 고르는 것 | 세트를 쓰고 저장한 뒤에 처음 잰다. 날짜와 "측정 전에 씀"을 파일에 남긴다 |
| **고르는 세트와 보고하는 세트를 나눈다** (dev / holdout) | 시험 문제로 공부한 점수 | 규칙·체크포인트·프롬프트는 dev로만 고친다. 결과는 holdout으로 보고한다. 고치다 holdout을 봤으면 그 holdout은 holdout이 아니라고 적고(`informed_fix`) 새 holdout을 쓴다 |
| **기준을 미리 정한다** | 결과를 본 뒤 기준을 바꾸는 것 | 예: 임베딩 교체는 "holdout에서 B보다 McNemar p<0.05, 긴 상담이 B 이상"을 학습 전에 정했다. GIST는 세 시드 모두 B보다 높았지만 이 기준을 못 넘어 바꾸지 않았다 |
| **흔들림을 잰다** | 모델 호출의 우연을 개선으로 읽는 것 | 같은 세트를 3~5번 돌려 흔들림을 잰다. 기준값은 그 폭의 두 배쯤 아래에 둔다 |
| **같은 문항끼리 비교한다** | 문항 구성이 달라서 생긴 차이 | 두 방법을 같은 문항으로 재고, 갈린 문항 수로 McNemar 검정을 한다 |
| **판사를 검증한다** | LLM 판사의 치우침을 품질로 읽는 것 | 사람이 블라인드로 매긴 표와 일치도(Cohen κ)를 쟀다(7절) |
| **누수를 센다** | 학습 데이터와 겹친 문항의 쉬운 점수 | 평가 질문 561개 중 53개(9%)가 학습 자료에 같은 상담의 다른 판이 있다. 이 문항을 뺀 점수도 함께 적는다. 2026-11-02부터는 학습에서도 뺀다 |
| **운영에서 보충한다** | 평가 세트가 실제 질문과 멀어지는 것 | 매달 1일 이슈가 열리면 배포 앱의 "자료에 없다" 문장과 👎 피드백을 읽고, 빠진 유형을 세트에 더한다. 운영 질문 원문은 저장하지 않는다 |

## 2. 지표: 무엇을 재고, 왜 골랐나

### 검색

| 지표 | 무엇을 재나 | 왜 이 지표인가 |
| --- | --- | --- |
| **`useful@3`** (주 지표) | 상위 3건 안에 "바로 쓸모 있음"(2점) 문서가 하나라도 있는 질문의 비율 | 앱의 답은 상위 근거로 쓴다. 그래서 "답에 쓸 근거가 위에 있는가"를 직접 잰다. 처음 쓴 라벨 일치(`hit@3`)는 라벨이 질문 본문과 연령 34%, 진료과 59%만 맞아 품질을 크게 낮춰 잡았다(0.29 대 0.72). 같은 상담의 복사본 53쌍도 라벨이 셋 다 같은 쌍은 15쌍뿐이었다. 그래서 2026-10-08부터 주 지표를 바꿨다 |
| `relevant@3` | 상위 3건에 1점 이상(관련 있음) 문서가 있는 비율 | 보조 지표다. 거의 늘 0.99라 비교에는 쓰지 않는다. 검색이 엉뚱한 곳을 찾는지 보는 경보로만 쓴다 |
| `precision@3` | 상위 3건 중 1점 이상 비율 | 리랭커처럼 순서만 바꾸는 방법은 `useful@3`가 같아도 이 값이 움직인다 |
| `hit@3`, `mrr@10` (라벨·합성 질의) | 라벨이 같은 문서가 상위에 있는지, 합성 질의의 원래 상담이 몇 위인지 | 판사 없이 싸게 재는 값이다. 예전 실험과 비교하거나 학습 중 dev 확인에만 쓴다. 결정에는 쓰지 않는다 |
| **후보 안 최선** | 후보 풀(Dense 12 + BM25 12)에 2점 문서가 있는 비율 | 순서를 바꾸면 얼마나 오를 수 있는지의 천장이다. 리랭커를 시도할지 정할 때 썼다(0.93 대 0.79) |

### 답할지, 보류할지 (CRAG 60)

| 지표 | 무엇을 재나 | 왜 이 지표인가 |
| --- | --- | --- |
| **`accuracy`** | 답해야 할 질문에 답하고, 보류해야 할 질문에 보류한 비율 | 이 앱의 첫 약속인 "근거가 없으면 지어내지 않는다"를 한 숫자로 본다 |
| **`over_abstain`** (지나친 보류) | 답할 수 있는 38문항 중 보류한 비율 | 정확도 하나로는 "다 보류"도 절반은 맞는다. 보호자가 답을 못 받는 쪽의 실패를 따로 본다. 기준 ≤ 0.10 |
| **`missed_abstain`** (놓친 보류) | 보류해야 할 22문항 중 답한 비율 | 지어낼 위험 쪽의 실패다. 의료 상담에서는 이쪽이 더 위험하지만, 검색은 자료 밖 질문에도 늘 무언가를 돌려주므로 0으로 만들기 어렵다. 지금 값(0.18~0.23)을 넘지 않게 지킨다(≤ 0.35) |
| `leads_with_missing` | 첫 문장이 "자료에 없다"로 시작하는 답 | 답할 수 있는 질문인데 거절처럼 읽히는 답을 센다("아는 것을 먼저" 규칙) |
| `names_gap` | 답 어딘가에 빠진 부분을 밝힌 답 | 자료가 일부만 다룰 때 정직하게 밝혔는지 본다. 배포 앱이 빈칸을 모으는 문장 규칙을 그대로 쓴다. 정직한 말투 일부는 놓치므로 아래쪽 값이다 |
| `latency_p90_s` | 90번째로 느린 답의 시간 | 품질을 올리려고 재검색을 늘리면 느려진다. 품질과 함께 경보로 본다 |

### 답이 맞는가 (건강 답변 100)

| 지표 | 무엇을 재나 | 왜 이 지표인가 |
| --- | --- | --- |
| **Answer Correctness** (RAGAS) | 앱의 답과 실제 수의사 답의 주장이 얼마나 겹치는가 | 정답(수의사 답)이 있는 유일한 세트라 "맞는 답"에 가장 가깝다. Ragas·DeepEval 권고대로 강한 신호 하나를 골랐다. 판정을 3번 바꿔도 평균이 0.012 안에서 움직이고, 경로가 틀린 답에서는 절반(0.14)으로 떨어진다. 가장 안정적이면서 민감했다. 절대값이 낮은 것은 수의사 답이 개별 사례라서다. 그래서 경보로만 쓴다(≥ 0.25) |
| **Context Recall** | 수의사 답의 주장 중 검색 근거로 뒷받침되는 비율 | 정확도가 떨어졌을 때 검색 탓인지 답 탓인지 가른다. 검색이 나빠지면 이 값이 먼저 내려간다. 문항별로는 흔들려서(0.2 이상 움직인 문항 21/91) 평균만 본다(≥ 0.35) |
| **Context Precision** | 쓸모 있는 근거가 앞쪽에 오는가 | 순서 문제를 Recall과 따로 본다(≥ 0.85) |
| Answer Relevancy | 답이 질문에 맞는 말인가 | 재 봤지만 쓰지 않는다. 같은 답이 0 → 0.68 → 0으로 바뀌는 문항이 있을 만큼 흔들렸다 |

### 검정과 판정

- **McNemar 검정:** 두 방법이 같은 문항에서 갈린 수(얻음/잃음)만 본다. 같은 문항을 쓰는 비교라서 평균 차보다 검정력이 높고, 문항 난이도 차이를 지운다.
- **안정 문항 재확인:** 기준선 3~5회에서 늘 통과한 문항이 이번에 실패하면 두 번 더 묻는다. 그중 하나라도 실패하면 회귀로 본다(`scripts/recheck_items.py`).
- **네 가지 검사**(`scripts/check_regression.py`): 완전성(기준선과 같은 문항) · 절대 기준 · 기준선 대비 하락 폭 · 안정 문항 회귀. 세트마다 품질 지표는 다섯 개 이하로 둔다.

## 4. 세트별: 무엇을 재려고, 어떻게 만들었나

크기의 이유가 따로 적혀 있지 않은 세트는 "고칠 문제의 유형마다 dev·holdout에 몇 개씩"으로 잡았다.

## 5. 기준값은 어떻게 정했나

- **원칙:** 병합된 결과의 흔들림 폭 아래에 둔다. 모델 호출의 우연으로 실패하지 않게 하되, 실제로 나빠지면 걸리게 한다.
- **예 1 — Answer Correctness ≥ 0.25:** 0.273~0.285(3번 채점), 판정 흔들림 0.012. 가장 낮은 값 아래로 흔들림의 두 배 이상을 뒀다. 경로가 틀린 답(0.14)은 걸린다.
- **예 2 — Context Recall ≥ 0.35, Precision ≥ 0.85:** Recall 0.385~0.418(다섯 번), Precision 0.887·0.903(주간 두 번). 같은 원칙이다(2026-11-06).
- **예 3 — 돌봄 지침 `guide_rate` ≥ 0.81:** 16문항 중 두 문항 흔들림까지 허용했다. 세 문항이 빠지면 지침이나 경로가 깨진 것이다.
- **기준선 대비 하락 폭:** CRAG 정확도 0.05, 경로 0.03, 가드레일 0.045. 3~5회 기준선의 흔들림에서 정했다.
- 기준값과 근거는 `scripts/check_regression.py`의 `LIMITS` 주석에 있다.

## 6. 판사(LLM-as-a-judge) 검증

검색 관련도와 답 정확도는 LLM이 채점한다. 판사를 믿을 수 있는지 따로 쟀다([judge-validation.md](wiki/judge-validation.md)).

| 같은 판사의 일관성 | 20문항 473개 후보 다시 채점 | 같은 점수 86.5%, κ 0.79 | |
| 관련도 판사 대 사람 | 판사 점수별로 16칸씩 48칸을 고르고, 사람이 블라인드로 매겼다 | κ 0.636. 사람이 쓸모없다고 한 칸의 90%를 잡지만, 쓸모 있는 칸은 72%만 인정한다(사람보다 엄격) | 엄격한 쪽이라 개선을 부풀리지 않는다 |

## 7. 알려진 한계

- **작은 세트:** 80문항 holdout으로는 10%p 안팎의 차이를 유의하게 가르기 어렵다. GIST처럼 방향은 같아도 결론을 보류한 경우가 있다.
- **의료 검토 없음:** 평가 질문, 참고 답, 판사 채점 모두 수의사 검토를 받지 않았다.
- **같은 계열 판사:** 질의를 만든 모델, 앱, 판사가 같은 계열이다.
- **CRAG 근거 평가기는 사람 검증이 없다.** 증류 실험에서 자기 일관성만 봤다.
- **복사본:** 평가 질문 53개(9%)가 학습 자료와 같은 상담이다. 비교를 이어 가려고 세트에 남기고, 뺀 점수를 함께 적는다.
- **비공개 데이터:** AI Hub 원문이 든 세트(`crag_eval_questions` 등)는 저장소에 없고 비공개 Hugging Face 데이터셋에 있다. 문항 수와 구성은 이 문서와 세트 메타데이터로 확인할 수 있다.
